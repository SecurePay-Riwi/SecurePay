# Analytics model

**Contract:** `shared/analytics.py` (C1, C2) · **Builders:** `services/analytics/` · **Views:** `services/analytics/sql/` · **Page of the ETL:** [Analytics](../components/analytics.mdx)

This page is the data dictionary (E-10). Every table, column, type and description below comes from `TABLES` in `shared/analytics.py`; `shared/tests/test_analytics_contract.py` fails if a table or a column of the code is missing here. A new column is a small PR on that file, with its row on this page.

## Layers and lineage

```text
engine ──SNS──► analytics consumer ──► raw/decisiones/fecha=<arrival day>/*.jsonl ─┐
generator labels.jsonl ──(services.analytics.labels)──► raw/labels/fecha=<day>/  ──┤
PostgreSQL cases ──(export.py, C6)──► raw/cases/fecha=<day>/                       ──┤
PostgreSQL reconciliation ──(export.py, C6)──► raw/reconciliation/fecha=<day>/     ──┤
Kaggle rows ──(python -m services.analytics.metrics --kaggle)──► raw/metrics/kaggle/ ──┤
                                                                                   ▼
                        build_decisions ──► curated/decisiones/fecha=<day>/ (Parquet, one row per transaction)
                                                                                   ▼
        analytics/<table>/[fecha=<day>/] (Parquet): facts and dimensions below
                                                                                   ▼
        sql/q1..q6 (Athena views)  ──►  Power BI (only the views, D6)
```

| Layer | Path | Format | Written by |
| :--- | :--- | :--- | :--- |
| Raw | `raw/decisiones/fecha=<day>/` | JSON lines, the `transaction.decided` event as it came (may repeat) | Analytics consumer |
| Raw | `raw/labels/fecha=<day>/labels.jsonl` | The generator's labels file, as it is | `python -m services.analytics.labels` |
| Raw | `raw/cases/fecha=<day>/` | `cases.jsonl`, `case_events.jsonl`: the current state | `export.py` (Yulianis) |
| Raw | `raw/reconciliation/fecha=<day>/` | `differences.jsonl`, `runs.jsonl`: the current state | `export.py` (Yulianis) |
| Raw | `raw/metrics/kaggle/` | `rule_metrics.jsonl`, `pattern_coverage.jsonl`: the metrics of the last Kaggle replay (rows of the two tables, ratios as decimal strings) | `python -m services.analytics.metrics --kaggle` |
| Curated | `curated/decisiones/fecha=<day>/` | Parquet with the schema of `curated_decision` | `build_decisions.py` |
| Analytics | `analytics/<table>/` | Parquet with the schema of each table | One builder per group of tables |

- **The day of a decision** is its `transaction_date` in UTC. raw/decisiones is partitioned by the day the event *arrived*, so the builder reads `fecha=<day-1..day+1>` and keeps the transactions of the day: a late event lands in its own day.
- **Deduplication:** raw keeps SQS's repeated deliveries; curated keeps the first event of each `transaction_id` (earliest `processed_at`, then file and line order).
- **Daily tables** are written to `fecha=<value of the partition column>/` and the partition column also stays inside the file. Running a day again replaces its folder: the same day gives the same result.
- **Types:** amounts `decimal(18,2)`, rates `decimal(18,8)`, ratios `decimal(9,4)`, days `date`, moments `timestamp` in UTC. Nobody infers a type: every builder writes with `spark_schema(<table>)`.

## Star schema

```text
                         dim_date (day)
                              │
 dim_rule (rule, rule_version)│            dim_merchant (merchant_id, as_of)
          │                   │                   │
   fact_rule_hit ──── transaction_id ──── fact_decision ──── device_id ──── dim_device (device_id, as_of)
                              │                   │
                         fact_label          fact_case (transaction_id)
                     (transaction_id)

 fact_difference (run_day, partner) ──── dim_partner (partner)
 rule_metrics, pattern_coverage: fact_decision + fact_label + fact_rule_hit (and the Kaggle replay, C5), by rule or pattern and label source
```

## Risk levels (dim_device, dim_merchant, view q6)

Defined in step 0 so the fixtures have an answer key; HU-47 and HU-53 (Yulianis) implement them.

| Kind | HIGH | MEDIUM | LOW |
| :--- | :--- | :--- | :--- |
| Device | `shared` (more than 3 accounts in 30 days, RN-04) **and** at least one `HOLD`/`REJECT` or case in 30 days | `shared`, **or** at least one `HOLD`/`REJECT` or case | Otherwise |
| Merchant | At least one payment labeled fraud **and** at least one `HOLD`/`REJECT` in 30 days | One of the two | Otherwise |

The accounts of a device are the main account of each transaction: the source, or in a top-up the destination (as the engine's `dev:{device}`).

## Views (contract C3)

One Athena view per business question, `services/analytics/sql/q<N>_<name>.sql`, with a control query `sql/control/q<N>.sql` that reaches the same numbers without the view. The SQL is the part Athena (Trino) and Spark SQL share, so `test_views.py` runs both over the fixtures and compares them with `services/analytics/tests/fixtures/expected_views.json`. Power BI reads only these views.

| View | Question | Columns | Owner |
| :--- | :--- | :--- | :--- |
| `q1_transactions` | Transactions by type, currency and channel | `day`, `type`, `currency`, `channel`, `decision`, `transactions`, `amount_usd` | Habith (step 0) |
| `q2_rules` | Rules that fire most, with precision and false positives | `rule`, `rule_version`, `hits`, `true_positives`, `false_positives`, `precision`, `false_positive_rate`, `label_source` (from `rule_metrics`) | Habith (HU-45) |
| `q3_fraud_detection` | Fraud detected and missed, by pattern | `pattern`, `label_source`, `frauds`, `detected`, `missed`, `detection_rate`, `top_rule` (from `pattern_coverage`) | Habith (HU-46) |
| `q4_cases` | Case resolution times and escalations | `day`, `status`, `outcome`, `cases`, `escalated`, `avg_minutes_to_resolve`, `p90_minutes_to_resolve`, `within_sla_pct` | Yulianis (HU-51) |
| `q5_reconciliation` | Reconciliation by partner and age of the differences | `run_day`, `partner`, `type`, `status`, `age_range`, `differences`, `amount_difference_total` | Yulianis (HU-52) |
| `q6_risk` | Riskiest devices and merchants | `kind` (`DEVICE` or `MERCHANT`), `id`, `risk_level`, `accounts_30d`, `transactions_30d`, `held_or_rejected_30d`, `cases_30d`, `rank` | Yulianis (HU-53) |

How the answer key computes each one (`make_fixtures.py`), so the views agree with it:

- **q1:** `COUNT(*)` and `SUM(amount_usd)` of `fact_decision` per day, type, currency, channel and decision.
- **q2:** for each rule of the catalog replayed (not `default_timeout`) and label source: `hits` = labeled transactions where it fired, `true_positives` = those that are fraud, `false_positives` = the rest, `precision` = tp / hits (null with 0 hits), `false_positive_rate` = fp / labeled legitimate transactions. Ratios with 4 decimals, rounded half up. A transaction without a label does not count. Every rule of the catalog has a row (0 hits included) when `dim_rule` has that catalog version. The view shows, per label source, only the latest catalog version (`MAX(CAST(rules_version AS INTEGER))`); its control computes the lake's sources from `fact_decision`, `fact_label`, `fact_rule_hit` and `dim_rule`, and takes the replayed Kaggle rows of `rule_metrics` as they are.
- **q3:** per fraud pattern and label source: `detected` = decision `HOLD` or `REJECT`, or `opens_case`; `missed` = the rest; `detection_rate` = detected / frauds; `top_rule` = the rule that fires most among the detected ones, any rule in `rules_triggered` (ties: alphabetical; null when none was detected). A fraud label without a pattern counts as `UNKNOWN`. Latest catalog version per source and control as in q2.
- **q4:** per day of `created_at`, `status` and `outcome`: `escalated` counts the cases with `escalated_at`; `minutes_to_resolve` is whole minutes (rounded down); `avg_minutes_to_resolve` with 2 decimals, `p90_minutes_to_resolve` the nearest-rank 90th percentile, `within_sla_pct` = resolved in 240 minutes or less × 100 / resolved, 2 decimals; null for cases still open.
- **q5:** per `run_day`, partner, type, status and `age_range` (age counted from `run_day` to the day built): the number of differences and the sum of `amount_difference` (null when the group has none).
- **q6:** only `HIGH` and `MEDIUM`; `rank` within each kind ordered by level, then `held_or_rejected_30d` and `transactions_30d` descending, then id. Merchants have null `accounts_30d` and `cases_30d`.
