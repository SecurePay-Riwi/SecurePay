# Decision engine

**Folder:** `services/decision_engine/` · **Run:** `uv run uvicorn services.decision_engine.main:app --reload`

The engine receives every transaction from the wallet core and answers `APPROVE`, `HOLD` or `REJECT`. In AWS it runs on Fargate behind an ALB; locally, with uvicorn on port 8000. Interactive API docs (Swagger): http://localhost:8000/docs. It shows every status code below with an example, and *Try it out* comes filled with the request example of this page.

## Endpoints

| Method | Path | What it does |
| :--- | :--- | :--- |
| `POST` | `/transactions` | Evaluates a transaction and returns the decision. |
| `POST` | `/security-events` | Stores a device or password change for the account takeover rule. See [Security events](#security-events). |
| `GET` | `/health` | Always `"ok"` while the process runs, plus the publisher counters. |

```json
GET /health
{"status": "ok", "messaging": {"pendientes": 0, "publicados": 1000, "fallidos": 0}}
```

Messaging problems never change `"ok"`: if SNS fails the engine keeps deciding, and the load balancer must not take it out of service.

## Request

```json
POST /transactions
{
  "id": "6f1c2a4e-8b1d-4c3a-9e7f-2d5b8a0c1e34",
  "type": "P2P",
  "channel": "APP",
  "source_account_id": "a8d456b7-ae6a-5481-9a4b-64deb0d295f7",
  "destination_account_id": "3e1a0cdb-e3c9-5dba-b7b1-7ac28a50254a",
  "merchant_id": null,
  "amount": "25.00",
  "currency": "EUR",
  "source_balance_before": "1999.97",
  "source_balance_after": "1974.97",
  "destination_balance_before": "1142.70",
  "destination_balance_after": "1167.70",
  "device_id": "f8692d53-a16a-595f-b796-dfde37f5f4b0",
  "transaction_date": "2026-10-01T08:15:00+00:00"
}
```

The two accounts are the first ones the seed creates (their ids never change), so this exact body answers `200` on a seeded database.

| Field | Rule |
| :--- | :--- |
| `id` | UUID, chosen by the core. The idempotency key. |
| `type` | `P2P`, `QR`, `RECARGA` or `RETIRO`. |
| `channel` | 1 to 30 characters. |
| Accounts | `P2P`: source and destination. `QR`: source and `merchant_id`. `RECARGA`: destination only. `RETIRO`: source only. Source and destination cannot be the same. |
| `amount` | Greater than 0. |
| `currency` | `COP`, `USD`, `EUR` or `JPY`, and it must be the account's currency. |
| Balances | Every account present must bring its balance before and after. |
| Decimals | At most 2 (JPY: 0). `88.910` is accepted as `88.91`; `88.913` is rejected, because rounding would change what the core sent. |
| `device_id` | UUID. It does not need to exist in the database. |
| `transaction_date` | With time zone. |

There is no `user_id`: the owner comes from the account.

## Response

```json
{
  "transaction_id": "6f1c…",
  "decision": "HOLD",
  "decision_reason": "Velocity: 6 outgoing transfers in 10 minutes from the same account.",
  "rules_version": "0",
  "rules_triggered": ["velocity"],
  "opens_case": false,
  "risk_score": 0,
  "by_default": false,
  "processed_at": "2026-10-14T00:10:03.512+00:00",
  "idempotent_replay": false
}
```

- `rules_triggered` lists **every** rule that fired, not only the one that decided (the statement asks every decision to record the rule version and the rules that fired). It feeds the rule effectiveness analysis and lets the cases consumer open a case only for the rules that require one.
- `rules_version` is the version of the [rule catalog](#rule-catalog) the decision used. `"0"` means the defaults in the code; once the rules API (HU-19) publishes catalogs, it is the number of the published version. The rules, the default decision and this field all use the same catalog, read once per decision.
- `opens_case` is `true` when a rule whose catalog entry says `opens_case` fired: by default mule account and restricted list ([Team decisions](../architecture/team-decisions.mdx)). Velocity and the default decision only hold. The cases consumer reads this flag.
- `risk_score` is the sum of the `score` of the rules that fired, at most 100. Every rule of Sprint 2 has score 0; the shared device rule (HU-14) is the first that raises it (30).
- `by_default` is `true` when the rules did not answer in time and the default decision was applied (see [Default decision on timeout](#default-decision-on-timeout)). Then `rules_triggered` is `["default_timeout"]`.
- `idempotent_replay` is `true` when the answer is a stored decision returned to a resend. A decision stored before `rules_version` and `rules_triggered` existed is replayed with `null` and `[]`.

## Status codes

| Code | When |
| :--- | :--- |
| `200` | Decided (or a resend of an already decided id). |
| `400` | Invalid body: missing fields, wrong types, wrong accounts for the type, too many decimals. Includes the validator's `errors`. |
| `409` | The same id is still being decided by another request, or the same id arrived with a different body. |
| `422` | The body is valid but references something unusable: an account or merchant that does not exist, or a currency that is not the account's. |
| `503` | Valkey (idempotency) is not available. |
| `500` | Database error. |

## Rules running today

Thresholds below are the catalog defaults.

| Rule | Decision | How |
| :--- | :--- | :--- |
| Restricted list | `REJECT` | The owner's document, normalized to digits only, is in `listas_restrictivas`. |
| Velocity | `HOLD` | More than 5 outgoing **P2P** transfers in 10 minutes from the same account, measured by event time. |
| Mule account | `HOLD` and opens a case | A **withdrawal** of 80 % or more of the balance, after `P2P` transfers from 3 or more different accounts, all in less than 30 minutes. |
| Shared device | `APPROVE`, `risk_score` +30 | The transaction's device was used by more than 3 accounts in the last 30 days. |
| Account takeover | `HOLD` | A device change and a password change of the source account in the 60 minutes before a `P2P`, `QR` or withdrawal of more than USD 200. See [Account takeover](#account-takeover). |
| Default decision | `APPROVE` below USD 50, `HOLD` from USD 50 | The rules did not answer in 120 ms. Never `REJECT`. |
| Anything else | `APPROVE` | "The transaction did not trigger any configured rule." |

Every enabled rule of the catalog is evaluated, in catalog order, even when one already rejects, and each one that fires adds a `TriggeredRule` (rule code, decision, reason, score, whether it opens a case) to a list. `choose_decision()` turns the list into one decision: **the most severe wins** (`REJECT`, then `HOLD`); with none, `APPROVE`. So an owner on the restricted list who also makes six transfers in a row gets `REJECT` with `rules_triggered: ["restricted_list", "velocity"]`.

```python
# services/decision_engine/decision_service.py
SEVERITY = {Decision.APPROVE: 0, Decision.HOLD: 1, Decision.REJECT: 2}

def choose_decision(triggered: list[TriggeredRule]) -> tuple[Decision, str]:
    if not triggered:
        return Decision.APPROVE, NO_RULES_REASON
    worst = max(triggered, key=lambda r: SEVERITY[r.decision])
    return worst.decision, worst.reason
```

`choose_decision()` is a pure function, so `tests/test_decision_outcomes.py` checks every outcome without PostgreSQL or Valkey. The velocity transfer is recorded even when another rule decides, because the attempt to transfer still counts.

## Rules and the catalog {/* #rule-catalog */}

The project brief asks that rules can be created, versioned, enabled and disabled through an API without a redeploy, and that every decision records the rule version it used (RF-03, RN-08, CA-06). So the code of a rule and its configuration are separate:

- **The catalog** (`shared/rule_catalog.py`) is data: for each rule its `code` (the name in `rules_triggered`), its `type` (which code runs it), `params` (thresholds), `action` (`APPROVE`, `HOLD` or `REJECT`), `opens_case`, `score`, `enabled` and `rule_version`. A `CatalogSnapshot` is the whole catalog at one `version`. The engine and the rules API share these models.
- **The rules** live in `services/decision_engine/rules/`, one module per type with `TYPE` and `evaluate(ctx, rule)`. A rule reads its thresholds from `rule.typed_params()`, never from environment variables, and returns `hit(rule, reason)` when it fires: decision, case and score come from the catalog. `rules/__init__.py` maps each type to its module (`REGISTRY`).
- **`catalog.current()`** returns the catalog the engine decides with. Today it is always the defaults (`DEFAULT_RULES`, version 0); HU-20 makes it read the catalog the rules API publishes in Valkey, without changing its signature.

```python
# services/decision_engine/rules/velocity.py
TYPE = "velocity"

def evaluate(ctx: RuleContext, rule: RuleEntry) -> TriggeredRule | None:
    if ctx.payload.type.value not in TYPES:      # TYPES = {"P2P"}
        return None
    p: VelocityParams = rule.typed_params()
    transfers = count(ctx.outgoing, ctx.t_ms, p.window_minutes)
    if transfers > p.limit:
        return hit(rule, f"Velocity: {transfers} outgoing transfers in ...")
    return None
```

| Code | Type | Rule | Default parameters | Action | Opens case | Score |
| :--- | :--- | :--- | :--- | :--- | :--- | ---: |
| `restricted_list` | `restricted_list` | RN-06 | none | `REJECT` | yes | 0 |
| `velocity` | `velocity` | RN-02 | `window_minutes` 10, `limit` 5 | `HOLD` | no | 0 |
| `mule` | `mule` | RN-03 | `window_minutes` 30, `min_senders` 3, `withdrawn_pct` 80 | `HOLD` | yes | 0 |
| `shared_device` | `shared_device` | RN-04 (HU-14) | `window_days` 30, `max_accounts` 3 | `APPROVE` | no | 30 |
| `splitting` | `splitting` | RN-05 (HU-15) | `window_hours` 24, `min_transactions` 3, `daily_limit_usd` 10000 | `APPROVE` | yes | 40 |
| `account_takeover` | `account_takeover` | RN-07 (HU-17) | `window_minutes` 60, `min_amount_usd` 200 | `HOLD` | no | 0 |
| `default_timeout` | `default_timeout` | RN-01 | `limit_usd` 50 | (default decision) | no | 0 |

- A type the catalog knows but the engine has no code for yet (`splitting` until its story lands) is skipped.
- `default_timeout` is never evaluated as a rule: `default_decision()` reads its `limit_usd`.
- The longest windows the catalog accepts match what the history keeps: velocity up to 24 h (`HISTORY_OUT_HOURS`), mule up to 60 minutes (`HISTORY_IN_MINUTES`), shared device up to 30 days (`HISTORY_DEVICE_DAYS`). The engine refuses to start with a shorter history.
- The history is written before the rules run, whatever rules are enabled, so a rule that is enabled again finds its history.

`tests/test_catalog_contract.py` checks the contract without PostgreSQL or Valkey: the defaults are valid, invalid rules are refused, parameters, decision, case and score come from the catalog, a disabled rule is skipped, a second rule of an existing type takes part, and the catalog order is the evaluation order.

## Default decision on timeout

RN-01 asks for a decision in 200 ms, and for a default one when the engine cannot make it: `APPROVE` below USD 50, `HOLD` from USD 50 up (the `limit_usd` of the catalog's `default_timeout` entry). `process_transaction()` runs the rules in a thread pool and waits `DECISION_TIMEOUT_MS` (120 ms) for them; past that it answers with `default_decision()`. It never rejects: being slow is not a reason to turn a customer down.

- The default decision is stored in the idempotency key and published like any other, so a resend gets the same answer (CA-05).
- A Python thread cannot be stopped, so the late evaluation ends in the background and its result is dropped. It keeps the database session and closes it itself; `get_db()` skips closing a session marked that way. Its history writes stay, like any attempt.
- The amount is converted to USD by `currency.to_usd()`. **For now it uses a fixed snapshot of the 2026-10-01 rates**; HU-42 replaces it with the rate of the transaction's day from the `pagoseguro-exchange-rates` table, without changing the callers.

`tests/test_default_decision.py` covers CA-04 (USD 30 approved, USD 80 held), the limit at exactly USD 50, a rule answer in time, the conversion from COP, a resend after a timeout and the late session.

## Request flow

```python
# services/decision_engine/decision_service.py (simplified)
def process_transaction(session, payload):
    transaction = payload.model_dump(mode="json")
    fingerprint = idem.huella(transaction)          # SHA-256 of the normalized body

    previous = idem.reservar(payload.id, fingerprint)  # SET NX in Valkey
    if previous:
        return previous, True                    # resend: same decision, not published again

    try:
        result = _decide_in_time(session, payload)  # rules, or the default after 120 ms
    except Exception:
        idem.liberar(payload.id)               # no decision: let the retry decide
        raise

    idem.guardar(payload.id, fingerprint, result)  # 1 h TTL
    publisher.publicar(evento_decision(transaction, result))  # does not wait for SNS
    return result, False
```

The engine **does not write to PostgreSQL**. It only reads accounts, merchants, users and the restricted list. The decision is stored in Valkey and published; the [consumers](./consumers.mdx) store what needs storing.

## Idempotency

`services/decision_engine/idempotency.py`. One Valkey key per transaction, `idem:{id}`:

1. The first request **reserves** the id with `SET NX` and a 30-second TTL, storing `PENDING` and a fingerprint of the body. `SET NX` is atomic, so of two simultaneous requests only one wins.
2. It decides and **stores** `DONE` with the decision, with a 1-hour TTL (`IDEMPOTENCY_TTL_SECONDS`).
3. A **resend** with the same body gets the stored decision. If it arrives while the first one is still deciding, it waits up to 100 ms and otherwise gets `409`.
4. The **same id with a different body** is `409`: it is a core error, not a resend.
5. If deciding **fails**, the reservation is deleted so the retry can decide. If the process dies mid-decision, the 30-second reservation expires by itself.

## Account history

`services/decision_engine/history.py`. The rules that look at the past of an account read one shared history instead of each keeping its own key. Two sorted sets per account and one per device, with `transaction_date` in milliseconds as score, so **an event that arrives late lands in its real place**, not at the end:

| Key | What goes in | Member | Kept | Read by |
| :--- | :--- | :--- | :--- | :--- |
| `out:{account}` | What leaves the account: `P2P`, `QR`, `RETIRO` | `id\|type\|amount` | 24 h (`HISTORY_OUT_HOURS`) | Velocity (10 min); splitting later (24 h) |
| `in:{account}` | `P2P` transfers that arrive, with the sender and the amount | `id\|sender_account\|amount` | 60 min (`HISTORY_IN_MINUTES`) | Mule account (30 min) |
| `dev:{device}` | The accounts that used the device; the score is the last time each one was seen | `account_id` | 30 days (`HISTORY_DEVICE_DAYS`) | Shared device (30 days) |

A `P2P` writes twice: `out:` of the source and `in:` of the destination. A `RECARGA` writes nothing to `out:` or `in:` (no sender, no money leaves). Every transaction writes its main account (the source; in a top-up, the destination) to `dev:` of its `device_id`. Each write is a Lua script on **one key** (ZADD, prune what is older than the retention measured from the most recent event, EXPIRE), so two requests for the same account cannot interleave. One key per script on purpose: in ElastiCache Serverless two keys can live on different nodes.

```python
# services/decision_engine/decision_service.py (simplified)
if payload.type in OUTGOING_TYPES:            # P2P, QR, RETIRO
    outgoing = history.record_outgoing(source, tx_id, tx_type, amount, date)
if payload.type == TransactionType.P2P:
    history.record_incoming(destination, tx_id, source, amount, date)
device_accounts = history.record_device(device_id, main_account, date)  # always
```

Decisions about what goes in (Jorge, 2026-10-21):

- **Attempts count, whatever the decision.** The history is written before deciding, in one call. Several people trying to send money to an account that withdraws it right away, or an account trying many transfers, is already the signal, even if the engine held one of them. Counting only approved ones would need a second write after deciding, inside the 200 ms. Every decision still reaches the event with its triggered rules.
- **The amount is in the account's currency.** All the transactions of an account use its currency, so sums add up. The conversion to USD arrives when the engine reads the exchange-rates table (needed first by the default decision on timeout).
- A resend never writes twice: idempotency answers it before the rules run, and if a decision fails after writing, the retry writes the same member, which Valkey does not duplicate.

## Velocity and out-of-order events

`services/decision_engine/rules/velocity.py`. It counts on the `out:` history the engine just read: only `P2P` entries, and only when the transaction being evaluated is itself a `P2P`. Python finds the **busiest window (10 minutes by default) that contains this transfer**. If the transfer arrived late, transfers processed earlier but that happened after it also count. Decisions already returned never change: if a late transfer completes a window, the late one is held.

```python
# services/decision_engine/rules/velocity.py
def count(outgoing, t: int, window_minutes: int) -> int:
    times = [o.t for o in outgoing if o.type in TYPES]   # TYPES = {"P2P"}
    return max_in_window(times, t, window_minutes * 60 * 1000)
```

The window and the limit are the catalog's `window_minutes` and `limit` (held when the window has **more than** `limit`).

| Variable | Default | Meaning |
| :--- | ---: | :--- |
| `HISTORY_OUT_HOURS` | 24 | Outgoing history kept per account. An event later than this is evaluated with incomplete history. At least 24. |
| `HISTORY_IN_MINUTES` | 60 | Incoming history kept per account. At least 60, the longest mule window. |
| `HISTORY_SECURITY_MINUTES` | 60 | Security events kept per account (`sec:{account}`), for the account takeover rule (1 hour). |

## Mule account

`services/decision_engine/rules/mule.py` (RN-03, HU-13). A mule account receives money from several accounts and takes it out right away. The rule runs on a **withdrawal** (`RETIRO`), which is when the money leaves the wallet:

1. It reads the account's `in:` history and counts the **different** senders whose transfer happened in the 30 minutes before the withdrawal. Three transfers from the same account count as one.
2. It compares the withdrawal with `source_balance_before`, the balance the core reports before the withdrawal. That balance already includes what came in; the engine keeps no balances of its own ([Team decisions](../architecture/team-decisions.mdx)).
3. With 3 or more senders and 80 % or more withdrawn, it adds `mule` with `HOLD`, and the decision carries `opens_case: true`.

```python
# services/decision_engine/rules/mule.py
def senders(incoming, t: int, window_minutes: int) -> int:
    window = window_minutes * 60 * 1000
    return len({i.sender for i in incoming if t - window < i.t <= t})

def withdraws_enough(amount, balance_before, pct) -> bool:
    return amount * 100 >= pct * balance_before
```

- **Withdrawal only.** RN-03 says "withdraws", like the generator's pattern. Moving the money on with a `P2P` or paying a merchant does not trigger it; adding them is one line (`mule.TYPES`).
- **Out-of-order events.** A transfer that arrives late but happened before the withdrawal counts in its real place. One recorded with a time after the withdrawal does not. A transfer that arrives after the withdrawal was decided cannot change that decision.
- **Amounts in the account's currency.** The rule compares a share of the balance, so it needs no USD conversion.
- **The case itself** (table, inbox, 4-hour timer) is HU-25 in Sprint 4: the cases consumer will open one for each event with `opens_case: true`.

| Catalog parameter | Default | Meaning |
| :--- | ---: | :--- |
| `window_minutes` | 30 | Window from the first transfer to the withdrawal. At most 60 (`HISTORY_IN_MINUTES`). |
| `min_senders` | 3 | Different senders needed. |
| `withdrawn_pct` | 80 | Share of the balance before the withdrawal, from 0 to 100. |

`tests/test_mule.py` covers the generator's pattern (3 senders, 90 % at minute 20) and its control (2 senders), the same sender three times, the 80 % limit, a transfer outside the window, one recorded after the withdrawal, a `P2P` instead of a withdrawal, and that velocity does not open a case. Replaying a 3,000-transaction generator run through the engine, the 9 labeled mule withdrawals were held and none of the 9 control withdrawals or any other transaction was flagged as mule.

## Shared device

`services/decision_engine/rules/shared_device.py` (RN-04, HU-14). One phone or computer used by many accounts is a sign of a fraud ring or of accounts opened to move money. The rule runs on every transaction:

1. The engine adds the main account to `dev:{device}` before deciding (the attempt counts, like the rest of the history) and passes the device's accounts to the rule as `RuleContext.device_accounts`.
2. The rule counts the **different** accounts seen on the device in the last 30 days.
3. With more than 3, it adds `shared_device`. By default its action is `APPROVE` with score 30: it **raises `risk_score`, it does not hold** by itself. A more severe rule that also fires still decides (`shared_device` + `velocity` is `HOLD`).

```python
# services/decision_engine/rules/shared_device.py
def accounts(device_accounts, t: int, window_days: int) -> int:
    window = window_days * 24 * 3600 * 1000
    return len({d.account for d in device_accounts if d.t > t - window})
```

- **"Raises the risk score for all" (RN-04).** Every account that uses the device reads the same `dev:` set, so from the fourth account on, each of them gets the score on its next transaction on that device, including the first three.
- **Out-of-order events.** The score of each account is the last time it was seen, so an account that used the device after a late event still counts: it shares the device inside the window too. A late event of an account already stored moves its last time back, which only shortens how long it is kept.
- **Where the pairs live.** The engine writes them in Valkey, like the rest of the history ([Team decisions](../architecture/team-decisions.mdx)). The durable copy in DynamoDB and the device network analysis come later.

| Catalog parameter | Default | Meaning |
| :--- | ---: | :--- |
| `window_days` | 30 | Window of days counted. At most 30 (`HISTORY_DEVICE_DAYS`). |
| `max_accounts` | 3 | Fires with **more than** this many accounts. |

`tests/test_rule_shared_device.py` covers 3 accounts (no) and 4 (yes, `APPROVE` with score 30), an account seen 30 and 31 days before, an account seen after the transaction, thresholds changed in the catalog, the `dev:` history in Valkey (one member per account, pruned at 30 days) and, through the API, four accounts on one device: the fourth and any later one get `risk_score` 30.

## Security events

`services/decision_engine/security_events.py`. The wallet core sends device and password changes apart from the transactions (the generator already does). The account takeover rule reads them: a device change, a password change and a transaction above USD 200 from the same account within an hour put it on `HOLD`. See [Account takeover](#account-takeover).

```json
POST /security-events
{
  "id": "0b6f2c1e-4d3a-5b8c-9e7f-1a2b3c4d5e6f",
  "type": "DEVICE_CHANGE",
  "user_id": "5d2c9b0a-7e4f-5a1b-8c3d-6e9f0a1b2c3d",
  "account_id": "a8d456b7-ae6a-5481-9a4b-64deb0d295f7",
  "device_id": "f8692d53-a16a-595f-b796-dfde37f5f4b0",
  "event_date": "2026-10-01T08:00:00+00:00"
}

202 {"recorded": true}
```

- `type` is `DEVICE_CHANGE` or `PASSWORD_CHANGE`. `event_date` needs a time zone.
- Each event goes to the sorted set `sec:{account}`, member `id|type|device_id`, score `event_date` in ms, with the same Lua script as the account history. Events older than `HISTORY_SECURITY_MINUTES` (60) before the newest one are trimmed.
- The account is not checked against PostgreSQL: the event can arrive before or after its transactions, and the endpoint stays fast.
- A resend of the same `id` is stored once (the id is part of the member).

| Code | When |
| :--- | :--- |
| `202` | Stored, or a resend of an id already stored. |
| `400` | Invalid body: missing fields, an unknown type, an id that is not a UUID or a date without time zone. Includes the validator's `errors`. |
| `503` | Valkey is not available. |

`tests/test_security_events.py` covers storing an event, a resend, events that arrive out of order, the retention, other accounts, invalid bodies and Valkey down.

## Account takeover

`services/decision_engine/rules/account_takeover.py` (HU-17). It runs on every transaction with a source account (`P2P`, `QR`, `RETIRO`) and fires when:

- the amount in USD (`RuleContext.amount_usd`) is **more than** `min_amount_usd` (200), and
- the source account has at least one `DEVICE_CHANGE` and at least one `PASSWORD_CHANGE` in the `window_minutes` (60) before the transaction, read from `sec:{account}` through the lazy `RuleContext.security_events`.

```python
# services/decision_engine/rules/account_takeover.py
def evaluate(ctx: RuleContext, rule: RuleEntry) -> TriggeredRule | None:
    if ctx.payload.type.value not in TYPES:          # P2P, QR, RETIRO
        return None
    p: AccountTakeoverParams = rule.typed_params()
    if ctx.amount_usd <= p.min_amount_usd:           # small amounts never read Valkey
        return None
    if SIGNALS <= changes_in_window(ctx.security_events, ctx.t_ms, p.window_minutes):
        return hit(rule, f"Account takeover: device and password changed in the last "
                         f"{p.window_minutes} minutes and the transaction is "
                         f"USD {ctx.amount_usd:.2f} (limit USD {p.min_amount_usd}).")
    return None
```

- The window looks back from the transaction date: a change dated after the transaction does not count, even if it arrived first.
- Thresholds, decision and case come from the catalog entry `account_takeover`, so the rules API can change them without a redeploy.
- `HISTORY_SECURITY_MINUTES` must be at least 60, the longest window the catalog accepts; the engine refuses to start otherwise.

`tests/test_rule_account_takeover.py` covers the three signals, two of three, exactly USD 200, the window edges, a change after the transaction, COP and JPY amounts, and thresholds changed in the catalog. `tests/test_account_takeover_flow.py` runs the generator's pattern through both endpoints. With seed 42 the generator's 3 takeover withdrawals are held and its 3 controls (withdrawal 70 minutes after the device change) are approved.

| `schemas.py` | Request and response models, their validation and the field descriptions Swagger shows. |
| `docs/` | Swagger documentation, one file per group of endpoints (`transactions.py`, `security.py`, `health.py`), plus the API description (`app.py`) and the error bodies (`errors.py`). Keep its examples equal to this page. |
| `decision_service.py` | Idempotency + catalog rules + publish. |
| `catalog.py` | `current()`: the rule catalog the engine decides with (defaults until HU-20). |
| `idempotency.py` | `idem:{id}` keys in Valkey. |
| `history.py` | `out:{account}`, `in:{account}` and `dev:{device}` sorted sets: the history every rule reads. `record()` writes any history key. |
| `security_events.py` | `sec:{account}` sorted set: device and password changes for the account takeover rule. |
| `rules/` | One module per rule type (`restricted_list.py`, `velocity.py`, `mule.py`, `shared_device.py`, `account_takeover.py`), `base.py` (`RuleContext`, `TriggeredRule`, `hit`) and `REGISTRY` in `__init__.py`. |
| `currency.py` | Amounts in USD for the dollar thresholds (fixed 2026-10-01 rates until HU-42). |
| `publisher.py` | Background SNS publisher. |
