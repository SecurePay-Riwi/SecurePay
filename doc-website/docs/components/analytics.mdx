# Analytics

**Folders:** `shared/analytics.py`, `services/analytics/` · **Run:** `uv run python -m services.analytics --day 2026-10-05` (or `--from 2026-10-01 --to 2026-10-07`) · **Model:** [Analytics model](../reference/analytics-model.mdx)

Sprint 6 takes the engine's decisions, the cases and the reconciliation to a dimensional model in the lake (Parquet), answers the six business questions with one Athena view each, and measures the rules against the labeled history by running the engine again over it.

:::info Status

HU-44 to HU-46 added the rule metrics (`rule_metrics`, `pattern_coverage`) and the views `q2` and `q3`, and HU-24 the simulation of a rule version. HU-51 and HU-52 added `fact_case`, `fact_difference`, `fact_reconciliation_match` (from the `matched.jsonl` the export counts in the match output), `dim_partner`, the export and the views `q4` (per analyst) and `q5` (differences per currency plus the `MATCHED` rows). HU-47 added `dim_device` and HU-53 view `q6`. The Lambda and the state machine step of the export are pending (HU-66).

## The flow

```text
raw/ (consumer, labels, export) ──► etl.run_day ──► curated/decisiones ──► analytics/<table> ──► views q1..q6 ──► Power BI
                                                                    │
                                  build_metrics (the engine's decisions + labels) ──► rule_metrics, pattern_coverage (q2, q3)
                                                                    ▲
 PostgreSQL (Kaggle rows) ──► metrics command: replay with the current catalog ──► raw/metrics/kaggle/
```

## Running it locally

```bash
# The fixture day, without anything else running (Java 17 or later):
uv run python -m services.analytics --day 2026-10-05 \
    --raw services/analytics/tests/fixtures --output generated/analytics

# A day of the local stack: the decisions are in LocalStack's bucket,
# the labels are copied first from the generator's output.
uv run python -m services.analytics.labels --day 2026-10-05
uv run python -m services.analytics --day 2026-10-05 --raw s3://pagoseguro-datalake
```

`--raw` is the root of `raw/` (default `ANALYTICS_DATA_DIR`; it may be `s3://`, read through `services/reconciliation/storage.py`). `--output` is where `curated/`, `analytics/` and `views/` go (default `ANALYTICS_DATA_DIR`); a local Spark session writes local folders only. `views/q<N>/` is the Parquet Power BI imports in development (D6). In AWS the Glue job `securepay-<env>-analytics` runs `infra/spark/analytics_job.py --day --raw --output` (`etl.run_day()` and then the quality checks) with `s3://<datalake>` for both; see [In AWS](#in-aws-hu-66).

## The builders

Each builder is `build(spark, day, raw, output) -> {table: rows written}`, registered with one line in `etl.BUILDERS` (the decisions first: the others read `curated/decisiones`). It writes each table with `services/analytics/spark.py` (`write()`, `read()`), which applies the schema of `shared/analytics.py` and replaces the day's partition, so a day can run again. pyspark is imported inside the functions, as in the reconciliation's match.

- `curated/decisiones`: the events of `raw/decisiones/fecha=<day-1..day+1>` whose transaction is of the day, one row per `transaction_id`.
- `fact_decision` adds `label_source` from the labels; `fact_rule_hit` takes each rule's `decision` and `score` from the catalog entry `(rule, rule_version)` of `dim_rule` (for `default_timeout`, the transaction's decision). `dim_rule` has the code default catalog (version `"0"`); a published catalog version is not in it yet (the ETL does not read the rules API), so a rule of it that never fired has no `rule_metrics` row.
- `fact_label` reads every `raw/labels/fecha=*/labels.jsonl` (a labels file covers a whole generator run), once per transaction, without security events or repeated lines, and keeps the transactions of the day.
- `dim_merchant` counts the QR payments of the 30 days up to the day.
- `fact_case` reads `raw/cases/fecha=<day>/`, the current state of the cases of the export window, and writes each case to the partition of the day of its `created_at`, so a case that changed state replaces its old row. `assigned_at` is the last `ASSIGNED` event, and `escalated` says whether it has an `ESCALATED` event.
- `fact_difference` reads `raw/reconciliation/fecha=<day>/` and writes one partition per `run_day`, with `age_days` and `age_range` counted to the day built. `dim_partner` asks `partner_for()` about every type and channel, so it cannot disagree with the reconciliation.
- `dim_device` counts the 30 days of `curated/decisiones` up to the day, the main account of each transaction, and the transactions with a case in `raw/cases/fecha=<day>/`.

## Data quality (HU-66)

`quality.py` checks every table of `shared/analytics.TABLES` for nulls, formats and ranges (MAG-294). The checks come from the column names and types, so a new table or column is checked without touching the file:

| Check | Columns |
| :--- | :--- |
| Not null | The partition column (`day`, `run_day`, `as_of`), `transaction_id`, `case_id`, `difference_id`, `amount`, `amount_usd`, `rule`, `partner`, and the key (first column) of every `dim_*` table |
| Not empty | Every `*_id` column that has a value |
| Format | `currency` in COP/USD/EUR/JPY; `decision` and `final_decision` in APPROVE/HOLD/REJECT |
| Range | `amount` and `amount_usd` greater than 0; `risk_score` and `score` from 0 to 100; every ratio (`decimal(9,4)`) from 0 to 1 |

`check_table(spark, table, root, day)` runs a table's checks in one pass (the partition of `day` of a daily table, the whole table otherwise) and returns `{check: bad rows}`; `check_day()` runs every table and raises `QualityError` with every failure. CI runs them on the fixture day (`test_quality.py`); in AWS the analytics Glue job runs them after the builders, so a failure fails the job and the nightly state machine warns `ops-alarms`.

```bash
# After the ETL of the day (exit code 1 and the failures if a check fails):
uv run python -m services.analytics.quality --day 2026-10-05 --output generated/analytics
```

## In AWS (HU-66)

The nightly state machine `securepay-<env>-reconciliation` builds the day after it saves the differences, before the treasury e-mail: the Lambda `-analytics-export` (`export.handler`, read-only database user `analytics_export`) → the same Lambda with `{"job": "kaggle_metrics"}` (the Kaggle replay below, MAG-312) → the Glue job `-analytics` (AWS Glue 6.0: builders and quality checks) → `CREATE OR REPLACE VIEW` of q1..q6 in Athena. A failure in any of the three e-mails `-ops-alarms` and the reconciliation still ends; run the job again with `--day` once the cause is fixed. Terraform: `infra/terraform/modules/analytics`.

- **Catalog.** The Glue database `GLUE_DATABASE` (`securepay_<env>_analytics`) has one Parquet table per entry of `TABLES`, built from `infra/terraform/modules/analytics/tables.json`. After a change to `shared/analytics.py`, run `uv run python -m services.analytics.catalog` and commit the file (`test_glue_job.py` fails until you do). Daily tables have the partition key `fecha` with partition projection, so Athena reads `fecha=<day>/` without a crawler or `MSCK REPAIR`; the views filter by `day`, the column inside the files.
- **Views.** Terraform passes the six `sql/q*.sql` (without comments) to the state machine, which recreates them every night in the workgroup `ATHENA_WORKGROUP` (`securepay-<env>-powerbi`, results in `athena-results/powerbi/`, at most 1 GB per query). Power BI reads them there with the `powerbi` IAM user.
- **Code.** Both Spark jobs share one zip (`services/reconciliation`, `services/analytics`, `shared`), which Terraform builds and the Deploy workflow uploads again on every merge (`infra/spark/package.py`). Glue installs SQLAlchemy, python-dotenv and pydantic at the versions of `uv.lock` (`python_modules` of the module; `test_glue_job.py` checks them).

The step by step and the test with the fixture day: [Deploy to AWS, step 8](../getting-started/deploy-aws-terraform.mdx#the-analytics-after-the-reconciliation-hu-66).

## Labels (C4)

| Source | Where | How it is read |
| :--- | :--- | :--- |
| Generator | `../securepay-generator/generated/instance-<n>/labels.jsonl` (`LABELS_SOURCE`): one line per event with `id`, `kind`, `pattern`, `pattern_id`, `is_fraud`, `expected_rule`; a resent duplicate repeats the id with `"duplicate": true`, and `kind: "security"` lines are device and password changes | `labels.copy_labels()` (the command) and `generator_labels()`; `generator_events()` reads its `events.jsonl` (`GEN_OUTPUT=file`) for the replay |
| PaySim, Sparkov | securepay-seed's Kaggle ETL, table `transacciones` (`is_fraud`, `fraud_pattern`) | `labels.kaggle_transactions(session, limit=None)` |

**What step 0 confirmed in the seed:** `transacciones` has **no column that says the dataset**, nor the type, account or currency of a row. A fraud row says it in `fraud_pattern` (`kaggle_paysim_<type>` or `kaggle_fraudtest_<category>`); a legitimate row has no pattern, and its id tells: the seed builds it as `uuid5(12345678-1234-5678-1234-567812345678, "hist:<dataset>:<row of the CSV>")`, so the reader recomputes the ids of the 555,719 rows of `fraudTest.csv` (Sparkov) and the rest are PaySim. Each row becomes a QR payment of its amount (USD in the datasets, converted to the account's currency at the engine's fixed rates) from the user's account to the row's merchant, with its channel and date; the balances are unknown (before = the amount, after = 0; only the mule rule reads them, on withdrawals). The generator's `shared_device` label expects the rule with more than 1 account per device, while RN-04 asks for more than 3: the metrics use `expected_rule` as a reference only.

## Replay (C5)

`replay.replay(snapshot, transactions, reference, security_events=())` runs the engine's own decision (`decision_service._decide`, so the rules of `rules.REGISTRY`, `evaluate_rules` and `choose_decision`) on each transaction in `transaction_date` order, inside

- `history.use_backend(InMemoryHistory())`: the same sorted sets as `out:`, `in:`, `dev:` and `sec:` in a dict, with Valkey's order and trim;
- `reference_data.use_source(ReferenceData)`: accounts, merchants and the restricted list in memory (`ReferenceData.from_database(session)` reads what the cache loader loads; `from_fixtures(folder)` reads `reference.json`).

Both are context variables: outside the block, and always in the engine, the history and the reference data are Valkey. No Valkey, network or PostgreSQL inside a replay. A repeated id is decided once; a currency that is not the account's (the engine's 422) is left out; security events are recorded before the transactions at or after their time. Exchange rates: what `currency` has loaded, else the fixed 2026-10-01 rates. Nobody outside `services/analytics/` imports it: the rules API reaches it only through `simulate.py`, inside its simulation route (HU-24, `services/rules_api/simulation.py`).

## Rule metrics (HU-44 to HU-46)

How good each rule is, measured against the labels (C4) with the definitions of the [model page](../reference/analytics-model.mdx#views-contract-c3): precision and false positives per rule (`rule_metrics`, view `q2`), and fraud detected against missed per pattern (`pattern_coverage`, view `q3`). Each row is per label source and catalog version; the views show the latest catalog version of each source.

The same definitions exist twice, like the reconciliation's match:

- `metrics.py` in plain Python, over a replay: `rule_metrics(decisions, labels, snapshot=None)` (with the snapshot every rule of the catalog has a row, 0 hits included), `pattern_coverage()`, `false_positive_examples()` (HU-45: per rule, the legitimate transactions with the largest amounts) and `expected_rule_hits()`.
- `build_metrics.py` in Spark, the last builder of the ETL: the engine's own decisions of every day in the lake (`fact_decision` with `fact_label`, `fact_rule_hit`, `dim_rule`), plus the rows a Kaggle replay left in `raw/metrics/kaggle/`. Both tables are rebuilt on every run.

`test_metrics.py` runs both against the answer key of the fixture day.

```bash
# PaySim and Sparkov (securepay-seed's Kaggle ETL loaded in PostgreSQL), replayed with the
# current catalog (the rules API's latest version, or the code defaults): prints the metrics
# and writes raw/metrics/kaggle/ under --root; the next ETL run adds them to q2 and q3.
uv run python -m services.analytics.metrics --kaggle [--limit 50000] [--root generated/analytics]

# The generator's run (GEN_OUTPUT=file), replayed with the current catalog: prints only (the
# lake already has the engine's decisions of it).
uv run python -m services.analytics.metrics \
    --events ../securepay-generator/generated/instance-0/events.jsonl \
    --labels ../securepay-generator/generated/instance-0/labels.jsonl
```

Both need PostgreSQL with the seed (the reference data); `--catalog file.json` replays another `CatalogSnapshot`.

**In AWS the Kaggle replay runs by itself** (MAG-312). The apply uploads PaySim and fraudTest from `../securepay-csv/data/kaggle` to `raw/kaggle/` and runs the seed's Kaggle ETL in the admin task (`HIST_RAW_DIR=s3://<datalake>/raw/kaggle`), which loads its 70,000 rows into RDS. Every night the state machine's `MeasureKaggle` step invokes `-analytics-export` with `{"job": "kaggle_metrics"}` (`metrics.kaggle_metrics()`: the same replay as `--kaggle`, written to `s3://<datalake>/raw/metrics/kaggle/`), and the Glue job adds those rows to q2 and q3. Without Kaggle rows it writes nothing; if it fails, the step only records the error and the analytics go on. The step by step: [Deploy to AWS](../getting-started/deploy-aws-terraform.mdx#the-analytics-after-the-reconciliation-hu-66).

| :--- | ---: | ---: | ---: | ---: | ---: |
| `account_takeover` | 1 | 1 | 0 | 1.0000 | 0.0000 |
| `mule` | 1 | 1 | 0 | 1.0000 | 0.0000 |
| `restricted_list` | 1 | 1 | 0 | 1.0000 | 0.0000 |
| `shared_device` | 13 | 0 | 13 | 0.0000 | 0.0345 |
| `splitting` | 1 | 1 | 0 | 1.0000 | 0.0000 |
| `velocity` | 2 | 2 | 0 | 1.0000 | 0.0000 |

| Pattern | Frauds | Detected | Missed | Detection rate | Top rule |
| :--- | ---: | ---: | ---: | ---: | :--- |
| `ACCOUNT_TAKEOVER` | 1 | 1 | 0 | 1.0000 | `account_takeover` |
| `MULE` | 4 | 1 | 3 | 0.2500 | `mule` |

| `SPLITTING` | 4 | 1 | 3 | 0.2500 | `splitting` |
| `VELOCITY` | 13 | 2 | 11 | 0.1538 | `velocity` |

**Why patterns escape (HU-46).** The generator labels every transaction of a fraud scheme as fraud, but the rules fire on the transaction that completes it, as the business rules say:

- `VELOCITY`: a burst of transfers; RN-02 holds from the 6th in 10 minutes, so the first five go through. The two transactions where the label expects the rule (`expected_rule = velocity`) were both held.
- `MULE`: three transfers in and one withdrawal; RN-03 holds the withdrawal, the transfers in are legitimate on their own.
- `SPLITTING`: RN-05 needs the sum to exceed the limit, so the first splits pass.
- `expected_rule_hits` in the output says it per rule: every transaction that expects `account_takeover`, `mule`, `restricted_list`, `splitting` or `velocity` got it.
- View `q3` says the same per pattern: `expected` counts the frauds whose label names a rule (the transaction that completes the scheme), `expected_detected` how many of them were held or rejected, and `expected_detection_rate` their ratio. On the fixture day `detection_rate` is 7 of 19 (36.84 %), and `expected_detection_rate` is 7 of 7 (100 %): every scheme was stopped where the business rule says. The Kaggle labels name no rule, so their `expected` is 0 and the rate is null.
- `shared_device` is not a fraud pattern: the generator labels its 75 transactions `is_fraud = false` with `expected_rule = shared_device`, and marks a device as shared with more than 1 account, while RN-04 asks for more than 3. The rule fired on 13 of them. Its "false positives" are by design: it only raises `risk_score` (`APPROVE`, score 30) and holds nothing.

#### PaySim and Sparkov (AWS, November 11, 2026)

Measured in the AWS rehearsal of November 11: the apply loaded the 70,000 Kaggle rows (`load_kaggle`), the state machine's `MeasureKaggle` step replayed them with catalog version 1 and the numbers below are views `q2` and `q3` read in Athena. The generator's rows of that same run are in the views too; they are the fixture day, so they differ a little from the table above.

| Source | Rule | Hits | True positives | False positives | Precision |
| :--- | :--- | ---: | ---: | ---: | ---: |
| PaySim | `restricted_list` | 49 | 2 | 47 | 0.0408 |
| PaySim | `splitting` | 18 | 0 | 18 | 0.0000 |
| Sparkov | `restricted_list` | 40 | 0 | 40 | 0.0000 |
| Sparkov | `splitting` | 2 | 0 | 2 | 0.0000 |

`velocity`, `mule`, `account_takeover` and `shared_device` had no hits on either dataset.

| Source | Frauds | Detected | Missed | Detection rate | Fraud missed (USD) |
| :--- | ---: | ---: | ---: | ---: | ---: |
| PaySim (`CASH_OUT`, `TRANSFER`) | 1,500 | 2 | 1,498 | 0.0013 | 2,107,488,547.80 |
| Sparkov (14 categories) | 600 | 0 | 600 | 0.0000 | 311,514.38 |

**What these numbers say.** The rules are written for the wallet's own patterns (RN-02 to RN-07), and the Kaggle frauds are a different kind of fraud, so the low detection is the expected result, not a defect:

- Each Kaggle row becomes a QR payment from one user to a merchant, with no balance before or after and no security events. `velocity` counts only `P2P`, `mule` runs only on a withdrawal and reads the balance, and `account_takeover` needs device and password changes, so these rules can never fire on these rows. `shared_device` needs more than 3 accounts on a device, which the ETL does not create.
- PaySim's frauds are single very large transfers and cash-outs (one row of USD 10,000,000); no rule of the catalog looks at a single large amount. A rule like "an amount far above the account's usual one" would be the first one to add. It would go into the catalog and be tested with the simulation (HU-24) before activating it.
- The `restricted_list` hits are right by RN-06: the ETL assigns the rows to seed users, and some of them are on the list, which has nothing to do with the dataset's label. They count as false positives only against the Kaggle label.
- Both datasets are very imbalanced, as the assignment warns. That is why the views give precision and missed amounts per pattern and do not give one accuracy number, which would be close to 100 % while detecting nothing.

## Simulating a rule version (HU-24)

`simulate.py` replays one day with two catalogs, the current one (or `--against N`) and a candidate, and compares them. Nothing is written: no rules, no catalog versions, no Valkey.

```bash
uv run python -m services.analytics.simulate --day 2026-10-05 --candidate candidate.json \
    [--against N] [--kaggle] [--raw ROOT] [--security security_events.jsonl] [--reference FOLDER]

# The fixture day (its accounts are not the seed's: --reference reads its reference.json)
uv run python -m services.analytics.simulate --day 2026-10-05 --candidate candidate.json \
    --raw services/analytics/tests/fixtures --reference services/analytics/tests/fixtures \
    --security services/analytics/tests/fixtures/security_events.jsonl
```

- `candidate.json` is a `CatalogSnapshot` or a list of `RuleEntry` (`candidate_snapshot()`).
- **The day's transactions** come from `raw/decisiones` (`day_history()`: plain Python, no Spark, the first event of each id) or, with `--kaggle`, from the Kaggle rows of PostgreSQL. The replay also runs the `WARMUP_DAYS` (1) before the day, so the 24-hour history of velocity, mule and splitting starts full; only the day is compared. The 30-day window of `shared_device` starts with that day only.
- **Labels:** every `raw/labels/fecha=*/` file (or the Kaggle labels), for the metrics of each side.
- **Reference data:** the seed tables of PostgreSQL, or `--reference` (a folder with `reference.json`, like the fixtures).
- **Security events** are not in `raw/decisiones`: pass the generator's with `--security`, or `account_takeover` cannot fire.
- **Output:** `{"day", "transactions", "current": {"rules_version", "decisions", "cases", "amount_usd", "metrics"}, "candidate": {...}, "changed", "changes", "released_usd", "stopped_usd", "examples"}`. `changes` says from what to what (`"HOLD->APPROVE"`), `released_usd` is the money the candidate approves that the current catalog held or rejected, `stopped_usd` the reverse, and `examples` are up to 10 changed transactions, largest amount first.

The rules API runs the same simulation in `POST /rules/simulations`, one day at a time (D5); see [Rules API](./rules-api.mdx#simulating-a-version-hu-24).

**The demo case (D2).** Over the fixture day, splitting back to `APPROVE` (the version before sprint 6) against the current `HOLD`: 2 transactions go from `HOLD` to `APPROVE` and USD 7,324.67 keeps leaving the accounts while the cases wait for an analyst. Both keep their case: the candidate only changes the decision.
