# Cases

**Folders:** `shared/cases.py`, `services/cases_api/`, `services/alerts/`, `shared/evidence.py` · **Run:** `uv run uvicorn services.cases_api.main:app --reload --port 8003` and `uv run python -m services.alerts` · **Swagger:** http://localhost:8003/docs

Sprint 4 turns the engine's decisions into cases an analyst works from start to end: a decision of mule account, splitting or restricted list **opens a case**, the case waits in an **inbox** ordered by risk and time left, someone **takes** it, it is **escalated** to the supervisor if it is not resolved in **4 hours** (RN-09), the analyst **resolves** it as fraud or legitimate, and its **evidence** is kept 10 years (RN-12).

:::info Status
Built: the shared contract (the tables, the states, the cases API with `/health` and the alerts task), the cases consumer, which opens the cases (HU-25), the restricted list reports with their compliance e-mail (HU-34) and the 30-day account history (HU-28). Each story of Sprint 4 fills in its part.
:::

## Who writes what

A case has one shape, in `shared/cases.py`, and three parts of the system write it. None of them imports another service, and none calls another over HTTP.

| Part | Folder | Writes | Story |
| :--- | :--- | :--- | :--- |
| Cases consumer | `services/consumers/cases.py` | A case (`OPEN`) and its `CREATED` event for each `transaction.decided` event with `opens_case: true`; a `compliance_reports` row per listed document when `restricted_list` fired | HU-25, HU-34 |
| History consumer | `services/consumers/history.py` | One `account_transactions` row per account of each transaction | HU-28 |
| Cases API (port 8003) | `services/cases_api/` | `ASSIGNED` and `RESOLVED`, on the analyst's request (`X-User` is the actor); then archives the evidence | HU-26, HU-27, HU-30, HU-35, HU-28, HU-29, HU-34 |
| Alerts task (every 5 minutes) | `services/alerts/` | `ESCALATED` for overdue cases, the compliance summary e-mail, the purge of old account history | HU-31, HU-34, HU-28 |
| Evidence | `shared/evidence.py` | The case's evidence in a bucket with Object Lock, and `EVIDENCE_ARCHIVED` | HU-32 |

All three services create the tables at startup with `create_schema()`: idempotent and under a PostgreSQL advisory lock, so they can start at the same time.

## States

```text
OPEN ──(alerts task, due_at passed)──> ESCALATED ──(analyst)──> RESOLVED
  └──────────────────(analyst)──────────────────────────────────────┘
```

- Only the decisions with `opens_case` open a case (team decision of 2026-10-13): by default mule account, splitting and restricted list. A velocity `HOLD` opens none.
- One case per transaction: a repeated event never opens a second case.
- `due_at` is `created_at` + `CASE_DUE_MINUTES` (240), with the consumer's clock.
- Only the alerts task escalates. An escalated case can still be assigned and resolved.
- `RESOLVED` is final: assigning or resolving it again is `409`. Resolving stores the outcome and the final decision: `FRAUD` → `REJECT`, `LEGITIMATE` → `APPROVE`.
- Every transition writes one row in `case_events`, in the same database transaction as the change. `case_events` is append-only: a trigger rejects `UPDATE`, `DELETE` and `TRUNCATE`.

| Event | Written by | `data` |
| :--- | :--- | :--- |
| `CREATED` | Cases consumer, actor `system` | `{}` |
| `ASSIGNED` | Cases API | `{"from": null, "to": "ana"}` |
| `ESCALATED` | Alerts task, actor `system` | `{"due_at": "…"}` |
| `RESOLVED` | Cases API | `{"outcome", "final_decision", "note"}` |
| `EVIDENCE_ARCHIVED` | `evidence.archive()` | `{"bucket", "key", "retain_until"}` |

## Opening a case

The cases consumer (`services/consumers/cases.py`, queue `casos`) reads each `transaction.decided` event:

- **`opens_case: false`:** acknowledged, nothing is written.
- **`opens_case: true`:** one case `OPEN` with the decision as it came (`decision`, `decision_reason`, `rules_triggered`, `rules_version`, `rule_versions`, `risk_score`, `amount_usd`), the amount and currency of the transaction, its date, the whole transaction as evidence, `account_id` = `main_account()` and `due_at` = now + `CASE_DUE_MINUTES`; and its `CREATED` event, actor `system`. A splitting `APPROVE` opens its compliance case the same way (RN-05).
- **The same transaction again** (SNS and SQS deliver at least once): `INSERT ... ON CONFLICT (transaction_id) DO NOTHING`, and `CREATED` is written only when the case was inserted. No second case, no second `CREATED`.

One session and one database transaction per batch of up to 10 messages. A message that cannot be a case (not JSON, no amount, an id that is not a UUID, a date without time zone) is checked before writing and fails alone in `batchItemFailures`. If PostgreSQL fails, nothing is committed and every message that opens a case goes back to the queue; after 5 attempts it lands in the DLQ `casos-dlq`. An event without `amount_usd` (older than Sprint 4) still opens a case, with `amount_usd` null.

Each transaction opens its own case: when a split goes on, every later transaction that fires `splitting` opens another one. The analyst sees them together through the account (`account_id`, HU-28 and HU-29).

## Restricted list reports (RN-06)

RN-06 asks for the reject and an immediate report to compliance. The engine rejects; the rest happens here (HU-34):

1. **The report.** When `restricted_list` is in `rules_triggered`, the cases consumer, in the same database transaction as the case, looks up the owners of the source and destination accounts in `usuarios` and `listas_restrictivas` the way the engine does (only the digits of the document) and writes one `compliance_reports` row per listed document: case, transaction, account, document, list type and `matched_at` (the consumer's clock). Two listed owners give two reports. `ON CONFLICT (transaction_id, document) DO NOTHING`: a repeated event writes none again, and it writes a report the first delivery missed (for example a case opened before HU-34).
2. **The e-mail.** Every run of the alerts task (5 minutes in AWS), `compliance_summary.send_summary()` takes the reports with `notified_at` null, sends them in **one** message to the SNS topic `BUSINESS_ALERTS_TOPIC` with the message attribute `audience = "compliance"` (the compliance subscription filters by it, [Team decisions](../architecture/team-decisions.mdx)) and sets `notified_at`. Without new reports nothing is published; running it twice sends one e-mail. If SNS fails, nothing is marked and the next run sends them.
3. **The query.** `GET /compliance/restricted-list-reports` on the cases API.

A report belongs to a case. If the catalog turns off `opens_case` for `restricted_list`, the transaction is still rejected but there is no case and no report. If nobody is listed when the consumer runs (the list changed after the decision), the case opens without a report and the consumer logs a warning.

`BUSINESS_ALERTS_TOPIC` takes a topic name (LocalStack; the task gets its ARN with `create_topic`, which returns the existing topic) or the topic's ARN, used as is (AWS, so the Lambda needs only `sns:Publish`).

## Account history (HU-28)

The analyst needs the last 30 days of an account to judge a case (D3: in PostgreSQL, not DynamoDB):

1. **The rows.** The history consumer (`services/consumers/history.py`, queue `historial`) writes, for **every** `transaction.decided` event (APPROVE, HOLD or REJECT), one `account_transactions` row per account of the transaction: `OUT` for the source and `IN` for the destination, each with the other as `counterparty_account_id`. A QR payment or a withdrawal has only `OUT`; a top-up only `IN`. Each row keeps the type, channel, merchant, amount and currency, the engine's `amount_usd`, the decision, its reason, `rules_triggered`, `risk_score`, `transaction_date` and `processed_at`. `device_id` is only on the main account's row (`main_account()`: the source; in a top-up, the destination), the same rule as the engine's `dev:{device}`; HU-29 reads it.
2. **Once.** `ON CONFLICT (transaction_id, account_id) DO NOTHING`: a repeated event writes nothing again. Each event is checked before writing (a broken one fails alone in `batchItemFailures`), one database transaction per batch, and if PostgreSQL fails the whole batch goes back to the queue.
3. **30 days.** Every run of the alerts task, `account_history.purge()` deletes the rows whose `transaction_date` is older than `now - ACCOUNT_HISTORY_DAYS` (30).
4. **The query.** `GET /accounts/{account_id}/transactions` on the cases API.

The window counts from today's clock. The generator dates its transactions from `FECHA_REFERENCIA` (2026-10-01): a run whose dates are more than 30 days old is written and then purged, and the API does not list it.

The columns of the four tables are in [Data model](../reference/data-model.mdx#cases-cases-case_events-compliance_reports-account_transactions).

## Amounts

The case and the account history keep the amount in the account's currency and `amount_usd`, which the engine adds to every decision (RN-11). Amounts are `Numeric`, never float, and decimal strings in JSON (`"12450.00"`). Dates are UTC.

## Calls between parts

These signatures are fixed; each story fills in the body.

```python
# shared/evidence.py (HU-32). Today: logs and returns None.
def archive(session, case: Case) -> str | None: ...

# services/alerts/ (until its story, each returns 0)
def escalate_overdue(session, now: datetime) -> int: ...   # escalation.py, HU-31
def send_summary(session, now: datetime) -> int: ...       # compliance_summary.py, HU-34 (built)
def purge(session, now: datetime) -> int: ...              # account_history.py, HU-28 (built)

# services/alerts/handler.py
def handler(event=None, context=None) -> dict: ...
```

`handler()` runs the three jobs in that order with the same `now`, each in its own `try`: a failing job rolls back and does not stop the others. In AWS, EventBridge runs it as a Lambda every 5 minutes; locally `python -m services.alerts` runs it every `ALERTS_INTERVAL_SECONDS`. The jobs publish to the SNS topic `business-alerts` (created in LocalStack by `infra/localstack/init/01_messaging.py`).

## Cases API

Built like the [rules API](./rules-api.mdx): FastAPI, tables created at startup, `X-User` (1 to 100 characters) required on what changes a case, Swagger examples of every status code in `docs.py` checked by `tests/test_openapi.py`. Errors: `400` invalid data, `404` not found, `409` invalid transition, `503` PostgreSQL down, always `{"detail": "..."}`.

### `GET /compliance/restricted-list-reports`

The restricted list reports, newest first by `matched_at`. `from` (inclusive) and `to` (exclusive) filter the period; a date or time without a time zone is UTC. Paginated with `page` (from 1) and `size` (default 50, at most 100). A period without reports is `200` with an empty list. `400` for an invalid date or page, or `from` after `to`; `503` without PostgreSQL.

```bash
curl "http://localhost:8003/compliance/restricted-list-reports?from=2026-10-31&to=2026-11-01"
```

### `GET /accounts/{account_id}/transactions`

The account's transactions of the last `days` days (1 to 30, default 30), newest first by `transaction_date`, whatever the engine decided. Paginated with `page` (from 1) and `size` (default 50, at most 100). An account without history is `200` with an empty list. `400` for an account id that is not a UUID or `days`, `page` or `size` out of range; `503` without PostgreSQL.

```bash
curl "http://localhost:8003/accounts/5d7f9b1c-3e5a-4c7e-9b1d-3f5a7c9e1b42/transactions?days=7"
```
