# Data flow

A transaction follows two paths. The **fast path** decides and answers the core in under 200 ms, using only memory. The **slow path** does everything else afterwards: cases, history, the Data Lake, reconciliation and the dashboard. The core never waits for the slow path.

## 1. The transaction enters {/* #entry */}

1. The wallet core sends the transaction over HTTPS to the **Application Load Balancer**, with its id, type, channel, accounts or merchant, amount, currency, balances, device and date.
2. The load balancer forwards it to one of the **decision engine** tasks on ECS Fargate, in either Availability Zone.
3. The engine validates the request. A malformed transaction gets `400`, an account that does not exist gets `422`, and the same id sent with a different body gets `409`. See [Decision engine](../components/decision-engine.mdx).

## 2. The decision, in under 200 ms {/* #decision */}

The engine checks, in order:

1. **Idempotency check** in the cache. If the id was already decided, the same decision is returned and the request ends.
2. **Read the active rules** from the cache, not from PostgreSQL.
3. **Read and update the time windows** in the cache (transfers in the last 10 minutes, amounts received and withdrawn, 24-hour sums). The engine updates the counters itself, so the next transaction sees them instantly.
4. **Shared device counter**, also in the cache. DynamoDB keeps the durable copy written by the history consumer, but the engine does not read it on every transaction.
5. **Restricted list check** against the cache. The external list service is only called when the cached copy is not available, behind a circuit breaker.
6. **Decide** `APPROVE`, `HOLD` or `REJECT`, and keep with the decision the rule version and which rules fired.

**Fallback.** If something takes too long, the engine falls back to a default decision: under USD 50 it approves, from USD 50 up it holds. It exists in two layers, one inside the engine with an internal time budget and one in the core in case the whole engine does not answer. The amount is converted to USD first, with the rate of the transaction's date (the last earlier day on weekends and holidays). Every fallback decision is flagged. See [Team decisions](./team-decisions.mdx).

:::info[Built so far]
Steps 1 and 3 (velocity only) and 6 run today, plus the restricted list read straight from PostgreSQL. The rest arrives in Sprint 2. See [Decision engine](../components/decision-engine.mdx).
:::

## 3. What happens afterwards, without the core waiting {/* #after-the-decision */}

The engine publishes the decision to the `decisiones` SNS topic, which fans it out to three SQS queues, each with its dead-letter queue:

| Queue | Consumer | Writes to |
| :--- | :--- | :--- |
| `casos` | Opens a case when a rule that requires one fired. | PostgreSQL |
| `historial` | Keeps the device–account pairs, writing only new pairs. | DynamoDB and the cache |
| `analitica` | Drops the transaction in the raw layer of the Data Lake. | S3 (through Kinesis Data Firehose in AWS) |

Keeping them separate means that if analytics falls behind, cases are still created. Details in [Messaging](../components/messaging.mdx).

## 4. Where each piece of data is stored {/* #storage */}

| Store | What it keeps | Written by | Read by |
| :--- | :--- | :--- | :--- |
| **Valkey** (ElastiCache Serverless) | Idempotency keys (1 hour), time windows and 24-hour sums, devices per account, active rules, the restricted list | The engine, the history consumer, the cache refresh and the daily list load | The engine, on every transaction |
| **PostgreSQL** (RDS) | Users, accounts, devices, merchants, versioned rules, cases and their events, reconciliation differences | The seed, the rules and cases APIs, the cases consumer, the alerts task, the reconciliation | The APIs, the alerts task, the cache refresh |
| **DynamoDB** | Device–account pairs for 30 days, the daily exchange rates | The history consumer, the exchange rates task | The engine (loads every day's rate at startup, refreshes daily), cache rebuilds |
| **S3 Data Lake, `raw`** | Every decision (`raw/decisiones/`) and the partner statements (`raw/extractos/`), as they arrived | Firehose, the partners | The Spark ETL and the reconciliation |
| **S3 Data Lake, `curated` and `analytics`** | Clean Parquet, reconciliation results and the dimensional model | The Spark jobs | Athena and Power BI |
| **S3 evidence bucket** | One locked file per closed case, for 10 years | The cases API, when a case closes | The cases API, when someone looks up a closed case |

Tables, keys and paths in detail: [Data model](../reference/data-model.mdx).

## 5. What people do {/* #people */}

| Who | What they do |
| :--- | :--- |
| **Fraud analyst** | Works the case inbox through the API. A held case unresolved for 4 hours is escalated to the supervisor by email. When a case closes, its evidence goes to S3 with Object Lock (10 years, cannot be modified or deleted). |
| **Risk manager** | Creates and versions rules through the API, without deploying code. Activating a rule saves it in PostgreSQL and publishes a notice on SNS that refreshes the cache immediately, with a short TTL as backup. |
| **Compliance** | Receives restricted-list rejections and suspicious operation reports. The record is written instantly; the email arrives as a summary every 5 minutes. |
| **Treasury** | Receives the reconciliation result and the pending differences every morning. |

## 6. Orchestration and scheduled processes {/* #scheduled */}

| Process | When | Runs on |
| :--- | :--- | :--- |
| Daily reconciliation | 02:00, must finish before 07:00 | EventBridge → Step Functions (Lambda reads the four partner files, Spark reconciles, Lambda saves differences and notifies treasury) |
| Exchange rates | Daily | EventBridge → Lambda → DynamoDB |
| Alerts (escalate old cases, compliance summary) | Every 5 minutes | EventBridge → one Lambda |
| Data Lake ETL | Daily | EventBridge → EMR Serverless |
| Rule effectiveness | Weekly | EventBridge → EMR Serverless |
| Shared device network | Weekly | EventBridge → EMR Serverless |
| Rule simulation | On demand | Rules API → EMR Serverless |

**The nightly reconciliation, step by step.**

1. At 02:00 **EventBridge Scheduler** starts the **Step Functions** state machine.
2. A **Lambda** finds and reads the day's files of the four partners in `raw/extractos/`, and validates them.
3. A **Spark** job on EMR Serverless compares them with the decisions of the day, with the tolerances for rounding and time zones, and writes the differences to the `curated` layer.
4. A second **Lambda** classifies the differences, stores them in PostgreSQL and sends treasury the result.
5. Each step retries on its own. If the process has not finished at 06:30, an alarm fires, which leaves half an hour before the 07:00 deadline.

## 7. From the Data Lake to the dashboard {/* #dashboard */}

Raw data in S3 (bronze) goes through the Spark ETL to a curated layer (silver, columnar and partitioned Parquet) and from there to the dimensional model (gold, the `analytics` layer). Glue keeps the table definitions, Athena queries them with SQL without moving data, and Power BI connects to Athena with its native connector.
