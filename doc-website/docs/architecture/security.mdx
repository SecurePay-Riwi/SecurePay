# Security

Security is built in layers: the network decides what can reach each resource, the security groups decide which ports are open between components, IAM decides what each component can do in AWS, and encryption protects the data at rest and in transit. Everything on this page is what Terraform will create; locally the same pieces run on LocalStack.

## Network: VPC and subnets {/* #network */}

A dedicated VPC with six subnets spread across the two zones and organized in three tiers, so that each resource has exactly the exposure it needs and no more. Decided.

| Tier | Subnets | Range | What it holds | Internet egress |
| :--- | :--- | :--- | :--- | :--- |
| Public | `publica-a`, `publica-b` | 10.0.0.0/24, 10.0.1.0/24 | Load balancer and the two NAT Gateways | Direct, through the Internet Gateway |
| Private application | `app-a`, `app-b` | 10.0.10.0/24, 10.0.11.0/24 | Fargate tasks (engine and admin task) and the Lambdas that need the database or the cache | Outbound only, through the NAT in its own zone |
| Private data | `datos-a`, `datos-b` | 10.0.20.0/24, 10.0.21.0/24 | RDS PostgreSQL and the cache | None |

VPC: `10.0.0.0/16`. The subnets use a /24 mask (251 usable addresses each), which is more than enough for the expected number of tasks and leaves room to grow without redesigning the addressing. Calculation: at peak there are 12 engine tasks per zone, plus the network interfaces of the Lambdas inside the VPC (Lambda shares one interface per combination of subnet and security group), so a zone uses a few dozen addresses.

**Route tables.** One for the public subnets, with a default route to the Internet Gateway. One for each private application subnet, each pointing to the NAT Gateway in its own zone: this detail is what keeps the loss of one zone from cutting off egress for the other. One shared by the data subnets, with no default route: those resources never go out to the internet. The three private tables also carry the routes for the two gateway endpoints.

**Gateway VPC endpoints for S3 and DynamoDB.** They are free and keep that traffic inside the AWS network, so it does not go through the NAT Gateway, which charges $0.045 per GB processed.

**Why NAT and not interface endpoints.** The engine and the Lambdas in the private subnets need to reach SNS, ECR, CloudWatch Logs, X-Ray and Parameter Store, which live outside the VPC. With the real traffic (~150 GB a month), two NATs and five interface endpoints cost practically the same, and the NAT covers any new service with no extra work. This is [ADR-08](./decisions.mdx#adr-08); the endpoints remain the hardening step if the system ever went into real production.

### What runs inside the VPC and what runs outside

Rule: only what talks to the database or the cache runs inside the VPC, because those two resources have no public address. Everything else runs outside, where it reaches AWS services without going through the NAT.

| Inside the VPC (application subnets) | Why | Outside the VPC | Why it can be outside |
| :--- | :--- | :--- | :--- |
| Decision engine (Fargate) | Reads and writes the cache | Analytics consumer | Only writes its batches to S3 |
| Admin task (Fargate, on demand) | Schema migrations and seed against the database | | |
| Case consumer | Writes cases to the database | Exchange rate task | Calls Frankfurter on the internet and writes to DynamoDB |
| History consumer | Writes the 30-day account history to the database | Statement reading (reconciliation) | Only reads the S3 raw layer |
| Rules API | Reads and writes rules in the database | Spark jobs (AWS Glue) | Only read and write S3 and the Glue catalog |
| Cases API | Reads and writes cases in the database | | |
| Alerts Lambda | Reads and updates cases in the database | | |
| Daily list load | Writes the list to the cache | | |
| Rule refresh in the cache | Reads the active rule from the database and writes it to the cache | | |
| Difference writing (reconciliation) | Writes to the database | | |

## How traffic flows without exposing the database or the cache {/* #traffic-flow */}

**1. A transaction from the core (synchronous path).**
1. The core calls the load balancer's name over HTTPS. The load balancer lives in the two public subnets and is the only resource that accepts connections from the internet, only on port 443.
2. The load balancer terminates TLS with the ACM certificate and forwards the request over HTTP to port 8080 of an engine task in `app-a` or `app-b`. The engine's security group only accepts that port, and only from the load balancer.
3. The engine queries and updates the cache, which lives in `datos-a` and `datos-b`, on ports 6379 and 6380 with TLS. It reads the day's exchange rate from DynamoDB at startup, through the gateway endpoint, without going through the NAT.
4. The engine responds to the load balancer and the load balancer to the core. Up to this point no packet has left the VPC.
5. After responding, the engine publishes the decision to SNS. SNS is a public AWS service, so the packet goes out through the NAT in the task's zone: from `app-a` to the NAT in `publica-a` and from there to the Internet Gateway. This is ~85 % of the NAT traffic.

**2. What happens next (asynchronous path).**
1. SNS delivers the decision to the three SQS queues. That traffic is internal to AWS and does not touch the VPC.
2. The Lambda service reads the queues and starts the consumers. The case and history consumers run with a network interface in the application subnets, from where they reach the database (5432) and the cache (6379 and 6380). The history consumer writes to DynamoDB through the gateway endpoint.
3. The analytics consumer runs outside the VPC and writes each batch (up to 1,000 decisions, gathered by the queue mapping) as one file in the Data Lake raw layer.

**3. Scheduled processes.**
1. EventBridge Scheduler triggers the Lambdas, Step Functions and the Spark jobs. None of those triggers goes through the VPC.
2. The Lambdas inside the VPC (alerts, list load) go out through the NAT when they call something public: the alerts Lambda publishes to SNS and calls the engine through the load balancer to review transactions approved by fallback; the list load Lambda calls the list service through API Gateway.
3. The Spark jobs have no VPC configuration: they read and write S3 and Glue directly.

**4. People.**
1. Analysts and the manager connect over HTTPS to API Gateway with a Cognito token. API Gateway is a managed service outside the VPC.
2. API Gateway invokes the rules or cases Lambda, which runs with its interface in the application subnets and reaches the database on 5432.
3. The team reaches the private network through Session Manager, and migrations run as a Fargate task launched by the pipeline (see [Administrative access](#admin-access)).

With this configuration, neither the database nor the cache accepts connections from outside the VPC, and neither has a public address. The only entry point from the internet is port 443 on the load balancer, plus API Gateway, which is managed by AWS and does not live inside the VPC.

## Security groups {/* #security-groups */}

One group per function, and the rules are written between groups instead of between address ranges. That way, when a Fargate task is replaced and its address changes, no rule has to be touched. Security groups keep the state of each connection, so the response to an allowed connection does not need an outbound rule. Decided.

| Group | Allowed inbound | Allowed outbound |
| :--- | :--- | :--- |
| `sg-alb` | 443/TCP from the internet (0.0.0.0/0) | 8080/TCP to `sg-motor` |
| `sg-motor` | 8080/TCP from `sg-alb` | 6379 and 6380/TCP to `sg-cache`; 443/TCP to the internet (SNS, ECR, CloudWatch, X-Ray, Parameter Store, DynamoDB through its endpoint) |
| `sg-lambda` | None (Lambdas do not receive connections) | 5432/TCP to `sg-rds`; 6379 and 6380/TCP to `sg-cache`; 443/TCP to the internet |
| `sg-admin` | None | 5432/TCP to `sg-rds`; 443/TCP to the internet (ECR, CloudWatch, Parameter Store) |
| `sg-load-runner` (dev, load test only) | None (no SSH: Systems Manager) | 443/TCP to the internet (GitHub, uv, Systems Manager, S3, the load balancer) |
| `sg-rds` | 5432/TCP from `sg-lambda` and `sg-admin` | None |
| `sg-cache` | 6379 and 6380/TCP from `sg-motor` and `sg-lambda` | None |

**Changes from version 1.0:**
- **The engine no longer reaches the database.** The engine never queries PostgreSQL: it reads the active rules and the restricted list from the cache, and the day's exchange rate from DynamoDB. The components that read the database to fill the cache are Lambdas (rule refresh, list load). The 5432 rule was removed from `sg-motor`, and so was the inbound rule from `sg-motor` in `sg-rds`. Since HU-67 the engine code reads accounts, owners and the restricted list from the cache too, loaded once a day by the `list-loader` Lambda.
  - **Temporary rule in dev, removed (2026-10-31 to 2026-11-03).** While the engine still read PostgreSQL, the Terraform variable `engine_reads_database` opened 5432/TCP from `sg-engine` to `sg-rds` and let `engine-execution` read `/securepay/<env>/rds/master-url`. MAG-356 removed the variable and both rules once HU-67 was in `main`.
  - **The Lambdas no longer use the master user (MAG-361, Sprint 6).** From 2026-11-02 to MAG-361 the cases, history, alerts, difference-writer and `list-loader` Lambdas got `DATABASE_URL` of the master user as an environment variable. Now each one connects with its own user and reads its own password at startup (see [Database users](#database-users)); only the admin task and `db-bootstrap` use the master user.
- **Port 6380 on the cache.** ElastiCache Serverless uses 6379 (writes and consistent reads) and 6380 (reads from a replica), and many clients open both even if they do not use the second one. With only 6379 the connection could fail.
- **`sg-admin`**, for the Fargate task that runs the schema migrations and the seed against the database. It had no group before.

## Administrative access {/* #admin-access */}

Team members reach resources inside the VPC through **AWS Systems Manager Session Manager**. It opens a shell on a task or instance from the console or the CLI over an outbound connection that the agent starts, so no inbound port is open and no SSH key exists. Every session is recorded in CloudTrail, and it costs nothing.

| What | How |
| :--- | :--- |
| Shell access to the private network | Session Manager, with the team member's own IAM user |
| Console sign-in | Personal users with MFA; the root account is never used |
| Schema migrations and seed | A Fargate task (`admin`) launched by the pipeline, in the application subnets, with its own security group `sg-admin` |
| Infrastructure changes | Terraform, with a separate admin role that no component uses |

## Identity and access {/* #iam */}

**One role per component, with the minimum policy that component needs.** No role is shared between components and there is no permission over all resources of a service, with three exceptions that AWS does not allow to be scoped and that are marked where they appear: `ecr:GetAuthorizationToken`, the network interface actions of the Lambdas inside the VPC, and the X-Ray actions. Designed.

### How to read this section

- **Execution role and application role.** In Fargate there are two roles per task: ECS uses the execution role to pull the image, write logs and inject secrets; the code uses the task role. In Lambda there is only one.
- **Logs.** Terraform creates each log group with its retention, so no role needs `logs:CreateLogGroup`: `logs:CreateLogStream` and `logs:PutLogEvents` on its own group are enough. In the tables this is summarized as "own logs".
- **Lambdas inside the VPC.** They need to create and delete their network interface. They use the managed policy `AWSLambdaVPCAccessExecutionRole` (checked: logs plus `ec2:CreateNetworkInterface`, `DescribeNetworkInterfaces`, `DescribeSubnets`, `DeleteNetworkInterface`, `AssignPrivateIpAddresses` and `UnassignPrivateIpAddresses`). In the tables this is summarized as "VPC networking".
- **How components connect to the cache and the database.** Decided by Jorge on October 14, 2026.
  - **Cache: with IAM.** Each component connects with a token generated by its own role (`elasticache:Connect`), with no stored password. If the token leaks, it expires in 15 minutes. Checked limitations: the connection is cut after 12 hours and the client must regenerate the token on its own; it requires TLS and Valkey 7.2 or later.
  - **Database: with a password.** One PostgreSQL user per component, each with only the permissions it needs, and its password in a `SecureString` parameter that only that component's role can read (`ssm:GetParameter`). RDS IAM authentication is not used because, according to the AWS documentation, it needs between 300 MB and 1 GB of free memory on the instance, and `db.t3.micro` has 1 GB in total. If the database moves to `db.t3.small` (2 GB, about $26 more a month with Multi-AZ, still to be checked in the pricing calculator), it can switch to IAM without touching the rest of the design.

**Analysts and the manager.** They are application users, not AWS identities: they sign in to a Cognito user pool with two groups (`analista` and `gerente`) in the token. Decided on October 14 and built in dev (`modules/api`): API Gateway checks the Cognito token on every rules and cases route and sets `X-User` to the token's e-mail, so the author of a change or the analyst of a case is the person who signed in, never a header the client sends. The groups follow the actors of the brief: the risk manager (`gerente`) creates, versions and activates rules, the fraud analyst (`analista`) works the cases. The rules API answers `403` to any change of the catalog (create, edit, enable, disable, activate a version, publish) from a user who is not in `gerente`; it reads the groups from the claims API Gateway passes to the Lambda (`services/rules_api/roles.py`), never from a header. Every signed-in user can read the catalog and every cases route. Locally there is no Cognito and `X-User` is a plain header. Their actions on cases are recorded in the `caso_evento` table (see [Data model](../reference/data-model.mdx)).

## Encryption and secrets {/* #encryption */}

| What | How |
| :--- | :--- |
| Encryption at rest | Enabled on RDS, S3, DynamoDB, SQS, SNS and the cache, with AWS managed keys |
| Encryption in transit | HTTPS on the load balancer and on API Gateway with an ACM certificate; SSL/TLS required on PostgreSQL (`rds.force_ssl = 1` in the parameter group); encryption in transit enabled on the cache; the buckets reject requests without TLS |
| Secrets | In Parameter Store, type `SecureString`. They are read at runtime by the component's role (next table) |
| What is never stored | No credentials in the repository or inside the images. The pipeline fails if it detects a secret |

**Parameters that exist.**

| Parameter | Who reads it | Note |
| :--- | :--- | :--- |
| `/pagoseguro/prod/rds/master-password` and `master-url` | The admin task (seed) and `db-bootstrap` | Generated by Terraform. No other component uses the master user |
| `/pagoseguro/prod/kaggle/token` | The Kaggle download script, if it runs in AWS | Today each team member runs it locally with their own token |
| `/pagoseguro/prod/rds/<user>` (8) | Each component, only its own: `cases_consumer`, `history_consumer`, `alerts`, `reconciliation`, `list_loader`, `analytics_export`, `rules_api` and `cases_api`, plus `db-bootstrap`, which sets them all | Passwords generated by Terraform. The cache has no password: only the engine and the Lambdas' security groups reach it, over TLS (cache users with IAM are [not built](./team-decisions.mdx#designed-but-not-built)) |

AWS managed keys were chosen instead of customer managed KMS keys because they encrypt just as well and cost nothing; a customer managed key adds manual rotation and fine-grained policies, which no requirement of this project asks for, at $1 a month per key. For the same reason, Parameter Store instead of Secrets Manager: the advantage of Secrets Manager is automatic rotation, and these secrets do not rotate.

### Database users {/* #database-users */}

Built in Sprint 6 (MAG-361). Each component that reaches PostgreSQL has its own user with only the grants its queries need; nobody but the admin task and `db-bootstrap` uses the master user.

**How a component connects.** Its Lambda has `DATABASE_USER`, `DATABASE_PASSWORD_PARAMETER` (the parameter's name, never the password), `DATABASE_HOST`, `DATABASE_PORT`, `DATABASE_NAME` and `CREATE_SCHEMA=false`. At startup `shared/config.py` reads the password with `ssm:GetParameter` and builds the URL with `URL.create()`, because the generated passwords may contain `#`, `?`, `%` or `:`. Whoever can read the function's configuration sees no password. Locally and in CI, `DATABASE_URL` is used as before.

**Who creates the tables, the users and the grants.** The `db-bootstrap` Lambda (`services/db_bootstrap/`, the engine's image), with the master user. Terraform invokes it (`aws_lambda_invocation`) when the database is new, a password changed or the image changed; the queue mappings and the schedules wait for it. It:

1. creates every table: the seed's, the case tables with the append-only trigger of `case_events`, and the reconciliation tables. The seed then finds them and only inserts; its reset uses `TRUNCATE`, so the grants survive every reseed and no manual step is needed after the seed;
2. creates or updates each user, sending PostgreSQL a SCRAM-SHA-256 verifier instead of the password;
3. revokes what each user had and grants only what `services/db_bootstrap/grants.py` lists, so a grant removed from the list is removed from the database too.

The components skip `create_schema()` in AWS (`CREATE_SCHEMA=false`): it runs `ALTER TABLE` and `CREATE TRIGGER`, which only the owner may run.

| User | Component | Grants |
| :--- | :--- | :--- |
| `cases_consumer` | Cases consumer | `SELECT`, `INSERT` on `cases`, `case_events`, `compliance_reports`; `SELECT` on `cuentas`, `usuarios`, `listas_restrictivas` (restricted-list reports); `USAGE` on the `case_events` sequence |
| `history_consumer` | History consumer | `SELECT`, `INSERT` on `account_transactions` |
| `alerts` | Alerts | `SELECT`, `UPDATE` on `cases`, `compliance_reports`; `SELECT`, `INSERT` on `case_events`; `SELECT`, `DELETE` on `account_transactions` (30-day purge); `SELECT` on `reconciliation_runs`; `USAGE` on the `case_events` sequence |
| `reconciliation` | Difference writer | `SELECT`, `INSERT`, `UPDATE` on `reconciliation_runs`; `SELECT`, `INSERT` on `reconciliation_differences` |
| `list_loader` | `list-loader` | `SELECT` on `cuentas`, `usuarios`, `comercios`, `listas_restrictivas` |
| `analytics_export` | Analytics export (HU-66) and the Kaggle metrics (MAG-312) | `SELECT` on `cases`, `case_events`, `reconciliation_differences`, `reconciliation_runs`, and for the Kaggle replay on `transacciones`, `cuentas`, `usuarios`, `comercios`, `listas_restrictivas`, `rule_catalog_versions` |

`INSERT ... RETURNING` also needs `SELECT`, and `SELECT ... FOR UPDATE` needs `UPDATE`. No user may `DROP`, `TRUNCATE` or `ALTER` a table, delete cases, or change `case_events`. The cases API, the rules API and the rules cache refresh get their users in the pull request that deploys them. The tests in `services/db_bootstrap/tests/` run each component's real code with its own user against PostgreSQL, and check what each user is denied.
