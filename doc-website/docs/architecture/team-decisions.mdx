# Team decisions

Smaller decisions than the [ADRs](./decisions.mdx), taken while building. Each one says what was decided and why.

## Which held transactions open a case

**Decided by the team on 2026-10-13.**

Only three rules open a case in the analyst's inbox:

| Opens a case | Does not open a case (recorded and shown on the dashboard) |
| :--- | :--- |
| Mule account | Velocity |
| Transaction splitting | Account takeover |
| Restricted list | Approvals by fallback |

**Why.** If every held transaction opened a case, the inbox would get about 1% of the volume, some 43,000 cases a day, which no team of people can work. The assignment only says "create a case" for the mule account and splitting rules, plus the report to compliance for the restricted list. Holding is automatic; a case is what takes a person's time and what must be archived for 10 years.

## What happens with approvals by fallback

**Decided on 2026-10-13.**

When the engine is too slow, transactions under USD 50 are approved by default. Those approvals:

- **Do not open a case** when approved: during an incident they arrive all at once (10 minutes at 50 tx/s is ~30,000) and would bury the real cases.
- Are **flagged as `fallback`** and visible on the dashboard.
- Trigger **one alert per incident** to the tech team, not one per transaction.
- Are **re-run through the rules when the engine recovers**: only those that trigger mule account, splitting or restricted list open a case. The money has already moved (the risk the assignment accepts, capped under USD 50), so the review is used to freeze the destination account if the money is still in the wallet, open the case and report.

**Who runs that later review** (decided on 2026-10-14): the alerts Lambda, which already runs every 5 minutes, re-runs them through the rules once the engine answers again. The implementation belongs to the Sprint 2 story "default decision on timeout".

**If the whole engine does not answer**, the fallback happens in the core: that transaction never reaches the queue, so the core resends it to the engine with the **same id** when it is back. The engine, being idempotent, decides and publishes it normally. In the simulation the generator plays that role.

## Idempotency window of 1 hour

A resent transaction gets the same decision for 1 hour (`IDEMPOTENCY_TTL_SECONDS=3600`). That sizes the idempotency memory at ~180 thousand keys (~18 MB). If a real core resend can arrive later, the TTL must go up and the memory be recalculated.

## The engine does not write to PostgreSQL

**Decided on 2026-10-13 (story 7).** Writing every transaction to the database inside the request breaks the 200 ms budget. The engine keeps the decision in Valkey (idempotency) and publishes it; the consumers store what needs storing.

## Velocity counts only P2P transfers, by event time

**Decided on 2026-10-13 (story 8).**

- The rule says "outgoing transfers", so **QR payments to merchants do not count**. If needed, they can become their own rule with its own threshold once rule management exists.
- The window uses `transaction_date`, **not the arrival time**, so out-of-order events are counted where they really belong.
- Decisions already returned never change: if a late event completes a window, the late event is the one held.
- History per account is 24 hours. Since 2026-10-21 it is the shared account history (see below).

## Account history for the rules

**Decided on 2026-10-21 (story HU-11, Jorge).**

- One history per account that every rule reads, instead of one key per rule: `out:{account}` (what leaves: P2P, QR, withdrawal; 24 h, for velocity and later splitting) and `in:{account}` (P2P received with the sender and the amount; 60 min, for the mule rule).
- **Attempts count, whatever the decision.** The history is written before deciding, in a single call; the statement does not say, and an attempt is already the signal. Every decision still records its triggered rules.
- Amounts are kept in the account's currency; USD arrives when the engine reads the exchange rates (default-decision story).
- Memory, measured in Valkey with realistic members (~70 bytes per entry): ~3.7 M outgoing entries alive at 50 tx/s, ~260 MB plus ~100 MB of keys. It replaces the 100–200 MB of "24 h sums" already in the 300 MB estimate and the ~100 MB velocity history noted above, so the cache would be ~400–450 MB (~$8/month more). To confirm in the load test.

## Data for the seed and the generator

**Decided on 2026-10-12 and 2026-10-13.**

| Decision | Why |
| :--- | :--- |
| One account per user, in its own table | The user is the identity (email, document, KYC); the account is currency, balance and status. |
| Four currencies: COP, USD, EUR, JPY | All available in Frankfurter v2. The yen has no decimals, which covers the "different decimal precision per currency" defect. |
| Fixed reference date 2026-10-01 00:00 UTC | Two runs produce the same data regardless of the day. |
| Random dates without Faker, user agents only from Chrome, Safari or Opera | Faker gives different dates on Windows and Linux with the same seed. The team works on Windows and AWS runs Amazon Linux. |
| Device–account is many-to-many | Needed by the shared device rule. |
| Canonical document = digits only | The seed's defects write documents with dots, a `CC` prefix or spaces; the engine normalizes before looking them up. |
| The seed loads only master data | Transactions come from the generator, like the real core. |
| The core reports balances before and after | Like PaySim. The engine does not keep balances; the mule rule uses the balance in the transaction. |
| No transfers between different currencies | The assignment does not ask for it and it adds complexity. |

## Card payment history: Sparkov {/* #card-payment-history-sparkov */}

**Decided on 2026-10-14, after talking with the professor.**

The assignment names a Kaggle credit card dataset as the card payment history. After discussing it with the professor, we agreed not to use that dataset and to replace it with the one he suggested, [Sparkov](https://www.kaggle.com/datasets/kartik2112/fraud-detection) (`kartik2112/fraud-detection`), because its data is actually useful for the project.

| Decision | Why |
| :--- | :--- |
| The assignment's card dataset is **not used**. | Its columns `V1`..`V28` are anonymized and it has no card number, merchant or sequence of operations, so no rule can be measured with it. |
| **Sparkov** replaces it: ~1.85 million simulated card transactions (2019–2020, `fraudTrain.csv` and `fraudTest.csv`). | It has the card number (`cc_num`), merchant, category, amount, date and time, and the `is_fraud` label. |
| It is labeled history, like PaySim, and **never goes through the engine**. | It is history, not live traffic. |
| **Linked to the seed users** (decided on 2026-10-19, replaces "not linked"): each Sparkov card (`cc_num`) and each PaySim source account (`nameOrig`) belongs to one seed user, like a card linked to the wallet. The PostgreSQL ETL (`securepay-seed`, `src/securepay_seed/kaggle_etl/`) gives each card a user the first time it appears and sends all its transactions to that user; a user can hold several cards. | The assignment asks the team to decide how to link the card dataset to the users. A fixed card-to-user link keeps each card's history together, which is what the rules and the analyst's user history need. |
| Uses: measure candidate rules for merchant payments with Spark (for example, velocity per card, since today the velocity rule does not count QR payments), risk per merchant and category on the dashboard, and a reference fraud rate. | PaySim keeps covering transfers (mule account). |
| Raw layer `raw/kaggle/sparkov/` as downloaded; the curated layer drops the fictitious personal data (name, address, birth date) and stores the card as a hash. | Same layers as every other source. |

## Restricted list service

**Decided on 2026-10-14.**

| Decision | Why |
| :--- | :--- |
| The seed also **exports the restricted list to a file in S3**, the "provider's database". The service loads it into memory **once at startup**, with no periodic refresh. | With the same seed and settings the list is always the same. If the seed parameters change, the service is restarted; the single-command Compose starts it after the seed. |
| In AWS its Lambda runs **outside the VPC**. | It does not read PostgreSQL, so it needs no private subnet. A real provider would have its own endpoint with the list up to date. |
| Two endpoints: `GET /lista` returns the whole list; `GET /lista/{documento}` answers whether one document is listed. Both with the simulated latency (50 ms to 3 s) and outages. | One for the daily load into the cache, one as the engine's backup. |
| A **daily Lambda** (EventBridge) calls `GET /lista` and loads the list into the engine's cache, like the exchange-rate task with Frankfurter. | Closes the gap of who loads the list into the cache every day. |
| The engine checks **only the cache**. It calls `GET /lista/{documento}` only when the cache is unavailable, behind an automatic circuit breaker and with the default decision if it does not answer in time. | The cache holds the complete list: a document that is not there is not listed, so asking the service again would mean calling it on almost every transaction. |

## Gaps closed on 2026-10-14

| Gap | Decision |
| :--- | :--- |
| Circuit breaker of the list service | Automatic. |
| Consumer Lambda memory | 512 MB, as in the cost table; raised to 1024 MB only if the load test asks for it (~$32 more a month). |
| SNS filters per recipient on the business alerts topic | Treasury and compliance only get their own emails. No extra cost. |
| Device history in the cache | A sorted set by date pruned to 30 days per account, like the other windows, instead of a set that expires whole. DynamoDB keeps the durable copy. |
| Rebuilding the cache from DynamoDB | Ignores anything older than 30 days, because DynamoDB's automatic deletion takes a few days. |
| Cost figures | Corrected after the load test and the AWS Pricing Calculator, not before. |
| Case evidence | One object (file) per case in S3 with Object Lock: each file is locked the moment it is written, so there is no unprotected window. ~$3/month with only mule, splitting and restricted list opening cases. The tests check our Terraform configuration, not S3 itself: after a case closes, deleting or overwriting its evidence must fail with access denied (proving the bucket was created with the default retention), and they confirm the real cost per file (Glacier Instant Retrieval bills at least 128 KB each). |
| Compliance summary | Every 5 minutes, like the escalation, for the "immediate report" the assignment asks for. |
| Kinesis Data Firehose for the raw layer | Approved (~$1.89/month plus ~$0.07 of PUTs, against ~$64.80 without batching). Enters the cost table with the post-load-test correction. |
| Who reviews fallback approvals | The alerts Lambda (see above). |
| Analyst and risk manager login | Amazon Cognito with an API Gateway authorizer. Documented now, built when AWS is set up; locally simulated with a fixed header. |

## Infrastructure

**Decided by Jorge on 2026-10-14**, while writing the final infrastructure design. Details in [Security](./security.mdx).

| Decision | Why |
| :--- | :--- |
| The **cache authenticates with IAM**; the **database uses one user per component, with its password in Parameter Store**. | RDS IAM authentication for PostgreSQL needs 300 to 1000 MiB of extra memory, and `db.t3.micro` has 1 GB. The cache's IAM token costs nothing extra. |
| The **engine's security group has no access to RDS**. | The engine never reads PostgreSQL; the database is only read to load the cache. |
| **Case evidence is written by the cases API** when a case closes, straight to the Object Lock bucket. | No queue in between: faster, and the evidence is protected from the first instant. |
| **Power BI uses a read-only IAM user** to query Athena. | Power BI Desktop runs outside AWS and needs its own credentials; read-only keeps the blast radius small. |
| The statement reader, the restricted-list service and EMR Serverless **stay outside the VPC**. | None of them needs RDS or the cache, so they do not need the private network or the NAT. |
| **LocalStack is the local environment**, not RabbitMQ or Airflow. | The same code runs locally and on AWS. |

## Partner statements

**Decided on 2026-10-14.** Details in [Partner statements](../components/partner-statements.mdx).

| Decision | Why |
| :--- | :--- |
| The statements are **built from the transaction generator's output**, which now always writes `events.jsonl`. | They must match what the engine saw, so the reconciliation has something real to find. |
| Each of the four partners sees **a subset by type and channel** (bank top-ups, cash-in/cash-out network, ATMs, QR acquirer); `P2P` never reaches a partner. | It is how money really leaves and enters a wallet, and it uses fields the generator already sends. |
| **Rejected and held transactions are left out** when the engine's answer is known. | No money moved. |
| The day of each file is the **day in the partner's time zone**. | It is the "dates in another time zone" defect, and the reason for the ±1 day tolerance. |
| An **answer key** (`extracts_report.json`) lists the differences the reconciliation must find. | The reconciliation job will be tested against it. |
| Same path locally and in the Data Lake: `raw/extractos/<partner>/fecha=YYYY-MM-DD/`. | One partition per partner and day, as each partner delivers it. |

## Messaging details

- **Publishing never blocks the answer.** The request leaves the event in an in-memory queue; a background thread publishes batches of up to 10 every 500 ms at most.
- **A resend is not published again.**
- **The event is versioned** (`transaction.decided` v1), so an old consumer rejects a new format instead of misreading it.
- **LocalStack is pinned** to `2026.09.1` so the whole team runs the same version; since March 2026 new versions need a free account token.
- **The LocalStack init script is Python, not bash**, because a `.sh` saved on Windows (CRLF or no execute permission) fails at startup.
