# AWS infrastructure

This is the infrastructure that Terraform will create in AWS: which service does each job and why, and the full list of resources. How the code is organized and how to create and destroy an environment is in [Terraform](./terraform.mdx). Network, security groups, IAM, S3 and RDS are already in Terraform and were created in the team's AWS account on 2026-10-23, checked and destroyed; nothing stays deployed. The application pieces built so far run locally on LocalStack (see [Local setup](../getting-started/local-setup.mdx)). The network, security groups, IAM roles and encryption are in [Security](./security.mdx).

The IAM permissions and ports were checked against the official AWS documentation on October 14; the links are at the end of the page.

**Naming convention.** Every resource is named `pagoseguro-<ambiente>-<pieza>`, where the environment is `dev` or `prod`. This page uses the production environment; development uses the same names with `dev`. In ARNs, `<cuenta>` is the AWS account number and the region is always `us-east-2`.

**Tagging.** Every resource carries the tags `proyecto`, `ambiente` and `responsable`, which the assignment requires and which also make it possible to split spending by environment in the budget alerts.

## Region and availability zones {/* #region-and-zones */}

**Region: US East (Ohio), `us-east-2`.** Decided.

Three reasons. First, pricing: Ohio sits in the same price band as N. Virginia, which is the cheapest in the catalog; the rates checked so far (SNS per request, SNS per email, NAT Gateway per hour and per GB, cross-zone data transfer) match N. Virginia's exactly. Second, service availability: every service this project uses, including EMR Serverless and ElastiCache Serverless for Valkey, is available there. Third, Ohio carries less concentrated load than N. Virginia, which because of its size has historically been the region with the most large-scale incidents.

**Availability zones: two.** Decided.

The assignment requires tolerating the loss of one zone, and two is the minimum that meets it. A third zone would add another NAT Gateway (about $32.85 a month, fixed) without changing whether the requirement is met, because with two zones the loss of one already leaves the system running.

## Services: purpose and why each one was chosen {/* #services */}

The general rule: **pay for capacity where volume is high and pay per use where it is low**, and always prefer a service AWS runs for us, because the team has six weeks and the time must go to the business rules.

| Need | Service | Why this one | Discarded |
| :--- | :--- | :--- | :--- |
| Receive 129.6 million transactions a month | **Application Load Balancer** | ~$25/month and no added latency | API Gateway: ~$129/month and 10–20 ms more |
| Run the decision engine | **ECS Fargate**, 4 to 24 tasks | Constant load: ~$72 against ~$235 on Lambda, no cold starts | Lambda for the engine; EKS ($73/month just for the control plane) |
| State that changes with every transaction | **ElastiCache Serverless (Valkey)** | Memory in milliseconds, grows by itself, replicated across zones | DynamoDB per transaction: ~$105/month; fixed nodes, because the size must be guessed |
| Decouple what happens afterwards | **SNS + 3 SQS queues** with dead-letter queues | Each consumer fails and recovers alone; the queues absorb the peak | RabbitMQ (we would run it); Kafka/MSK (~$70/month minimum) |
| Low-volume components (APIs, consumers, tasks) | **Lambda** (12 functions) | Pay per use: ~$41 against ~$108 with containers always on | Everything on Fargate |
| Business data: users, rules, cases, reconciliation | **RDS PostgreSQL** `db.t3.micro`, Multi-AZ | Relational, automatic failover; it does not store transactions, so the smallest instance is enough | Aurora (~3 times the cost); self-managed PostgreSQL on EC2 |
| Durable, infrequent data | **DynamoDB** | Device-account pairs with automatic 30-day expiry, and the daily rates | |
| Data Lake and evidence | **S3** in three layers (raw, curated, analytics) and **Firehose** to batch the writes | Cheap storage; Firehose avoids millions of small files (~$2 against ~$65/month) | |
| Immutable evidence for 10 years | **S3 Object Lock** in COMPLIANCE mode, Glacier Instant Retrieval class | Nobody can delete it, not even the account administrator; ~83% cheaper than S3 Standard | Locking in the application |
| Batch jobs with Spark | **EMR Serverless** | Managed Spark, paid per minute of use | Spark on our own containers; Glue ETL (minimum charge per run) |
| Orchestration and scheduling | **Step Functions** (reconciliation) and **EventBridge Scheduler** | Free at our volume, no servers | Airflow with Celery |
| Query and show | **Glue Data Catalog + Athena + Power BI** | SQL straight on S3, no data movement, no cluster running | Redshift (~$180/month minimum) |
| Analyst and risk manager access | **API Gateway + Cognito** | Managed sign-in with groups per role | |
| Secrets and administrative access | **Systems Manager**: Parameter Store and Session Manager | Free; passwords stored as `SecureString`, and shell access to the private network with no open ports or keys | Secrets Manager (its advantage is automatic rotation, which these secrets do not need) |
| Logs, metrics, alarms and traces | **CloudWatch** and **X-Ray** | Managed, ~$14/month together | |
| Container images | **ECR** | One repository per component, image scanning on push | |
| Infrastructure | **Terraform** and **GitHub Actions** | Create and destroy everything with one command; CI blocks the merge if anything fails | Creating resources by hand in the console |

**Locally** we use **LocalStack**, which emulates the AWS services in a container. The same code runs on a laptop and on AWS.

The highest-impact choices are recorded as [architecture decisions](./decisions.mdx).

## Database backup strategy {/* #backups */}

The program requires an explicit backup strategy, not just having backups turned on. Designed.

| What | Configuration | Purpose |
| :--- | :--- | :--- |
| Automated backups | Daily, with 7-day retention | Recover from a deletion or a badly applied migration |
| Point-in-time recovery | Enabled, with the 5-minute granularity RDS provides | Go back to the moment before an incident, not to the end of the previous day |
| Manual snapshot | Before every schema migration and before the final demo | Migrations are the moment of highest risk |
| Maintenance window | Outside the reconciliation schedule | So that an AWS restart does not collide with the 07:00 deadline |
| Restore test | Once, before the demo | An untested backup is not a backup |

A 7-day retention is enough because the database holds operational state, not the historical record: transactions and evidence live in S3, with their own retention periods.

## Alarms and thresholds {/* #alarms */}

Each threshold comes from a requirement, not from intuition. Proposed: the thresholds are tuned with the load test data.

| # | Alarm | Threshold | Where the threshold comes from | Action |
| :--- | :--- | :--- | :--- | :--- |
| 1 | Engine latency | p99 > 180 ms for 5 minutes | The limit is 200 ms; the alarm fires before it is broken | Check the cache and the scaling |
| 2 | Fallback decisions | > 1% of decisions in 5 minutes | A degraded decision; above 1% it is no longer exceptional | Check the engine and its dependencies |
| 3 | Messages in a dead-letter queue | ≥ 1 | Any message there is work that was not done | Review and reprocess |
| 4 | Age of the oldest message | > 5 minutes in any queue | A consumer fell behind | Check the consumer |
| 5 | Reconciliation not finished | Not finished at 06:30 | The deadline is 07:00; half an hour to react | Manual intervention |
| 6 | Load balancer errors | 5xx > 1% in 5 minutes | The engine is failing, not just slow | Check the tasks |
| 7 | Healthy engine tasks | < 2 in any zone | Below that, losing a zone is no longer tolerable | Check the scaling |
| 8 | Database | CPU > 80% for 15 minutes, or connections > 80% of the maximum | `db.t3.micro` running out | Check queries and connections |
| 9 | Cache refreshed by expiry | ≥ 1 time | A rule change event was lost | Check the subscription |
| 10 | Budget | 80% and 100% of the $200 credit | Spending control on the team's credit | Review and, if needed, destroy the development environment |
| 11 | Unpublished events | ≥ 1 log line with `EVENTO_NO_PUBLICADO` in the engine | The engine keeps answering even if SNS fails three times or its in-memory queue fills up; those events never reached the queues | Republish from the log, which keeps the full event |

Alarm 10 is an AWS Budgets alert; the other ten are CloudWatch alarms. The easiest one to show live is number 3: a message the consumer cannot process is sent on purpose, it lands in the dead-letter queue and the alarm sends the email.

## Estimated figures and how they were calculated {/* #estimates */}

Some figures in the inventory cannot be known before building and measuring. Each one comes with its calculation, the expected value, and what happens if the measurement says otherwise. None is presented as verified.

**Engine tasks: minimum 4, maximum 24.**
- Calculation: with two zones, losing one takes half the tasks. For the 2 surviving tasks to handle the sustained 50 tx/s, each task must serve 50 ÷ 2 = 25 requests per second. For the peak: 300 ÷ 25 = 12 live tasks, and 12 × 2 = 24 so that 12 survive if a zone goes down (see [ADR-07](./decisions.mdx#adr-07)).
- Expected: 25 requests per second per 0.5 vCPU task. **Still to be measured** in the load test.
- If it comes out different: at 20 per task it would be 6 and 30; at 15, 8 and 40.

**Memory of the consumer Lambdas: 512 MB.**
- Calculation: 129.6 million decisions a month reach the 3 queues and are read in batches of 10, so that is 3 × 12.96 M = 38.88 M invocations. With 100 ms per batch and 0.5 GB: 38.88 M × 0.1 s × 0.5 GB = 1,944,000 GB-s. Minus the 400,000 free, at $0.0000166667, that is $25.73; plus $7.58 for invocations, **≈ $33 a month**.
- Expected: 100 ms per batch of 10 messages. **Still to be measured.**
- If it comes out different: with 1024 MB it would be 3,888,000 GB-s and ≈ $66 a month (≈ $32 more). It is raised only if the load test calls for it (decided on October 14).

**Cache memory: ~300 MB expected (range 150–400 MB), plus ~100 MB for the velocity history.**
- Calculation: idempotency ~180 thousand keys with a 1 h lifetime (~18 MB), 24 h sums for 0.5 to 1 million active accounts (100–200 MB), short windows (~15 MB) and the restricted list (~5 MB, 50 thousand documents). The 24 h velocity history per account adds ~1.7 million entries a day at 50 tx/s with ~40 % P2P transfers, about 100 MB.
- **Still to be measured** with the seed in full mode and in the load test.
- If it comes out different: every extra 100 MB is ~$6 a month. With 1 h of velocity history instead of 24 h, that block drops to ~5 MB.

**NAT traffic: ~150 GB a month.**
- Calculation: publishing the decisions to SNS is 129.6 M × ~1 KB = 129.6 GB, plus ~15 GB of logs, ~5 GB of ECR images and ~1.8 GB of X-Ray. 2 × 730 h × $0.045 + 151 GB × $0.045 = $65.70 + $6.81 = **$72.51 a month**.
- Expected: ~1 KB per published decision. Confirmed with the real event size.
- If it comes out different: the fixed NAT cost ($65.70) does not change; every extra 100 GB is $4.50.

**Spark jobs: 4 workers with 2 vCPU and 8 GB, ~10 minutes per job.**
- Calculation: (4 × 2 × 0.167 h × $0.052624) + (4 × 8 × 0.167 h × $0.0057785) ≈ $0.10 per run, times 72 runs a month ≈ $7.50.
- **Still to be measured** with the first real runs. It is the weakest figure in the estimate.
- If it comes out different: the cost is proportional to the time; at 5 minutes per job it drops to ~$4.

**Case consumer on Lambda.**
- Expected: the case is created in milliseconds (one `INSERT`), far below Lambda's 15-minute limit.
- **Still to be measured.** If it turned out to be heavy, the alternative is to move it to Fargate (~$30 a month per task).
