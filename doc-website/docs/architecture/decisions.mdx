## ADR-01 — The decision engine sits behind an ALB, not API Gateway {/* #adr-01 */}

**Status:** Accepted · **Date:** 2026-10-02

**Context.** The core needs a synchronous decision service with p99 ≤ 200 ms at 300 tx/s. At the sustained 50 tx/s that is 129.6 million requests a month, the busiest path in the system.

**Decision.** The engine sits directly behind an Application Load Balancer. API Gateway is kept for the low-volume endpoints (the rules and cases APIs). The restricted list service of the first design is not deployed: the engine reads the list from the cache ([Restricted list service](../components/restricted-list.mdx#how-the-system-uses-it)).

**Alternatives.** API Gateway for everything: about $128.60/month against $25 for the ALB, and 10 to 20 ms of extra latency on a 200 ms budget. Network Load Balancer: faster, but no HTTP-level health checks or built-in TLS termination with ACM.

**Consequences.** Two different entry points, which must be documented. In exchange, the critical path has the lowest possible latency and cost.

## ADR-02 — Fargate for the engine, Lambda for everything else {/* #adr-02 */}

**Status:** Accepted · **Date:** 2026-10-02

**Context.** One component has high, constant traffic (the engine) and six have low or sporadic traffic (queue consumers, rules and cases APIs, list service, partner ingestion, exchange rates).

**Decision.** The engine runs on Fargate with autoscaling. The rest runs on Lambda.

**Alternatives.** Everything on Lambda: about $235/month for the engine's volume against $72.08, plus the cold-start risk against the 200 ms limit. Everything on Fargate: the six small components would need 12 tasks to survive a zone loss, about $108/month against $35.55.

**Consequences.** Two compute models to maintain and package. The rule is explicit: constant, latency-sensitive load goes to Fargate; sporadic load goes to Lambda.

## ADR-03 — High-frequency state lives in ElastiCache Serverless for Valkey {/* #adr-03 */}

**Status:** Accepted, with checkpoint · **Date:** 2026-10-03

**Context.** On every transaction the engine reads and updates idempotency keys, 10 to 30-minute window counters, 24-hour rolling sums, the active rules and the restricted list cache: 129.6 million transactions a month inside 200 ms.

**Decision.** That state lives in ElastiCache Serverless for Valkey. DynamoDB is kept for low-frequency data: the exchange rates. (The device–account pairs first planned there live in the cache and in PostgreSQL `account_transactions`.)

**Alternatives.** Storing each transaction in DynamoDB: about $105/month and it grows with traffic. Fixed-size nodes (Redis OSS or Valkey): predictable cost, but the size must be guessed before having data; if it falls short, the cache evicts keys and idempotency is the first thing lost.

**Consequences.** The cost becomes variable ($9 to $25 depending on real memory). Latency of the serverless layer and real operation usage stay open until measured. **Checkpoint:** if latency is not enough, the way out is Valkey on `t3.small` nodes ×2 (~$39.71/month), a Terraform change that does not touch the engine code.

**Checkpoint result (HU-60, run 8, 2026-11-08).** The way out exists as a variable: `cache_node_type` (`null` = Serverless, the default; for example `cache.m7g.large` = one shard with one replica, PR #128). Run 8 used it at 300 tx/s with 10 tasks: the client p99 went from 180 to 140 ms and the default decisions from 307 to 147, but the load balancer's p99 still reached 205 to 215 ms in two minutes, because the pause once a minute stayed ([known issue](../getting-started/load-test.mdx#known-issue)). The cache is not the cause, so the decision stands: Serverless, which costs less at this volume and needs no size guessed in advance.

## ADR-04 — Messaging is SNS fanned out to three SQS queues {/* #adr-04 */}

**Status:** Accepted · **Date:** 2026-10-03

**Context.** The decision service must not depend synchronously on any later process. After deciding there are three independent jobs: create cases, keep history and feed analytics.

**Decision.** The engine publishes each decision to an SNS topic; three SQS queues are subscribed, one per consumer, each with its dead-letter queue. No subscription filters.

**Alternatives.** Self-managed RabbitMQ (what the assignment names): it has to be installed, patched and replicated. Amazon MSK: a floor near $70/month for replay we do not need. One SQS queue with a dispatcher consumer: simpler, but a slow consumer becomes a single point of failure. Filtering the cases queue: saves ~$10/month at the cost of a silent failure if the engine labels a message wrong.

**Consequences.** All three queues receive the full volume ($31.10/month for SQS). In exchange, each consumer fails and recovers on its own, and SQS absorbs the 300 tx/s peak without slowing the engine. Implemented locally in Sprint 1: see [Messaging](../components/messaging.mdx).

## ADR-05 — Spark jobs run on AWS Glue 6.0 (was EMR Serverless) {/* #adr-05 */}

**Status:** Accepted, amended 2026-11-02 · **Date:** 2026-10-02

**Context.** Five distributed data jobs: Data Lake ETL, daily reconciliation (hard deadline at 07:00), rule effectiveness, shared device network and rule version simulation. The team has no previous Spark experience.

**Decision.** The five jobs run on EMR Serverless.

**Alternatives.** Spark in containers on Fargate: ~30% cheaper per compute hour, but needs a custom Spark image and manual temp storage. AWS Glue ETL: a minimum charge per run that punishes short jobs. EC2 Spot: cheapest, but can be reclaimed with 2 minutes' notice, unacceptable against the 07:00 deadline.

**Consequences.** A premium per compute hour in exchange for weeks of work the team does not have. Job durations are not measured yet, so the $7.50/month is provisional.

**Amendment (2026-11-02, Sprint 5, MAG-236).** EMR Serverless is not available on AWS's free account plan, which the team's account uses: `CreateApplication` fails with `SubscriptionRequiredException`. AWS Glue is available, so the Spark jobs run on **AWS Glue 6.0** (Spark 4.1.1, Python 3.13, the same Spark as the `pyspark` 4.1.x pin). The reconciliation is the first job: `infra/spark/match_job.py` runs `match.main` unchanged, Step Functions waits for it with `glue:startJobRun.sync`, and Terraform zips the code itself, so no custom image is needed. Glue's minimum charge per run (1 minute, USD 0.308 per DPU-hour, two G.1X workers) costs about a cent a night for a job of a couple of minutes, which removes the objection above. The other four jobs follow the same pattern when they are built. Design pages that still show EMR Serverless (infrastructure, overview, costs) describe the original plan and are updated with those jobs. Step by step: [Deploy to AWS, step 8](../getting-started/deploy-aws-terraform.mdx#8-run-the-nightly-reconciliation).

## ADR-06 — Managed services instead of the self-managed stack in the assignment {/* #adr-06 */}

**Status:** Accepted · **Date:** 2026-10-03

**Context.** The assignment names RabbitMQ, Airflow with Celery, Spark on custom containers and EKS. The professor allows other services as long as the requirements are met and the choice is argued. The team is 3 to 4 people for 6 weeks.

**Decision.** They are replaced by SQS and SNS, EventBridge Scheduler with Step Functions, managed Spark (EMR Serverless at first, AWS Glue since [ADR-05](#adr-05) was amended) and ECS/Fargate. EKS stays out of the production architecture.

**Alternatives.** Building the assignment's stack as is: about $320/month without replicating the broker or Airflow's metadata database, and the team maintaining four systems. The EKS control plane is $73/month fixed plus continuous operation.

**Consequences.** The solution is tied to AWS. In exchange, high availability comes with each service and the team spends its time on the business rules instead of running infrastructure.

**Kubernetes comparison.** The course program asks to deploy the decision engine on Kubernetes and compare it with Fargate. This is done as a one-off exercise, not as part of the architecture. The plan was one EKS session in dev's VPC; in the end it was run locally on kind, with the same Deployment, Service and namespace, at no cost (how and result below). The results confirm or revise this decision.

**Kubernetes comparison: how (HU-58).** The manifests are in `infra/k8s/` (kustomize: one `base` and the overlays `kind` and `eks`); the steps, in [Run the engine on Kubernetes](../getting-started/kubernetes.mdx). The same image, command, size (0.5 vCPU, 1 GB) and variables as the ECS service. First on **kind**, a real Kubernetes cluster whose nodes are Docker containers on the team's computer: it costs nothing and proves the engine runs on Kubernetes unchanged, but it has no AWS (no load balancer, IAM or zones), so it cannot measure latency against Fargate. The `eks` overlay is ready for one session in AWS, measured with the same load test as Fargate (HU-60), but it was not applied.

| | ECS Fargate (today) | EKS (managed nodes) |
| :--- | :--- | :--- |
| Fixed cost | None | $0.10/hour per cluster ($73/month) for the control plane |
| Compute | Per task: 4 tasks of 0.5 vCPU and 1 GB, about $72/month | Per node, whether full or not: 2 `t3.medium` are about $60/month, and more nodes for the peak |
| What the team writes | Task definition, service and autoscaling in Terraform (`modules/ecs`) | Deployment, Service, PodDisruptionBudget, HPA, plus the cluster, node group, service account (IRSA) and metrics-server |
| What the team operates | Nothing below the task | Kubernetes versions (a minor version every ~4 months, upgrade of control plane and nodes), node AMIs, add-ons (CNI, CoreDNS, kube-proxy, metrics-server) |
| Scaling | Tasks in about 1 minute | Pods in seconds if a node has room; a new node takes minutes (Cluster Autoscaler or Karpenter to install) |
| Load balancer and IAM | ALB and task role, native | AWS Load Balancer Controller or the in-tree NLB; IAM through IRSA or Pod Identity |
| Portability | AWS only | Any Kubernetes (the same manifests run on kind) |

**Kubernetes comparison: how it was run.** EKS was not deployed in AWS because it is not included in the account's AWS free plan (the credits plan the team works on), the same limit that moved the Spark jobs from EMR to Glue and removed Firehose ([supported services](https://docs.aws.amazon.com/accounts/latest/reference/supported-services-sign-up-new.html)). Paying for a cluster outside the plan for one comparison was not justified, so the comparison was run locally on kind, on one team computer (Windows, Docker Desktop), with the manifests of `infra/k8s/`, the same image and variables as the ECS service, and nothing else changed:

1. `kind create cluster --name securepay --config infra/k8s/overlays/kind/kind.yaml`: a real Kubernetes cluster (API server, scheduler, kubelet, containerd) whose nodes are Docker containers. The three nodes of `kind.yaml` (one control plane, two workers) started; the measurement used one node, because three nodes next to the Compose stack ran out of the computer's memory.
2. `kind load docker-image securepay-engine:kind`: the engine image built by Compose, copied into the nodes (kind does not pull from a registry).
3. `kubectl apply -k infra/k8s/overlays/kind`: the namespace `securepay`, the ConfigMap with the engine's variables, a Deployment of two pods of 0.5 vCPU and 1 GB with `/health` as readiness and liveness, a PodDisruptionBudget and a NodePort Service published on `localhost:8080`. The pods reach the Compose stack's Valkey and LocalStack, so both engines decide with the same data.
4. `infra/k8s/latency.py` sent the same 1,000 requests (10 at a time) to the Compose engine and to the engine on kind.
5. One pod was deleted to watch the Deployment replace it while the Service kept answering from the other.

**Kubernetes comparison: result.**

| Measure | Compose (local) | kind (local) |
| :--- | :--- | :--- |
| p50 / p95 / p99 (ms) | 51.1 / 65.2 / 77.0 | 44.5 / 70.9 / 80.3 |
| Throughput of the run (tx/s) | 193 | 227 |
| Errors | 0 of 1,000 | 0 of 1,000 |
| Time for a new pod to be ready | — | 11 s (the other pod kept answering) |
| Team hours to get it running | — | About 15 min (create the cluster, load the image, deploy, measure, replace a pod) |
| Cost of the session | $0 | $0 |

**Kubernetes comparison: analysis.** The brief (topic 19) asks to deploy the decision engine on Kubernetes (pods, Deployments, Services, namespaces) and to compare **latency, operation and cost** against Fargate. The deployment is the one above: the namespace `securepay`, the Deployment with its two pods and the NodePort Service. These are the three answers.

*Latency: Kubernetes does not change how fast the engine decides.*

| Percentile | Compose | kind | Difference |
| :--- | :--- | :--- | :--- |
| p50 (half of the decisions took less) | 51.1 ms | 44.5 ms | kind 6.6 ms faster |
| p95 (95 of every 100 took less) | 65.2 ms | 70.9 ms | kind 5.7 ms slower |
| p99 (99 of every 100 took less) | 77.0 ms | 80.3 ms | kind 3.3 ms slower (4 %) |

- **The median is lower on kind** because kind ran two pods (two engine processes) and Compose one container, so the 10 requests at a time were split between two; that is also why kind answered more per second (227 against 193 tx/s). It is the effect of having two replicas, not of Kubernetes being faster.
- **The tail is a few milliseconds higher on kind.** Each request takes one more hop (the port of the kind node, then the NodePort Service to a pod), and the cluster's nodes and the Compose stack shared the same computer's memory. 3 to 6 ms is the cost of that hop.
- **Both are far under RN-01's 200 ms** (p99 77 and 80 ms) and neither failed a request (0 of 1,000 each): the time goes to the engine and Valkey, not to whatever runs the container.
- These numbers are **local** and are not compared directly with AWS: no load balancer, zones or ElastiCache, and the client ran on the same computer. Fargate's own latency is the [load test](../getting-started/load-test.mdx)'s, measured on the ALB in dev (p50 12 ms and p99 50 ms at 50 tx/s; p99 above 200 ms in some minutes at 300 tx/s, its known issue). What kind shows is that moving the engine to Kubernetes would not add latency worth noting.

*Operation: Kubernetes works, but the team would run more pieces.*

- **It runs unchanged.** The same image, command, size and variables as the ECS service; the only new files are the manifests of `infra/k8s/`. Once kind was installed it took about 15 minutes to create the cluster, load the image, deploy, measure and replace a pod.
- **It heals itself.** A deleted pod was replaced and `Ready` in 11 s while the other pod kept answering. ECS does the same with a stopped task (about 1 minute to start a new one, with the ALB sending traffic to the healthy ones), so for this service Kubernetes gives no availability that Fargate lacks. On EKS the 11 s holds only while a node has room; a new node takes minutes.
- **It needs care.** Even the local run hit three problems of the cluster itself (memory, ports that stopped forwarding; see [If something fails on Windows](../getting-started/kubernetes.mdx#if-something-fails-on-windows)). On EKS the team would also upgrade Kubernetes every few months, patch the nodes and install the load balancer controller, the autoscaler and IRSA (the table above). On Fargate there is nothing below the task.

*Cost: EKS costs more for the same engine.*

- **The engine alone:** Fargate is $72.08/month and EKS about $134/month, before any extra node for the peak. Both are computed from AWS's `us-east-2` price list (November 4, 2026, the one of [AWS services and costs](./aws-services-and-costs.mdx)) for 730 hours a month, with the same capacity: the 4 tasks Fargate keeps (2 per zone) against the 2 nodes that hold the same 4 pods.

  | | Price | Monthly |
  | :--- | :--- | :--- |
  | Fargate: 4 tasks of 0.5 vCPU and 1 GB | $0.04048 per vCPU-hour + $0.004445 per GB-hour = $0.0247 an hour per task | 4 × $0.0247 × 730 = **$72.08** |
  | EKS: control plane | $0.10 an hour per cluster | $0.10 × 730 = $73.00 |
  | EKS: 2 `t3.medium` nodes (2 vCPU, 4 GB), one per zone | $0.0416 an hour each | 2 × $0.0416 × 730 = $60.74 |
  | EKS total | | **$133.74** |

  Neither line counts the load balancer, the cache or the logs, which are the same on both. EKS costs more mostly because of the control plane, a fixed charge Fargate does not have.
- **The whole platform:** the built option (A) is $337.31/month; the assignment's stack on EKS (C, with RabbitMQ, Airflow and Spark on the cluster, on 6 `t3.large` nodes) is $664.89/month, almost double. How each is computed is in [Three options](./aws-services-and-costs.mdx#options).
- **This comparison:** $0, on kind. EKS is not on the account's AWS free plan, so trying it in AWS would have been an extra cost only for the exercise.

**Conclusion.** The decision stands: for one service with constant load and a team of 3 to 4, Fargate gives the same latency and the same Deployment-like behaviour (rolling deploys, health checks, self-healing, autoscaling, two zones) for about half the cost ($72 against $134 for the engine) and without a cluster to operate. Kubernetes would pay off with many services, several teams, or a need to leave AWS, none of which this project has; the manifests stay in `infra/k8s/` in case that changes.

## ADR-07 — The engine's autoscaling maximum goes from 12 to 24 tasks {/* #adr-07 */}

**Status:** Proposed · **Date:** 2026-10-05

**Context.** The system must sustain 300 tx/s and survive the loss of one zone. With two zones, losing one removes half the tasks: 12 become 6, and 6 tasks cover only 150 tx/s.

**Decision.** Raise the maximum to 24 so the 12 survivors cover the full peak, and set **25 requests per second per task** as the target the load test must confirm.

**Alternatives.** Stay at 12 and accept degradation during an outage. Raise the minimum instead: pays all month for an exceptional scenario. Three zones: the maximum would drop to 18 but add ~$36.50/month fixed.

**Consequences.** The maximum is only paid while scaled out: 24 tasks cost $0.59/hour against $0.10 for the base 4. If the load test disproves the target of 25, the numbers change (20 → 6 base and 30 max; 15 → 8 and 40).

**Load test (HU-60, 2026-11-08).** Not confirmed either way: 10 tasks (30 tx/s each) leave the CPU under 41 % but miss the 200 ms p99 at 300 tx/s in some minutes, because of a pause once a minute; 20 tasks (15 each) meet it. The status stays Proposed until that [known issue](../getting-started/load-test.mdx#known-issue) is fixed.

## ADR-08 — Private subnets go out through NAT Gateway, not VPC endpoints {/* #adr-08 */}

**Status:** Accepted, validated with the professor · **Date:** 2026-10-05

**Context.** The engine and the Lambdas that use RDS or the cache live in private subnets and must call AWS services outside the VPC. The NAT was costed with 20 GB of traffic when the real figure is ~150 GB.

**Decision.** Keep NAT Gateway ×2, one per zone, with the cost corrected to $72.51.

**Alternatives.** Interface VPC endpoints: same cost at our volume and more secure, but one endpoint per service, four design changes, and more expensive as services grow. NAT instance, proxy, a single NAT and IPv6: discarded.

**Consequences.** Private subnets keep internet egress, mitigated with security groups and least privilege. Any new service works with no extra work, and X-Ray and Session Manager stay available. Endpoints are documented as the next hardening step.
