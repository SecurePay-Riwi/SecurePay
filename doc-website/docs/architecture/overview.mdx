# Architecture overview

Event-driven microservices, serverless first, in Ohio (`us-east-2`) across two Availability Zones.

![PagoSeguro architecture flow on AWS](/img/architecture-flow.jpg)

*The diagram labels are in Spanish; the legend at the bottom explains the colors of each flow.* <a href={require('@site/static/img/architecture-flow.jpg').default} target="_blank">Open full size</a>.

## In one paragraph

The wallet core sends each transaction over HTTPS to an **Application Load Balancer**, which spreads it across the **decision engine tasks on ECS Fargate** (FastAPI, 4 to 24 tasks). The engine reads and updates its state in **ElastiCache Serverless for Valkey** and answers in under 200 ms. It then publishes the decision to **SNS**, which copies it to **three SQS queues** (cases, history, analytics), each with its dead-letter queue and its **Lambda** consumer: cases writes to **RDS PostgreSQL** (Multi-AZ), history to **DynamoDB** and the cache, and analytics to the raw layer in **S3**. Batch jobs run on **EMR Serverless (PySpark)**, woken up by **EventBridge Scheduler**; the daily reconciliation is orchestrated by **Step Functions + Lambda**. The Data Lake has three layers (`raw`, `curated`, `analytics`), cataloged in **Glue Data Catalog**, queried with **Athena** and shown in **Power BI**. Analysts and the risk manager use **API Gateway + Lambda**; the evidence of closed cases goes to a separate S3 bucket with **Object Lock** and **Glacier Instant Retrieval**.

## The path of a transaction, in under 200 ms

1. **Idempotency check** in the cache. If the id was already decided, the same decision is returned and the request ends.
2. **Read the active rules** from the cache, not from PostgreSQL.
3. **Read and update the time windows** in the cache (transfers in the last 10 minutes, amounts received and withdrawn, 24-hour sums). The engine updates the counters itself, so the next transaction sees them instantly.
4. **Shared device counter**, also in the cache. DynamoDB keeps the durable copy written by the history consumer, but the engine does not read it on every transaction.
5. **Restricted list check** against the cache. The external list service is only called when the cached copy is not available, behind a circuit breaker.
6. **Decide** `APPROVE`, `HOLD` or `REJECT`, and keep with the decision the rule version and which rules fired.

**Fallback.** If something takes too long, the engine falls back to a default decision: under USD 50 it approves, from USD 50 up it holds. It exists in two layers, one inside the engine with an internal time budget and one in the core in case the whole engine does not answer. The amount is converted to USD with the day's rate first. Every fallback decision is flagged. See [Team decisions](./team-decisions.mdx).

:::info[Built so far]
Steps 1 and 3 (velocity only) and 6 run today, plus the restricted list read straight from PostgreSQL. The rest arrives in Sprint 2. See [Decision engine](../components/decision-engine.mdx).
:::

## What happens afterwards, without the core waiting

The engine publishes the decision to the `decisiones` SNS topic, which fans it out to three SQS queues, each with its dead-letter queue:

| Queue | Consumer | Writes to |
| :--- | :--- | :--- |
| `casos` | Opens a case when a rule that requires one fired. | PostgreSQL |
| `historial` | Keeps the device–account pairs, writing only new pairs. | DynamoDB and the cache |
| `analitica` | Drops the transaction in the raw layer of the Data Lake. | S3 (through Kinesis Data Firehose in AWS) |

Keeping them separate means that if analytics falls behind, cases are still created. Details in [Messaging](../components/messaging.mdx).

## The people

| Who | What they do |
| :--- | :--- |
| **Fraud analyst** | Works the case inbox through the API. A held case unresolved for 4 hours is escalated to the supervisor by email. When a case closes, its evidence goes to S3 with Object Lock (10 years, cannot be modified or deleted). |
| **Risk manager** | Creates and versions rules through the API, without deploying code. Activating a rule saves it in PostgreSQL and publishes a notice on SNS that refreshes the cache immediately, with a short TTL as backup. |
| **Compliance** | Receives restricted-list rejections and suspicious operation reports. The record is written instantly; the email arrives as a summary every 5 minutes. |
| **Treasury** | Receives the reconciliation result and the pending differences every morning. |

## Scheduled processes

| Process | When | Runs on |
| :--- | :--- | :--- |
| Daily reconciliation | 02:00, must finish before 07:00 | EventBridge → Step Functions (Lambda reads the four partner files, Spark reconciles, Lambda saves differences and notifies treasury) |
| Exchange rates | Daily | EventBridge → Lambda → DynamoDB |
| Alerts (escalate old cases, compliance summary) | Every 5 minutes | EventBridge → one Lambda |
| Data Lake ETL | Daily | EventBridge → EMR Serverless |
| Rule effectiveness | Weekly | EventBridge → EMR Serverless |
| Shared device network | Weekly | EventBridge → EMR Serverless |
| Rule simulation | On demand | Rules API → EMR Serverless |

## The dashboard

Raw data in S3 (bronze) goes through the Spark ETL to a curated layer (silver, columnar and partitioned Parquet) and from there to the dimensional model (gold, the `analytics` layer). Glue keeps the table definitions, Athena queries them with SQL without moving data, and Power BI connects to Athena with its native connector.
