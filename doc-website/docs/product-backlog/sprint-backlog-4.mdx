# Sprint backlog 4
## Case Management + Compliance + ECS/Fargate

**Sprint Goal:** Turn the engine's decisions into cases an analyst works from start to finish: a mule account, splitting or restricted list decision opens a case by itself, the case shows up in an inbox, someone takes it, it is escalated after 4 hours without a resolution, it is resolved as fraud or legitimate, and its evidence is kept for 10 years without anyone being able to change it. Also send the compliance reports (restricted list and suspicious transactions) and run the engine in AWS on ECS/Fargate.

## How the work is split

A case has one shape (a table, its states and an event history) and three parts of the system write it: the **consumers** create the case when the decision arrives, the **cases API** (new, port 8003) shows, assigns and resolves it, and the **alerts task** (every 5 minutes) escalates it when it is overdue. Habith first puts that shared shape in `main` ("step 0": tables, states, an empty API and the functions the three call, without logic yet). From there each person works on their own files in parallel:

- **Habith:** step 0 → HU-25 (which also closes HU-15 from Sprint 3) → HU-34 → HU-28 → HU-29 → integration.
- **Yulianis:** HU-26 → HU-27 → HU-30, and HU-35. The four are the cases API, with the same shape as the rules API she built in Sprint 3.
- **Jorge:** HU-57 (waits for nobody) → HU-31 → HU-32. The three that touch AWS the most: Fargate and the load balancer, the alerts Lambda and the evidence bucket with Object Lock.

The only wait is step 0. At the end the team runs the whole life of a case (create, assign, escalate, resolve and archive the evidence) and the generator against the full Docker stack.

## Decisions already made

- **Only mule account, splitting and restricted list open a case** (decided on October 13). If every `HOLD` opened one, there would be about 43,000 a day. See [Team decisions](../architecture/team-decisions.mdx).
- **Escalation is done by the alerts task every 5 minutes**, not by one timer per case.
- **The 30-day account history lives in PostgreSQL.**
- **Resolving a case stores the final decision:** `APPROVE` if legitimate, `REJECT` if fraud.
