# Sprint 1 review

**Sprint goal:** have the system's foundation running (data generated, the ingestion pipeline operational and the architecture documented) so the team can build the anti-fraud engine on a solid, reproducible base.

**Planned:** September 23 – October 6, 2026 · **Closed:** October 13, 2026, with every story merged to `main` (last merge: PR #8) and marked done in Jira.

**Tests:** 107. **End-to-end check (seed 42):** 1,023 transactions answered `200`, 23 resends with the same decision as their original, 3 restricted-list transactions rejected, 4 velocity frauds held (and none of their controls), 1,000 decisions in S3 with no duplicates, and the engine kept answering with LocalStack down.

## Where we differ from the backlog

| Backlog said | What we did | Why |
| :--- | :--- | :--- |
| Publish events to **RabbitMQ** | **SNS + SQS**, LocalStack locally | Managed, highly available, no broker to operate ([ADR-04](../architecture/decisions.mdx#adr-04), [ADR-06](../architecture/decisions.mdx#adr-06)). |
| Register each transaction with its decision **in the database**, inside the service | The engine writes **nothing** to PostgreSQL; the decision goes to Valkey and to the event | A database write inside the request breaks the 200 ms budget. |
| Idempotency so that **no duplicate record** is created in the database | Idempotency in **Valkey** | Same reason; the cache answers in under a millisecond. |
| The seed generates transactions | The seed loads **master data only**; the generator sends transactions over HTTP | That is how the real core behaves. |
| Branches `main`, `develop`, `feature/`, `hotfix/` | No `develop` branch yet | Feature branches merge into `main` through PRs. |
