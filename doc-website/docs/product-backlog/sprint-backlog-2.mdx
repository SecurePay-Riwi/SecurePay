# Sprint backlog 2
## Core Fraud Engine + Docker

**Sprint Goal**: Implement the anti-fraud decision engine capable of evaluating transactions in real time and issuing APPROVE, HOLD, or REJECT decisions, applying basic detection rules based on user history and blacklists, ensuring a response time of less than 200 ms and a reproducible local environment using Docker.

## Sprint result

All nine stories were merged into `main` by October 21, 2026, with 256 tests passing. The engine decides with three rules (restricted list, velocity, mule account), applies the default decision when the rules take longer than 120 ms, records every triggered rule, and the whole environment starts with one Docker Compose command. Two criteria are covered only in part and continue in later stories:

- HU-13, criterion 2 ("a case is generated"): the engine marks the decision with `opens_case`; the case itself is created by the cases consumer (HU-25, Sprint 4).
- HU-33: the restricted list is checked for every party, in PostgreSQL. Loading it into Valkey comes in a later story.

## Acceptance Criteria

### HU-10 — APPROVE / HOLD / REJECT Decision

#### Criterion 1
Given a valid transaction is received by the antifraud decision service, when the transaction is evaluated by the decision engine, the system returns one of the decisions: APPROVE, HOLD, or REJECT.

#### Criterion 2
Given a transaction has been evaluated against the configured antifraud rules, when the decision process is completed, the corresponding decision is returned to the core system.

---

### HU-11 — Evaluate Rules Using User History

#### Criterion 1
Given a transaction is received and the user's transaction history is available, when the antifraud rules that use historical information are evaluated, the system uses the user's history to identify suspicious behavior.

#### Criterion 2
Given the user's historical transactions contain information relevant to an antifraud rule, when a new transaction is evaluated, the historical information is considered in the decision.

---

### HU-12 — Detect Multiple Outgoing Transfers

#### Criterion 1
Given a user has multiple outgoing transfers within a short period, when a new outgoing transaction is evaluated, the system detects the suspicious transfer pattern.

#### Criterion 2
Given the number of outgoing transfers exceeds the configured condition for a short period, when the antifraud rule is evaluated, the transaction is identified as suspicious.

---

### HU-13 — Detect Money-Mule Pattern

#### Criterion 1
Given a user's transactions match the configured money-mule pattern, when the antifraud rules are evaluated, the system identifies the operation as suspicious.

#### Criterion 2
Given a transaction is identified as part of a money-mule pattern, when the antifraud decision is generated, the transaction is retained and a case is generated.

---

### HU-16 — Reject Transactions on Restricted Lists

#### Criterion 1
Given a transaction is associated with a document that appears on a restricted list, when the transaction is evaluated, the system rejects it.

#### Criterion 2
Given a transaction is associated with a document that is not present on a restricted list, when the transaction is evaluated, the restricted-list rule does not reject it.

---

### HU-18 — Default Decision if Engine Exceeds 200 ms

#### Criterion 1
Given a transaction is being evaluated by the decision engine, when the engine exceeds the 200 ms response limit, the system applies the predefined default decision.

#### Criterion 2
Given the decision engine completes its evaluation within the 200 ms limit, when the transaction is processed, the system returns the decision generated by the engine.

---

### HU-33 — Check Restricted Lists Before Deciding

#### Criterion 1
Given a transaction is received by the antifraud system, when the system performs the checks required before making a decision, the restricted lists are consulted before the final decision is generated.

#### Criterion 2
Given the transaction's associated document is found in a restricted list, when the restricted-list check is performed, the result is considered in the antifraud decision.

---

### HU-63 — Package Components into Docker Images

#### Criterion 1
Given the project components and their dependencies are defined, when Docker images are built for the components, each component has a reproducible Docker image.

#### Criterion 2
Given a Docker image has been created for a component, when the image is executed in the configured environment, the component runs with its required dependencies without manual installation.

---

### HU-64 — Spin Up Entire Ecosystem with a Single Command

#### Criterion 1
Given the required Docker configuration is available, when the configured single command is executed, the complete local ecosystem is started.

#### Criterion 2
Given the complete ecosystem has been started with the single command, when the services are checked, the required components are running and available in the local environment.
