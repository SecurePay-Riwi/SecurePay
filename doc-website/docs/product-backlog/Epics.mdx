| ID | User Story | Priority |
| :--- | :--- | :--- |

## EP-03 — Anti-Fraud Decision Engine

This will be one of the central epics of the product, because the main objective is to evaluate transactions through configurable rules and produce a decision. Each transaction must receive APPROVE, HOLD, or REJECT, with a 200 ms limit and specific behavior when the engine exceeds that time (corresponds directly to BR-01 through BR-07).

| ID | User Story | Priority |
| :--- | :--- | :--- |
| **US-10** | As a fraud analyst, I want to receive an APPROVE, HOLD, or REJECT decision for each transaction. | Critical |
| **US-11** | As a fraud analyst, I want the system to evaluate rules that use user history to detect suspicious behaviors. | Critical |
| **US-12** | As a fraud analyst, I want the system to allow me to detect multiple outgoing transfers in a short period to identify suspicious behaviors. | Critical |
| **US-13** | As a fraud analyst, I want the system to allow me to detect money mule patterns to hold the operation and generate a case. | Critical |
| **US-14** | As a fraud analyst, I want the system to increase the risk of accounts associated with shared devices to identify possible related networks. | High |
| **US-15** | As a fraud analyst, I want to be able to detect transaction splitting to generate cases destined for compliance. | High |
| **US-16** | As a fraud analyst, I want the system to allow rejecting transactions associated with documents present in restricted lists. | Critical |
| **US-17** | As a fraud analyst, I want the system to allow detecting device changes, password changes, and a high-value transaction in a short period to identify possible account takeovers. | High |
| **US-18** | As a risk analyst, I want to apply a default decision when the engine exceeds 200 ms to maintain the behavior defined by the business. | Critical |

## EP-05 — Anti-Fraud Case Management

Analysts need a prioritized queue, history, and related networks; furthermore, a held case must be resolved or escalated within four hours. Evidence retention for ten years is established in BR-12, and immutability is also a non-functional requirement.

| ID | User Story | Priority |
| :--- | :--- | :--- |
| **US-25** | As a fraud analyst, I want a suspicious transaction to generate a case to be able to investigate it. | Critical |
| **US-26** | As a fraud analyst, I want to consult a case queue to identify pending operations. | High |
| **US-27** | As a fraud analyst, I want to assign a case to a person in charge to establish who should investigate it. | High |
| **US-28** | As a fraud analyst, I want to consult the user's transactional history to analyze their behavior. | Critical |
| **US-29** | As a fraud analyst, I want to consult related accounts via shared devices to identify possible networks. | High |
| **US-30** | As a fraud analyst, I want to resolve a case by recording its result to preserve the investigation evidence. | Critical |
| **US-31** | As a supervisor, I want unresolved cases within four hours to escalate automatically. | Critical |
| **US-32** | As a system, I want to preserve the evidence of each case for ten years without the possibility of modification. | Critical |

## EP-12 — DevOps & CI/CD

Covers development practices, automation, and code quality. Includes Git repository setup, component packaging into reproducible Docker images, local ecosystem spin-up, and CI/CD pipelines for both application and data pipelines.

| ID | User Story | Priority |
| :--- | :--- | :--- |
| **US-62** | As a development team, I want to configure the Git repository with a component-based structure, branch conventions, and Pull Request workflow to ensure orderly and traceable work from the start. | High |
| **US-63** | As a development team, I want to package each component into a reproducible Docker image to ensure the system runs identically in any environment. | High |
| **US-64** | As a development team, I want to spin up the complete ecosystem locally with a single command so any member can reproduce the environment without manual setup. | High |
| **US-65** | As a development team, I want an application CI/CD pipeline that runs lint, tests, image building, and automatic deployment to ensure code quality on every merge. | High |
| **US-66** | As a data team, I want a data CI/CD pipeline that validates DAGs, runs job tests, and quality controls to ensure data pipelines are reliable before deployment. | High |

It covers everything related to development, automation, and code quality practices. This includes configuring
the Git repository with team collaboration conventions, packaging components into reproducible Docker images, settingup the entire ecosystem locally with a single command, and continuous integration and delivery pipelines for both the application and the data pipelines. These epic tasks ensure that the team works in an organized
manner, that the code is automatically verified before each deployment, and that the environment is
reproducible at any time.
