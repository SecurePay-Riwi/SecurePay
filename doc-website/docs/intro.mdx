# Introduction

<Callout title="Run it yourself" type="tip">
With Git and Docker Desktop, one command brings the whole platform up on AWS and one takes it down: [From zero to AWS](#8-from-zero-to-aws).
</Callout>

## 1. What is PagoSeguro?

PagoSeguro is a digital wallet with **2.3 million users**. Its customers top up their balance at banks and cash agents, send money to other people (P2P), pay merchants with QR codes and withdraw cash at agents and ATMs. It handles about **1.8 million transactions a day** in four currencies: COP, USD, EUR and JPY.

Every movement of money goes through the wallet's **core system**, which must ask for an anti-fraud decision before it moves the money.

## 2. The problem

Fraud in the wallet grew 60% in the last year, mostly through three patterns: account takeover, mule accounts that receive money from several people and withdraw it quickly, and fake merchants.

| Today | Goal |
| :--- | :--- |
| Fraud losses of 0.35% of the volume | Under 0.15% |
| 70% false positives: legitimate customers blocked | Under 40% |
| The fraud rules live inside the core; changing one takes weeks and a deployment | Risk analysts change rules without deploying code |
| Reconciliation with banks and agents is manual; differences stay unexplained for more than 10 days | 99.5% reconciled the next day, before 07:00 |
| Reports to the financial supervisor are built by hand | Suspicious operations are reported automatically, and the evidence is kept for 10 years |

<Callout title="Performance and availability target" type="important">
The decision cannot slow the business down: it must come back in **under 200 ms (p99)** at 50 transactions per second sustained and 300 at peak, and keep working if an entire AWS Availability Zone goes down.
</Callout>

## 3. Our solution: PagoSeguro Anti-fraud

PagoSeguro Anti-fraud is the platform this project builds for the wallet. It is separate from the wallet's business systems: the core only sends each transaction and receives one of three answers.

<div className="decision-grid">
  <InfoCard title="APPROVE">The transaction goes through.</InfoCard>
  <InfoCard title="HOLD">The transaction is held for review.</InfoCard>
  <InfoCard title="REJECT">The transaction is refused.</InfoCard>
</div>

The design splits the work into two paths:

<div className="path-grid">
  <InfoCard title="Fast path — the decision">
    The decision engine keeps everything it needs in an in-memory cache (recent activity per account, active rules, the restricted list) and answers without querying a database or waiting for another process. If it runs late, it falls back to a safe default by amount.
  </InfoCard>
  <InfoCard title="Slow path — everything else">
    After answering, the engine publishes the decision to a messaging topic. Independent consumers open cases for analysts, keep the device history and feed the Data Lake, and scheduled jobs reconcile the partners' statements, measure rule effectiveness and build the dashboard.
  </InfoCard>
</div>

It runs on AWS (Ohio, `us-east-2`, two Availability Zones), managed services first, and is designed as a real company system that runs 24/7. The [Architecture summary](./architecture/summary.mdx) explains each choice and its cost.

## 4. Key features

- **Real-time fraud decisions** in under 200 ms, with velocity, mule account, transaction splitting, shared device, account takeover and restricted list rules.
- **Same answer for a repeated transaction** (idempotency) and correct handling of events that arrive out of order.
- **Rules managed without deploying code:** versioned, enabled and disabled through an API, and simulated on history before activation.
- **Case management** for analysts, with escalation after 4 hours and evidence locked for 10 years.
- **Daily reconciliation** with four payment partners, each with its own file format and data defects.
- **Reproducible data:** a seed and a transaction generator with labeled fraud patterns that produce the same data on Windows and Linux, plus daily exchange rates from a public API and a simulated restricted-list provider.
- **Analytics** on a three-layer Data Lake, queried with SQL and shown in Power BI.

## 5. Tech stack

| Area | Technologies |
| :--- | :--- |

| Infrastructure and CI/CD | **Terraform** (network, IAM, S3 and RDS so far) and **GitHub Actions** (Docker images validated on every pull request; tests in CI planned) |
| Dashboard | **Power BI** |
| Documentation | **Docusaurus**, deployed to GitHub Pages |

## 6. Project structure

The project is split across five repositories in the [SecurePay-Riwi](https://github.com/SecurePay-Riwi) organization.
All source repositories install [`securepay-shared`](https://pypi.org/project/securepay-shared/) from PyPI, so you only clone `SecurePay` when you work on the engine, the consumers or this site.

```text
SecurePay-Riwi (GitHub org)
├── SecurePay              ← product: services + shared + infra + docs
├── securepay-seed         ← DB seed and Kaggle ETL
├── securepay-generator    ← simulated transaction stream
├── securepay-csv          ← PaySim, Sparkov fraudTest, partner statements
└── securepay-apis         ← exchange rates, restricted list

PyPI
└── securepay-shared 0.1.0 ← models, db, config, aws (shared by all repos)
```

## 8. From zero to AWS

Everything runs in AWS (dev, region `us-east-2`) from one command. On a Windows computer you install only:

- **Git** and **Docker Desktop** (running). Terraform, the AWS CLI and uv come inside the `deployer` container (`compose.aws.yml`, `infra/deployer/`), so you do not install them.
- **Power BI Desktop** and the [Amazon Athena ODBC driver 2.x](https://docs.aws.amazon.com/athena/latest/ug/odbc-v2-driver.html) (64-bit), only for the dashboard. They are Windows programs, so they cannot run in a container.

Run the commands in PowerShell.

**1. AWS user (once, in the console).** Sign in to the [AWS console](https://console.aws.amazon.com/) and go to **IAM → Users → Create user**. Name it `<your-name>-terraform`, attach **`PowerUserAccess`**, then add an inline policy named `securepay-terraform-iam` with the whole [`infra/terraform/terraform-user-policy.json`](https://github.com/SecurePay-Riwi/SecurePay/blob/main/infra/terraform/terraform-user-policy.json). In **Security credentials → Create access key → Command Line Interface**, create a key. Each step in detail: [Deploy to AWS, steps 2 and 3](./getting-started/deploy-aws-terraform.mdx#2-create-an-iam-user-for-terraform).

**2. Clone the four repositories side by side.**

```powershell
mkdir SecurePay-Riwi; cd SecurePay-Riwi
git clone https://github.com/SecurePay-Riwi/SecurePay.git
git clone https://github.com/SecurePay-Riwi/securepay-seed.git
git clone https://github.com/SecurePay-Riwi/securepay-apis.git
git clone https://github.com/SecurePay-Riwi/securepay-csv.git
cd SecurePay
```

**3. Give the container your AWS key.** Answer with the key of step 1, region `us-east-2` and format `json`. It is saved in `~\.aws\credentials`, never in the repository. Then check that everything is in place:

```powershell
docker compose -f compose.aws.yml run --rm deployer aws configure
docker compose -f compose.aws.yml run --rm deployer check
```

**4. The Kaggle datasets (optional).** These are PaySim and fraudTest, so that the rule metrics (views q2 and q3) also measure them. Without them, the rest works the same. With a [Kaggle API token](https://www.kaggle.com/settings) in `securepay-csv\.env` (`KAGGLE_API_TOKEN=...`; copy `.env.example` first):

```powershell
docker compose -f compose.aws.yml run --rm deployer kaggle
```

Or download [PaySim](https://www.kaggle.com/datasets/ealaxi/paysim1) and [fraudTest](https://www.kaggle.com/datasets/kartik2112/fraud-detection) from the web into `securepay-csv\data\kaggle\`. Keep the names `PS_20174392719_1491204439457_log.csv` and `fraudTest.csv`.

**5. Your settings.** Copy the example and set `owner` (your name) and `budget_emails` (your e-mail):

```powershell
copy infra\terraform\envs\dev\terraform.tfvars.example infra\terraform\envs\dev\terraform.tfvars
notepad infra\terraform\envs\dev\terraform.tfvars
```

**6. Bring it up.** Answer `yes`. About 343 resources (340 without the Kaggle CSVs); it takes a while. The apply does all of this:

- builds and pushes the images;
- creates the network, the engine, the Lambdas, the APIs with their Cognito users, the database, the cache, the data lake, Glue and Athena;
- seeds the database and loads the Kaggle sample;
- reconciles the demo day 2026-10-05;
- writes Power BI's key to the AWS profile `securepay-powerbi`.

```powershell
docker compose -f compose.aws.yml run --rm deployer apply
```

Then click **Confirm subscription** in each e-mail from AWS Notifications. AWS requires that click, and nothing can do it for you. The API users' passwords: `docker compose -f compose.aws.yml run --rm deployer output -json api_user_passwords`.

**7. Power BI.** Create the DSN once per computer:

```powershell
$bucket = (docker compose -f compose.aws.yml run --rm -T deployer output -json bucket_names | ConvertFrom-Json).datalake
Add-OdbcDsn -Name "securepay-athena" -DriverName "Amazon Athena ODBC (x64)" -DsnType "User" -Platform "64-bit" -SetPropertyValue @("AwsRegion=us-east-2", "Catalog=AwsDataCatalog", "Schema=securepay_dev_analytics", "Workgroup=securepay-dev-powerbi", "OutputLocation=s3://$bucket/athena-results/powerbi/", "AuthenticationType=Default Credentials", "AwsProfile=securepay-powerbi")
```

Open `services\analytics\powerbi\securepay.pbix`. In **Transform data → Manage parameters**, set `DataSource` to `Athena`, then **Close & Apply**. About 10 minutes after the apply, once the treasury e-mail of 2026-10-05 has arrived, **Refresh** shows the six pages from Athena. Details: [Power BI over Athena](./getting-started/deploy-aws-terraform.mdx#power-bi-over-athena).

**8. Take it down.** Run this after every session: the NAT Gateways and the database cost money even when idle. Answer `yes`.

```powershell
docker compose -f compose.aws.yml run --rm deployer destroy
```

The Terraform state stays in `infra\terraform\envs\dev\terraform.tfstate` on this computer. Apply and destroy always from the same computer, and never share that file: it holds the database passwords. To work without the container (Terraform, the AWS CLI and uv installed), the same steps are in [Deploy to AWS](./getting-started/deploy-aws-terraform.mdx).
