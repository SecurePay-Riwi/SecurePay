# Introduction

## 1. What is PagoSeguro?

PagoSeguro is a digital wallet with **2.3 million users**. Its customers top up their balance at banks and cash agents, send money to other people (P2P), pay merchants with QR codes and withdraw cash at agents and ATMs. It handles about **1.8 million transactions a day** in four currencies: COP, USD, EUR and JPY.

Every movement of money goes through the wallet's **core system**, which must ask for an anti-fraud decision before it moves the money.

## 2. The problem

Fraud in the wallet grew 60% in the last year, mostly through three patterns: account takeover, mule accounts that receive money from several people and withdraw it quickly, and fake merchants.

| Today | Goal |
| :--- | :--- |
| Fraud losses of 0.35% of the volume | Under 0.15% |
| 70% false positives: legitimate customers blocked | Under 40% |
| The fraud rules live inside the core; changing one takes weeks and a deployment | Risk analysts change rules without deploying code |
| Reconciliation with banks and agents is manual; differences stay unexplained for more than 10 days | 99.5% reconciled the next day, before 07:00 |
| Reports to the financial supervisor are built by hand | Suspicious operations are reported automatically, and the evidence is kept for 10 years |

On top of that, the decision cannot slow the business down: it must come back in **under 200 ms (p99)** at 50 transactions per second sustained and 300 at peak, and keep working if an entire AWS Availability Zone goes down.

## 3. Our solution: PagoSeguro Anti-fraud

PagoSeguro Anti-fraud is the platform this project builds for the wallet. It is separate from the wallet's business systems: the core only sends each transaction and receives one of three answers.

| Decision | Meaning |
| :--- | :--- |
| `APPROVE` | The transaction goes through. |
| `HOLD` | The transaction is held for review. |
| `REJECT` | The transaction is refused. |

The design splits the work into two paths:

- **The fast path, the decision.** The decision engine keeps everything it needs in an in-memory cache (recent activity per account, active rules, the restricted list) and answers without querying a database or waiting for another process. If it runs late, it falls back to a safe default by amount.
- **The slow path, everything else.** After answering, the engine publishes the decision to a messaging topic. Independent consumers open cases for analysts, keep the device history and feed the Data Lake, and scheduled jobs reconcile the partners' statements, measure rule effectiveness and build the dashboard.

It runs on AWS (Ohio, `us-east-2`, two Availability Zones), managed services first, and is designed as a real company system that runs 24/7. The [Architecture summary](./architecture/summary.mdx) explains each choice and its cost.

## 4. Key features

- **Real-time fraud decisions** in under 200 ms, with velocity, mule account, transaction splitting, shared device, account takeover and restricted list rules.
- **Same answer for a repeated transaction** (idempotency) and correct handling of events that arrive out of order.
- **Rules managed without deploying code:** versioned, enabled and disabled through an API, and simulated on history before activation.
- **Case management** for analysts, with escalation after 4 hours and evidence locked for 10 years.
- **Daily reconciliation** with four payment partners, each with its own file format and data defects.
- **Reproducible data:** a seed and a transaction generator with labeled fraud patterns that produce the same data on Windows and Linux, plus daily exchange rates from a public API and a simulated restricted-list provider.
- **Analytics** on a three-layer Data Lake, queried with SQL and shown in Power BI.

## 5. Tech stack

| Area | Technologies |
| :--- | :--- |
| Language and APIs | Python 3.12 with **uv**, **FastAPI**, **httpx** |
| Data | **PostgreSQL 16** (master data, rules, cases), **Valkey 8** (high-frequency state) |
| Messaging | **Amazon SNS + SQS** with dead-letter queues |
| Batch processing | **PySpark** on EMR Serverless (planned) |
| Local environment | **Docker Compose** and **LocalStack**, which emulates AWS on a laptop |
| AWS | ALB, ECS Fargate, Lambda, ElastiCache Serverless, RDS, DynamoDB, S3, Step Functions, EventBridge Scheduler, Glue, Athena |
| Infrastructure and CI/CD | **Terraform** and **GitHub Actions** (planned) |
| Dashboard | **Power BI** |
| Documentation | **Docusaurus**, deployed to GitHub Pages |

## 6. Project structure

Monorepo: one folder per piece that is deployed separately, each with its own tests. It will be split into several repositories after the first delivery.

```text
SecurePay/
├── services/
│   ├── decision_engine/        # decision engine (FastAPI)
│   └── consumers/              # SQS consumers written as Lambda handlers
├── shared/                     # models, clients and the decision event format
├── db/
│   ├── seed/                   # PostgreSQL master data seed
│   └── datasets/               # loads a Kaggle sample into PostgreSQL
├── generators/                 # transaction generator (simulated wallet core)
├── sources/
│   ├── csv_files/
│   │   ├── partner_statements/ # daily files of the four payment partners
│   │   └── kaggle/             # loads the Kaggle datasets into the Data Lake
│   └── apis/
│       ├── restricted_list/    # simulated restricted-list provider
│       └── exchange_rates/     # daily exchange rates from Frankfurter
├── infra/localstack/           # creates SNS, SQS and S3 in LocalStack
├── doc-website/                # this site
└── docker-compose.yml          # PostgreSQL, Valkey and LocalStack
```

| Piece | Folder | Status |
| :--- | :--- | :--- |
| [Seed](./components/seed.mdx) | `db/seed/` | Done: users, accounts, devices, device–account pairs, merchants and restricted lists in PostgreSQL. |
| [Transaction generator](./components/generator.mdx) | `generators/` | Done: plays the wallet core, with labeled fraud patterns and data defects. |
| [Decision engine](./components/decision-engine.mdx) | `services/decision_engine/` | Running with two rules (restricted list and velocity), idempotency and out-of-order handling in Valkey. |
| [Messaging](./components/messaging.mdx) | `services/decision_engine/publisher.py`, `infra/localstack/` | Done locally: SNS topic, three SQS queues with dead-letter queues, on LocalStack. |
| [Consumers](./components/consumers.mdx) | `services/consumers/` | Analytics writes to S3; cases and history are skeletons. |
| [Partner statements](./components/partner-statements.mdx) | `sources/csv_files/partner_statements/` | Done: daily files of the four payment partners, with their defects, locally and in LocalStack. |
| [Kaggle datasets](./components/kaggle-datasets.mdx) | `sources/csv_files/kaggle/`, `db/datasets/` | Done: PaySim and Sparkov (`fraudTest.csv`) downloaded, validated and loaded untouched into `raw/kaggle/` with a manifest; an ETL loads a sample of both into PostgreSQL. |
| [Restricted list service](./components/restricted-list.mdx) | `sources/apis/restricted_list/` | Done: simulated external provider with full-list and per-document endpoints, random latency and outages; reads the list the seed exports. |
| Exchange rates | `sources/apis/exchange_rates/` | Client done: daily rates from Frankfurter, saved locally for now; to DynamoDB when AWS is set up. |
| AWS infrastructure (Terraform) | `infra/` | Designed, not built yet. |
