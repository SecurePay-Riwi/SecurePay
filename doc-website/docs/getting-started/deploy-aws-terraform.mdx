# Deploy to AWS with Terraform

This page takes you from a machine without any AWS tools to a full test of the development environment in AWS: create it, check it, run the engine and the consumer Lambdas, prove that the evidence bucket cannot be deleted, and destroy it. [Terraform](../architecture/terraform.mdx) explains what the code creates and why; this page is only the how.

A full session lasts about 40 minutes and costs less than USD 0.30 (the two NAT Gateways and RDS Multi-AZ cost about USD 0.15 an hour together). **Always finish with `terraform destroy`:** the NAT Gateways and RDS charge by the hour even with no traffic.

The commands are for PowerShell on Windows. Run them one at a time.

## The short path

Once the tools and the IAM user exist (steps 1 to 3), a whole session is one command up and one down. Without installing the AWS CLI, Terraform or uv, the same session runs in the `deployer` container with only Git and Docker Desktop: `docker compose -f compose.aws.yml run --rm deployer apply` (and `aws configure`, `kaggle`, `output`, `destroy`); see [From zero to AWS](../intro.mdx#8-from-zero-to-aws).

1. In `infra\terraform\envs\dev`, with Docker Desktop running and `securepay-seed` and `securepay-apis` cloned and up to date beside SecurePay: `terraform init -upgrade` and `terraform apply` ([step 4](#4-create-the-environment)). It builds and pushes the images, seeds RDS, loads the cache and the exchange rates, creates two Cognito users and uploads and reconciles the demo day.
2. Click **Confirm subscription** in each SNS e-mail. AWS requires one click per subscription; nothing can do it for you.
3. Use it: the engine ([step 6](#6-deploy-the-engine-on-fargate)), the APIs with the users of `terraform output -json api_user_passwords` ([the APIs](#the-rules-and-cases-apis)), the reconciliation e-mail and the views ([step 8](#8-run-the-nightly-reconciliation)), Power BI ([its key is already in the profile `securepay-powerbi`](#power-bi-over-athena)) and the load test ([Load test](./load-test.mdx)).
4. `terraform destroy` ([step 12](#12-destroy-it)).

Steps 6 to 9 below also say how to do each part by hand (`build_images = false`, `load_data_on_apply = false`, `load_demo_day = false`, `api_users = {}`) and what each one checks.

## 1. Install the AWS CLI and Terraform

```powershell
winget install Amazon.AWSCLI
```

```powershell
winget install Hashicorp.Terraform
```

Close the terminal and open a new one, so it sees the new programs. The terminal inside VS Code may keep the old path until you close VS Code completely. Then check both:

```powershell
aws --version
```

```powershell
terraform -version
```

Terraform must be 1.9 or later.

## 2. Create an IAM user for Terraform

Terraform never uses the root account. Sign in to the [AWS console](https://console.aws.amazon.com/) with the root account only for these steps.

1. **IAM → Users → Create user.** Name it `<your-name>-terraform` (for example `jorge-terraform`). Leave "Provide user access to the AWS Management Console" unchecked: this user only runs commands.
2. **Set permissions → Attach policies directly**, and check **`PowerUserAccess`**. It allows everything except managing IAM. Create the user.
3. Open the user → **Permissions → Add permissions → Create inline policy → JSON**. Paste the whole content of [`infra/terraform/terraform-user-policy.json`](https://github.com/SecurePay-Riwi/SecurePay/blob/main/infra/terraform/terraform-user-policy.json) and name the policy **`securepay-terraform-iam`**. It only lets the user create roles and users whose name starts with `securepay-`, the GitHub OIDC provider, attach the one managed policy the Lambdas use, and hand those roles only to ECS tasks, Lambda and EventBridge Scheduler.

The user must end with exactly these two: `PowerUserAccess` and `securepay-terraform-iam`. Other policies such as `AmazonEC2FullAccess` are already covered by `PowerUserAccess` and can be removed.

## 3. Create the access key and configure the CLI

1. In the user: **Security credentials → Access keys → Create access key → Command Line Interface (CLI)**. Accept the warning and create it.
2. AWS shows the **secret access key only once**. Keep this tab open until the next step finishes. Never paste the key in a file in the repository, in a chat or in a screenshot.
3. Configure the CLI with that key:

   ```powershell
   aws configure
   ```

   It asks for four values: the Access Key ID, the Secret Access Key, the region **`us-east-2`** and the output format (`json`).

4. Check that the CLI signs in as the new user. The `Arn` must end with `user/<your-name>-terraform`:

   ```powershell
   aws sts get-caller-identity
   ```

   `InvalidClientTokenId` means the key was copied wrong: run `aws configure` again. The key is saved in `%USERPROFILE%\.aws\credentials`, outside the repository; Terraform reads it from there.

## 4. Create the environment

**One `apply` does it all** (MAG-308, since November 5, 2026). With `build_images` and `load_data_on_apply` (both `true` by default), the same `terraform apply` also does what steps 6, 7 and 9 do by hand:

1. It tags each image with the short commit of its clone.
2. It builds and pushes the engine, the seed (`securepay-seed`) and `securepay-apis` to ECR, unless that tag is already there.
3. After `db-bootstrap`, it seeds RDS with the admin task and loads the cache (`list-loader`).
4. It loads today's exchange rates (`exchange-rates`).
5. It writes the fixed rates of 2026-10-01, the day of the test transactions, so the fixed-rates alarm stays quiet.
6. It creates the Cognito users of `api_users` (by default `analista@example.com` and `gerente@example.com`, one per group) with a generated password: `terraform output -json api_user_passwords`.
7. With `load_demo_day` (default `true`), it uploads the fixture day 2026-10-05 to the Data Lake (the reconciliation's partner files and decisions, the analytics' decisions and labels) and starts the nightly state machine for that day. The apply does not wait for that run: it ends `Succeeded` 5 to 10 minutes later and e-mails treasury `Differences of the day: 19 (new: 19)` (see [step 8](#8-run-the-nightly-reconciliation)).
8. With `load_kaggle` (default `true`) and PaySim and fraudTest in `../securepay-csv/data/kaggle` (run `uv run python -m securepay_csv.kaggle_datasets` there once; `kaggle_dir` for another folder), it uploads both CSVs (about 640 MB) to `raw/kaggle/` and runs the seed's Kaggle ETL in the admin task (5 to 15 minutes), before the demo day's run. That run then measures the rules against them, and q2 and q3 show `paysim` and `fraudtest` next to the generator. Without the CSVs this step is skipped and the rest of the apply is the same.
9. With `powerbi_profile` (default `securepay-powerbi`), it creates the access key of the `securepay-dev-powerbi` user and writes it to that AWS CLI profile, the one Power BI's DSN reads ([Power BI over Athena](#power-bi-over-athena)). A Terraform user made before November 9, 2026 needs the whole [`terraform-user-policy.json`](https://github.com/SecurePay-Riwi/SecurePay/blob/main/infra/terraform/terraform-user-policy.json) pasted again in its inline policy (step 2.3): it now allows `iam:CreateAccessKey` on the `securepay-*` users.

This needs, on the computer that applies:

- Docker Desktop running;
- `uv`;
- the AWS CLI signed in;
- `securepay-seed` and `securepay-apis` cloned beside SecurePay (without `securepay-apis` there is no exchange-rates Lambda).

Terraform runs `infra/terraform/scripts/dev_up.py` for these steps, and a step that fails (a build, the seed task) fails the `apply`. A commit with uncommitted changes gets the tag `<commit>-dirty-<hash>`: commit first to keep the tags readable. The whole `apply` takes about 25 minutes: RDS and the image builds run side by side.

**Without Docker on this computer,** set `build_images = false` in `terraform.tfvars`. Then follow steps 6, 7 and 9 by hand: push the images yourself and set their tags. Set `load_data_on_apply = false` to seed and load by hand as well.

Everything runs in `infra\terraform\envs\dev`:

```powershell
cd infra\terraform\envs\dev
```

1. The first time, create your variables file:

   ```powershell
   Copy-Item terraform.tfvars.example terraform.tfvars
   ```

   Open `terraform.tfvars` and fill in `owner` (just your name, free text that goes in the `owner` tag) and `budget_emails` (your real email: the budget alerts and the operational alarms arrive there). For [step 7](#7-run-the-consumers-and-the-alerts-task-as-lambdas) also fill in `supervisor_emails` and `compliance_emails`: two different addresses, so you can see that each one gets only its own e-mails (with Gmail, `you+supervisor@gmail.com` and `you+compliance@gmail.com` land in the same inbox). For a short test, `database_multi_az = false` halves the RDS cost and saves 10 minutes each way. Git ignores this file.

2. Download the providers:

   ```powershell
   terraform init
   ```

3. See what will be created. With one `apply` (the default) it must say <code>Plan: {plan.oneApply} to add, 0 to change, 0 to destroy</code>, or {plan.oneApplyWithKaggle} with the Kaggle CSVs in `../securepay-csv/data/kaggle` (2 uploads and the Kaggle ETL run). With `build_images = false` and no tags it must say <code>Plan: {plan.stepByStep} to add</code>. Both with one budget e-mail and no supervisor, compliance or treasury e-mail; each address adds one subscription (`terraform plan` of {plan.checked}; what each part adds is in [Terraform](../architecture/terraform.mdx#what-it-creates)):

   ```powershell
   terraform plan
   ```

4. Create it and type `yes`. RDS takes 10 to 15 minutes:

   ```powershell
   terraform apply
   ```

   It ends with <code>Apply complete! Resources: {plan.stepByStep} added</code> ({plan.oneApply} with one `apply`, {plan.oneApplyWithKaggle} with the Kaggle CSVs, which also prints each `docker build` and the seed's `exit code 0`). AWS e-mails each address in `supervisor_emails`, `compliance_emails` and `budget_emails` a link "AWS Notification - Subscription Confirmation": **click Confirm subscription in each one.** `apply` does not wait for it, but until you click, SNS sends nothing to that address. Every new environment creates new subscriptions, so this happens after every `apply` from scratch. From this moment it costs money. With one `apply`, go on with the checks of step 5 and then send the transactions of steps 6.6 and 7.3. With `build_images = false`, the engine is not running yet: its service starts in [step 6](#6-deploy-the-engine-on-fargate), once its image is in ECR.

**If `apply` fails,** Terraform stops and prints `Error:` with the resource and the AWS message. What it created before the error stays in the state: fix the cause and run `terraform apply` again (it only creates what is missing; a resource that failed halfway is replaced), or run `terraform destroy`.

## 6. Deploy the engine on Fargate

With one `apply` (step 4), steps 1 to 5 are already done: start at step 6.

The engine image goes to ECR tagged with the short git commit, the admin image (the seed) seeds the database once, and then a transaction is sent through the load balancer. Docker Desktop must be running.

1. Log Docker in to ECR (the token lasts 12 hours) and keep the repository URLs:

   ```powershell
   $REPOS = terraform output -json ecr_repository_urls | ConvertFrom-Json
   ```

   ```powershell
   $REGISTRY = $REPOS.engine.Split("/")[0]
   $ECR_PASS = aws ecr get-login-password --region us-east-2
   docker login --username AWS --password $ECR_PASS $REGISTRY
   ```

   It prints `Login Succeeded` (and a warning about `--password`; the token only works for ECR and lasts 12 hours). Windows PowerShell can alter text piped to another program, so the usual `aws ecr get-login-password | docker login --password-stdin` fails there with `400 Bad Request`.

2. Build and push the engine from the root of the **SecurePay** repository (four folders up from `envs\dev`):

   ```powershell
   cd ..\..\..\..
   $ENGINE_TAG = git rev-parse --short HEAD
   docker build --provenance=false -t "$($REPOS.engine):$ENGINE_TAG" .
   docker push "$($REPOS.engine):$ENGINE_TAG"
   ```

   `--provenance=false` matters: without it Docker Desktop adds an attestation and pushes an image index, which Lambda rejects (`The image manifest, config or layer media type for the source image ... is not supported`). The Lambdas of step 7 run this same image.

3. Build and push the seed from the root of the **securepay-seed** repository (it is the admin image):

   ```powershell
   cd <path-to>\securepay-seed
   $ADMIN_TAG = git rev-parse --short HEAD
   docker build -t "$($REPOS.admin):$ADMIN_TAG" .
   docker push "$($REPOS.admin):$ADMIN_TAG"
   ```

   In **ECR → Repositories** each image shows its tag and, a minute later, its scan result. Pushing the same tag twice fails with `tag invalid ... already exists`: tags are immutable, so make a commit or use the existing image.

4. Go back to `infra\terraform\envs\dev`, add both tags to `terraform.tfvars` and apply. It must say `5 to add` (the two task definitions, the engine service and its autoscaling target and policy):

   ```hcl
   engine_image_tag = "<ENGINE_TAG>"
   admin_image_tag  = "<ADMIN_TAG>"
   ```

   ```powershell
   terraform apply
   ```

5. Seed the database with the admin task. Terraform prints the exact command:

   ```powershell
   Invoke-Expression (terraform output -raw admin_run_task_command)
   ```

   The task takes about a minute (pulling the image, then the seed itself, a few seconds in dev mode). Its output, which ends with `Seed completado.`:

   ```powershell
   aws logs tail /ecs/securepay-dev-admin --since 10m
   ```

6. Wait until the load balancer sees two healthy tasks, one per zone (**EC2 → Target groups → securepay-dev-engine → Targets**: 2 "healthy"), then ask the engine through the load balancer. `-k` skips the check of the self-signed certificate:

   ```powershell
   $ALB = terraform output -raw alb_dns_name
   curl.exe -k "https://$ALB/health"
   ```

   It answers `{"status":"ok", ...}`, with the decisions topic in `messaging`. Now a transaction between two seeded accounts ([`smoke-transaction.json`](https://github.com/SecurePay-Riwi/SecurePay/blob/main/infra/terraform/envs/dev/smoke-transaction.json), the Swagger example):

   ```powershell
   curl.exe -k -X POST "https://$ALB/transactions" -H "Content-Type: application/json" --data-binary "@smoke-transaction.json"
   ```

   It must return a decision (`"decision":"APPROVE"`, with `rules_version` and `processed_at`). Until the cache loader of step 7 runs, the cache holds no accounts, so the engine answers with the default decision (`"by_default":true`, the reason names the missing account): the engine never reads PostgreSQL (HU-67). Sending it again returns the same decision with `"idempotent_replay":true`: whichever task gets it, the answer comes from the shared cache.

7. Stop one engine task and watch ECS replace it:

   ```powershell
   $TASK = aws ecs list-tasks --cluster securepay-dev --service-name engine --query "taskArns[0]" --output text
   aws ecs stop-task --cluster securepay-dev --task $TASK --reason "failover test"
   ```

   ```powershell
   aws ecs describe-services --cluster securepay-dev --services engine --query "services[0].events[0:3].message"
   ```

   Within a minute or two the events say `has started 1 tasks` and the target group shows two healthy targets again. The other task keeps answering meanwhile: repeat the `curl.exe` of step 6.

**Tested on AWS on October 31, 2026** (engine `5f38965`, seed `94745a5`, single-AZ RDS): the seed took about 4 seconds; `/health` answered `{"status":"ok", ...}`; the smoke transaction returned `APPROVE` with `amount_usd` `28.32`, and `"idempotent_replay":true` the second time; the two tasks ran in `us-east-2a` and `us-east-2b`; after `stop-task` the events showed `deregistered 1 targets`, `has begun draining connections on 1 tasks` and `has started 1 tasks`, while `/health` kept answering.

## 7. Run the consumers and the alerts task as Lambdas

With one `apply` (step 4), the Lambdas exist and the cache is loaded. Only the e-mail test of step 2 needs `case_due_minutes = 2` and another `apply`, which changes the alerts Lambda in place; then go on at step 3.

The engine publishes every decision to `securepay-dev-decisions`, which copies it to three queues. Each queue has its Lambda: `securepay-dev-cases-consumer` and `-history-consumer` write to RDS from the application subnets, and `-analytics-consumer` writes the decisions to `raw/decisiones/` in the Data Lake from outside the VPC. `securepay-dev-alerts` runs every 5 minutes (EventBridge Scheduler): it escalates overdue cases to the supervisor, sends the restricted list summary to compliance, purges the 30-day history and retries the evidence. `securepay-dev-list-loader` copies accounts, merchants and the restricted list from RDS into the cache once a day at 01:00 Bogotá (HU-67). They run the engine image of step 6 with another command (`python -m awslambdaric <handler>`). Each Lambda that reaches RDS connects with its own database user and reads its own password from Parameter Store at startup; `securepay-dev-db-bootstrap`, which Terraform invokes during the apply, creates the tables, those users and their grants with the master user (see [Database users](../architecture/security.mdx#database-users)).

1. If your Terraform user was created before November 2026, paste again the whole [`terraform-user-policy.json`](https://github.com/SecurePay-Riwi/SecurePay/blob/main/infra/terraform/terraform-user-policy.json) in its inline policy `securepay-terraform-iam` (step 2.3): it now also lets Terraform hand the roles to Lambda and to EventBridge Scheduler (statement `PassRolesToServices`, which now names the three services; the policy must stay under the 2,048 characters IAM allows inline).

2. Add the image tag to `terraform.tfvars` (the same as the engine's) and, **only for this test**, 2 minutes per case instead of 4 hours, so the escalation e-mail arrives during the session:

   ```hcl
   lambda_image_tag = "<ENGINE_TAG>"
   case_due_minutes = 2
   ```

   ```powershell
   terraform apply
   ```

   It must say `21 to add`: the 6 functions and their 6 log groups, the `db-bootstrap` invocation, the 3 queue mappings, the two schedules (alerts and cache loader), the alerts invoke settings, its error metric filter and its alarm. **Lambda → Functions** shows the six, "Image" package type. (From `main` today the same apply also creates step 8, so it says `32 to add`.) If `db-bootstrap` fails, the apply fails with its error and nothing reads the queues.

   Check that `db-bootstrap` created the five users, and that a Lambda's configuration has the name of its password parameter but no password:

   ```powershell
   terraform state show 'module.lambdas.aws_lambda_invocation.db_bootstrap[0]'
   aws lambda get-function-configuration --function-name securepay-dev-cases-consumer --query "Environment.Variables"
   ```

   The first shows `result` with `"users": ["alerts", "cases_consumer", "history_consumer", "list_loader", "reconciliation"]`; the second shows `DATABASE_USER`, `DATABASE_PASSWORD_PARAMETER` = `/securepay/dev/rds/cases_consumer` and `CREATE_SCHEMA` = `false`, and no `DATABASE_URL`.

   Load the cache now instead of waiting for 01:00. It prints how many accounts, merchants and listed documents it wrote:

   ```powershell
   aws lambda invoke --function-name securepay-dev-list-loader --payload "{}" --cli-binary-format raw-in-base64-out list-loader.json
   Get-Content list-loader.json
   ```

   Without this load the engine answers with default decisions and the restricted list test below returns `HOLD` instead of `REJECT`. Valkey keeps nothing when the cache is recreated, so run it again after a new `apply` that replaces the cache.

   **Tested on AWS on November 3, 2026** (engine and Lambdas `7dd1ddb`, from `main` after MAG-356): after one `list-loader` run, `smoke-transaction.json` returned `APPROVE` without `by_default` and `restricted-transaction.json` returned `REJECT` with `restricted_list`, and the cases Lambda opened the case. The exchange-rates table was empty (nothing fills it in AWS yet), so the engine logged that and converted with the fixed snapshot.

3. Send a withdrawal from an account whose owner is on the restricted list ([`restricted-transaction.json`](https://github.com/SecurePay-Riwi/SecurePay/blob/main/infra/terraform/envs/dev/restricted-transaction.json); the seed is deterministic, so the account is the same in every environment seeded with the same `SEED_USERS`, 10,000 in `envs/dev`; with another number the seed lists other customers and this withdrawal is approved):

   ```powershell
   curl.exe -k -X POST "https://$ALB/transactions" -H "Content-Type: application/json" --data-binary "@restricted-transaction.json"
   ```

   It returns `"decision":"REJECT"`, `"rules_triggered":["restricted_list"]` and `"opens_case":true`.

4. The cases Lambda opens the case and writes the compliance report within seconds:

   ```powershell
   aws logs tail /aws/lambda/securepay-dev-cases-consumer --since 10m
   ```

   It shows `Cases: case <id> opened for transaction 7a2d3b5f-... (restricted_list)` and `1 restricted list report(s)`. The history and analytics Lambdas log their own line (`History: 1 row(s) written`, `Analítica: 1 eventos en s3://...`). The analytics line can take up to a minute: its queue waits up to 60 seconds to fill a batch of 1,000.

5. Within 5 minutes the alerts task sends the compliance summary, **only to the compliance address**. Within 5 more minutes (the case was due 2 minutes after it opened) it escalates the case and sends **one** summary, **only to the supervisor address**:

   ```powershell
   aws logs tail /aws/lambda/securepay-dev-alerts --since 15m
   ```

   Each run logs `Alerts: {'escalated': 1, 'notified': 0, ...}` with what it did. Check both inboxes: the supervisor never gets the restricted list summary and compliance never gets the escalation.

6. Nothing must be in the DLQs (`0` for the three):

   ```powershell
   aws sqs get-queue-attributes --queue-url (terraform output -json dlq_urls | ConvertFrom-Json).cases --attribute-names ApproximateNumberOfMessages
   ```

**Tested on AWS on November 2, 2026** (engine and Lambdas from the MAG-351 branch, seed `94745a5`): the restricted withdrawal returned `REJECT`; 10 seconds later the cases Lambda opened the case and its compliance report, the history Lambda wrote its row and the analytics Lambda wrote `raw/decisiones/fecha=2026-11-02/...jsonl`. The next alerts run escalated the case and sent the compliance summary: one e-mail each, each only to its address. The three DLQs stayed at 0. The first alerts run logged `platform.initReport ... "status":"timeout"` (the image's cold start in the VPC took more than 10 seconds); Lambda retried by itself and the run worked. That run also logged `purged: 1`: `restricted-transaction.json` is dated October 1, so the 30-day purge deleted its history row.

Remove `case_due_minutes = 2` from `terraform.tfvars` after the test: the default is the 4 hours of the business rule.

**Cost.** The Lambdas, the queues, the topics and the schedule cost cents during a session (they charge per request); the session still costs what step 6 costs, about USD 0.22 an hour, mostly the NAT Gateways, RDS, the cache and the load balancer.

### The rules and cases APIs

The same apply creates `securepay-dev-rules-api` and `securepay-dev-cases-api`, the HTTP API `securepay-dev-api` in front of them and the Cognito user pool the analysts sign in to (module `api`, [Terraform](../architecture/terraform.mdx#what-it-creates)). The paths are the ones of the local APIs; every route but `GET /health` needs a Cognito token, and the user's e-mail becomes `X-User`.

1. The apply already created the users of `api_users` (by default `analista@example.com` in `analista` and `gerente@example.com` in `gerente`, nobody can sign up) with a permanent password. Read them:

   ```powershell
   $pool = terraform output -raw user_pool_id
   $client = terraform output -raw user_pool_client_id
   $api = terraform output -raw api_url
   $passwords = terraform output -json api_user_passwords | ConvertFrom-Json
   $password = $passwords.'analista@example.com'
   ```

   With `api_users = {}`, create one by hand instead (an administrator does it; a password of at least 12 characters with upper case, lower case and numbers):

   ```powershell
   aws cognito-idp admin-create-user --user-pool-id $pool --username analista@example.com --message-action SUPPRESS
   aws cognito-idp admin-set-user-password --user-pool-id $pool --username analista@example.com --password "<password>" --permanent
   aws cognito-idp admin-add-user-to-group --user-pool-id $pool --username analista@example.com --group-name analista
   ```

   The passwords are in the Terraform state, which never leaves the computer that applies. That is fine for dev's demo users; prod would create real users by hand.

2. Sign in. The ID token lasts 60 minutes:

   ```powershell
   $token = aws cognito-idp initiate-auth --client-id $client --auth-flow USER_PASSWORD_AUTH --auth-parameters USERNAME=analista@example.com,PASSWORD="$password" --query AuthenticationResult.IdToken --output text
   $auth = @{ Authorization = $token }
   ```

3. Without a token the API answers `401`; with it, the rules and the cases:

   ```powershell

   Invoke-RestMethod "$api/rules" -Headers $auth | Select-Object version
   Invoke-RestMethod "$api/cases" -Headers $auth | Select-Object -ExpandProperty items
   ```

4. Change a rule without a redeploy (CA-06): disable velocity and enable it again. Only the `gerente` group changes the catalog, so the analyst's token gets `403`; sign in as the manager. Each change is a new catalog version with the manager as its author, and the engine reads it from the cache within a second (`rules_version` in its next decision):

   ```powershell
   curl.exe -s -o NUL -w "%{http_code}`n" -X POST -H "Authorization: $token" "$api/rules/velocity/disable"   # 403
   $manager = aws cognito-idp initiate-auth --client-id $client --auth-flow USER_PASSWORD_AUTH --auth-parameters USERNAME=gerente@example.com,PASSWORD="$($passwords.'gerente@example.com')" --query AuthenticationResult.IdToken --output text
   $auth = @{ Authorization = $manager }
   Invoke-RestMethod -Method Post "$api/rules/velocity/disable" -Headers $auth
   (Invoke-RestMethod "$api/rules/versions" -Headers $auth).versions[0] | Select-Object version, author
   Invoke-RestMethod -Method Post "$api/rules/velocity/enable" -Headers $auth
   ```

5. Assign and resolve the case of step 7 (its id is in `GET /cases`) as the analyst again; the case events record `analista@example.com`:

   ```powershell

   Invoke-RestMethod -Method Put "$api/cases/$case/assignee" -Headers $auth -ContentType "application/json" -Body '{"assignee": "analista@example.com"}'
   Invoke-RestMethod -Method Post "$api/cases/$case/resolution" -Headers $auth -ContentType "application/json" -Body '{"outcome": "FRAUD", "note": "Confirmed with the customer."}'
   ```

   Resolving archives the case's evidence in the evidence bucket ([step 11](#11-prove-that-evidence-cannot-be-deleted)).

The same steps work from the browser: the pages [/rules-api](/rules-api) and [/cases-api](/cases-api) sign in with these users and call the same API ([Rules and cases API pages](../components/api-console.mdx)).

The first call to each API after an apply takes a few seconds (the Lambda starts inside the VPC); the next ones answer in milliseconds. A `500` with `Internal Server Error` is the Lambda failing: `aws logs tail /aws/lambda/securepay-dev-rules-api --since 10m` (or `-cases-api`).

## 8. Run the nightly reconciliation

Every night at 02:00 Bogotá (07:00 UTC), EventBridge Scheduler starts the state machine `securepay-dev-reconciliation`. It runs four steps, and each one retries by itself:

1. **ReadStatements**: the Lambda `securepay-dev-statement-reader` reads the four partners' files of yesterday from `raw/extractos/` and writes `curated/extractos/fecha=<day>/`.
2. **MatchWithSpark**: the AWS Glue 6.0 job `securepay-dev-reconciliation-match` (Spark 4.1.1 and Python 3.13) runs `match.main` and writes `curated/conciliacion/fecha=<day>/`.
3. **SaveDifferences**: the Lambda `securepay-dev-difference-writer` runs `store.handler` against RDS.
4. **NotifyTreasury**: an e-mail to `-business-alerts` with `audience = treasury`, with the counts of the day.

The machine stops after 4 h 30 min. A run still going at 06:30 fails, and any failed, timed-out or aborted run triggers the alarm `securepay-dev-reconciliation-failed`. At 06:30 a second schedule also invokes the alerts Lambda with `{"job": "reconciliation_check"}`. If yesterday's run is not `DONE` in `reconciliation_runs`, it warns `-ops-alarms`; this also covers a run that never started. Everything goes to the team before the 07:00 deadline.

The match runs on AWS Glue, not EMR Serverless: on AWS's free account plan EMR is not available ([supported services](https://docs.aws.amazon.com/accounts/latest/reference/supported-services-sign-up-new.html)) and Glue is. Terraform zips `services/reconciliation` and `shared` itself and uploads the zip and `infra/spark/match_job.py` to `jobs/reconciliation/` in the artifacts bucket: there is nothing to build. When a run starts, Glue installs SQLAlchemy and python-dotenv (`--additional-python-modules`, the versions of `uv.lock`); it brings boto3.

## 11. Prove that evidence cannot be deleted

The evidence bucket has Object Lock. In dev it has no default retention, so `destroy` works the same day; instead, you upload a test object locked for 5 minutes in COMPLIANCE mode. Decide the time before uploading: COMPLIANCE can be extended but never shortened.

1. Get the bucket name (the one ending in `-evidence-<account>`):

   ```powershell
   terraform output bucket_names
   ```

2. Create a test file, compute the lock date (5 minutes from now, in UTC) and upload it. Replace `<evidence-bucket>` with the name from step 1:

   ```powershell
   "test evidence" | Out-File test.txt
   ```

   ```powershell
   $until = (Get-Date).ToUniversalTime().AddMinutes(5).ToString("yyyy-MM-ddTHH:mm:ssZ")
   ```

   ```powershell
   aws s3api put-object --bucket <evidence-bucket> --key test.txt --body test.txt --object-lock-mode COMPLIANCE --object-lock-retain-until-date $until
   ```

   It returns a `VersionId`. Each upload creates another version, and each version keeps its own lock.

3. Try to delete it with that `VersionId`. **It must fail** with `AccessDenied ... protected by object lock`:

   ```powershell
   aws s3api delete-object --bucket <evidence-bucket> --key test.txt --version-id <VersionId>
   ```

4. To see until when a version is locked (the time is in UTC, `+00:00`):

   ```powershell
   aws s3api get-object-retention --bucket <evidence-bucket> --key test.txt --version-id <VersionId>
   ```

Delete the local `test.txt` so it does not end up in a commit.

Resources: {plan.oneApplyWithKaggle} destroyed</code> after one `apply` with the Kaggle CSVs and one budget e-mail ({plan.oneApply} without the CSVs, {plan.stepByStep} step by step); each extra e-mail address is one more. The `powerbi` user goes with its access key (`force_destroy`), so there is no need to delete the key first. A Terraform user made before November 9, 2026 needs the policy again for `iam:CreateAccessKey` (the apply makes the Power BI key); one made before November 5, 2026 needs the whole [`terraform-user-policy.json`](https://github.com/SecurePay-Riwi/SecurePay/blob/main/infra/terraform/terraform-user-policy.json) pasted again in its inline policy: it now allows `iam:DeleteAccessKey` and `iam:DeleteLoginProfile` on the `securepay-*` users and `iam:ListVirtualMFADevices` (statement `ListMfaDevicesOnDestroy`: `force_destroy` lists the user's MFA devices, which IAM only allows on `*`, and always tries to delete its console password; without them the destroy stops with `AccessDenied` on `securepay-dev-powerbi`), and the instance profile and `AmazonSSMManagedInstanceCore` of the load test machine ([Load test](./load-test.mdx#from-inside-the-vpc-ec2)). Fewer if some steps were skipped: it destroys what the state has. The Glue job and its files go with it. The image repositories are deleted with their images. The buckets are emptied first, all versions included. If a version is still locked, only the evidence bucket fails: wait and run `terraform destroy` again.

**Check that nothing is left.** This must print nothing:

```powershell
terraform state list
```

In the console, NAT gateways must show "Deleted", **EC2 → Elastic IPs** must be empty (an address left alone keeps charging) and **RDS → Databases** must be empty. Deleted NAT Gateways and databases can still appear for up to an hour, and Tag Editor may list them for a while; they no longer cost anything.

**Cost.** The bill does not show what is running right now: **Billing → Cost Explorer** shows each day about 24 hours later (group by service, daily). To filter future tests by `project = securepay`, activate the `project` tag once in **Billing → Cost allocation tags**; it counts only from the day it is activated.

## Automatic deploys from GitHub Actions

Steps 6 and 7 build and push the image by hand. Once dev exists, `.github/workflows/deploy.yml` does the same on every merge to `main`: it assumes the role `securepay-dev-deploy` with GitHub's OIDC token (no AWS keys in GitHub; the role only trusts the `main` branch), pushes the engine image to `securepay-dev-engine` tagged with the short commit, registers a new revision of the engine task definition with that image, rolls out the ECS service `engine`, updates and runs `db-bootstrap` (a new image may need new tables or grants), and then updates the seven Lambdas of steps 7 and 8. Terraform still creates and destroys the environment.

**Once:** create the repository variable with the role ARN (anyone with admin access to the repository). Get the ARN:

```powershell
aws iam get-role --role-name securepay-dev-deploy --query Role.Arn --output text
```

Then in GitHub: **SecurePay → Settings → Secrets and variables → Actions → Variables → New repository variable**, name `AWS_DEPLOY_ROLE_ARN`, value the ARN. It is a variable, not a secret: it holds no key, only the account number.

**Run it by hand** after an `apply`, to deploy what is already in `main`: **Actions → Deploy → Run workflow** (branch `main`). The job log ends with `Engine running ...` and one `... running ...` line per Lambda.

**Tested on AWS on November 3, 2026.** With dev up but no image tags, the first run built `7dd1ddb`, pushed it to ECR and ended green with the notices "Engine not deployed" and "Lambda not deployed". After the `apply` with that tag, the second run reused the image (`Image 7dd1ddb is already in ECR.`), rolled out the engine service in 3 min 24 s without a rollback and updated the seven Lambdas in 1 min 25 s. Before the fix of the deploy role's trust (`github_immutable_subject`), "Get AWS credentials" failed with `Not authorized to perform sts:AssumeRoleWithWebIdentity`.

| Situation | Result |
| --- | --- |
| Dev destroyed (the role does not exist) or the variable is not set | Green, with the notice "Nothing deployed" |
| `Not authorized to perform sts:AssumeRoleWithWebIdentity` in "Get AWS credentials" (green, with the notice "Nothing deployed") | The token's `sub` does not match the role's trust. CloudTrail shows the one GitHub sent: `aws cloudtrail lookup-events --lookup-attributes AttributeKey=EventName,AttributeValue=AssumeRoleWithWebIdentity --max-results 1`; compare it with `github_immutable_subject` in `modules/iam` |
| The image tag is already in ECR (a rerun of the same commit) | The image is reused; tags are immutable |
| The service or a Lambda does not exist yet (no image tag in `terraform.tfvars`) | Green, with a notice for each one |
| The new tasks fail their health checks | The ECS circuit breaker rolls back and the job fails with "Rollback" |
| `db-bootstrap` returns an error | The job fails with "db-bootstrap failed" before touching the other Lambdas, which keep their old image; its log is `/aws/lambda/securepay-dev-db-bootstrap` |

**securepay-apis** has the same workflow for its own image: on every merge to its `main` it assumes `securepay-dev-deploy-apis` (it only trusts the `main` branch of securepay-apis, and may only push to `securepay-dev-apis` and update `securepay-dev-exchange-rates`), pushes the image tagged with the short commit and updates the exchange-rates Lambda. It needs its own repository variable: `AWS_DEPLOY_ROLE_ARN` in **securepay-apis → Settings → Secrets and variables → Actions → Variables**, with the ARN of `aws iam get-role --role-name securepay-dev-deploy-apis --query Role.Arn --output text`. The SecurePay workflow does not touch that Lambda.

A later `terraform apply` puts back the image of your clone (with `build_images`) or of `terraform.tfvars` in the engine and the Lambdas. Run **Deploy** again after every `apply`, or `git pull` before applying so your clone is the deployed commit. Cost: the deploy itself is free (GitHub Actions); while it rolls out, two engine tasks run side by side for a few minutes.

## Rules

- **One computer.** The state (`terraform.tfstate`) stays in `envs\dev` on your computer and git ignores it. Always run `apply` and `destroy` from the same computer: another one has no state and does not know what exists.
- **Never share the state.** It holds the RDS passwords in plain text.
- **Never commit** `terraform.tfvars`, `terraform.tfstate` or anything with keys. Do commit `.terraform.lock.hcl` when `terraform init` adds hashes to it.

## Errors already seen

| Error | Cause | What to do |
| :--- | :--- | :--- |
| `uv` is not recognized, or `docker ... failed` during the `apply` | One `apply` builds the images on this computer | Install uv, start Docker Desktop and apply again; or set `build_images = false` and follow steps 6 to 9 |
| The `apply` fails at `terraform_data.seed` with `exit code 1` | The seed task failed | `aws logs tail /ecs/securepay-dev-admin --since 30m` names the cause; fix it and apply again (the seed empties its tables first) |
| `aws` or `terraform` is not recognized | The terminal was open before the install | Open a new terminal (close VS Code completely if it is its terminal) |
| `InvalidClientTokenId` | Access key copied wrong | `aws configure` again |
| `not authorized to perform: ec2:DescribeAvailabilityZones` | The Terraform user is missing `PowerUserAccess` | In IAM → Users → your Terraform user → Permissions, attach `PowerUserAccess` directly. Keep the `securepay-terraform-iam` inline policy too, then retry `terraform plan` |
| `UnicodeDecodeError` in `dev_up.py` while Terraform reads image tags | Git returned a diff that is not valid in the Windows console encoding | Update SecurePay to the latest code and retry `terraform plan` |
| `FreeTierRestrictionError: backup retention period` | An account on the AWS free plan accepts at most 1 day of RDS backups | Already handled: dev uses `database_backup_retention_days = 1`. If a similar error mentions Multi-AZ, add `database_multi_az = false` to `terraform.tfvars` |
| `docker login` fails with `400 Bad Request` | PowerShell altered the token piped to `--password-stdin` | Use the variable form of step 6.1 |
| `not authorized to perform: iam:PassRole` on the task definition | The Terraform user lacks the statement `PassRolesToServices` | Paste again the whole `terraform-user-policy.json` in its inline policy |
| The engine service never gets healthy tasks; `aws logs tail /ecs/securepay-dev-engine` shows `ResourceNotFoundException` or no logs | The image tag does not exist in ECR | Check the tag in ECR and in `terraform.tfvars`. The circuit breaker rolls the deployment back on its own |
| `curl` gets `503` with `idempotencia` | The engine cannot reach the cache | Check that `VALKEY_CLUSTER` is `true` in the task definition and the cache is "Available" |
| `terraform apply` fails creating a Lambda with `image manifest, config or layer media type ... is not supported` | The image was built without `--provenance=false` | Build again with `--provenance=false` and a new commit (tags are immutable), set the new tag and apply |
| `not authorized to perform: iam:PassRole` creating a Lambda or the schedule | The Terraform user lacks `lambda.amazonaws.com` or `scheduler.amazonaws.com` in `PassRolesToServices` | Paste again the whole `terraform-user-policy.json` (step 7.1) |
| `terraform apply` fails on `aws_lambda_invocation.db_bootstrap` | `db-bootstrap` could not reach RDS or Parameter Store, or a SQL statement failed | `aws logs tail /aws/lambda/securepay-dev-db-bootstrap` shows the cause. The apply can be run again: the bootstrap is idempotent |
| A Lambda logs `permission denied for table ...` or `for sequence ...` | Its database user lacks a grant its code needs | Add it in `services/db_bootstrap/grants.py` (and a test), build a new image and apply: the new tag runs `db-bootstrap` again |
| No e-mail arrives from the alerts task | The subscription is still "Pending confirmation" | Click the link of the confirmation e-mail (also check spam), or **SNS → Subscriptions → Request confirmation** |
| `AccessDenied ... protected by object lock` on `destroy` | A test object is still locked | Wait until its retain-until date and run `destroy` again |
