# Load test the engine

RN-01 says every transaction gets its decision in 200 ms or less. The brief sizes the load at 50 tx/s sustained and 300 tx/s at the peak ([Estimated figures](../architecture/infrastructure.mdx#estimates)). This test sends 50, 150 and 300 tx/s to the engine on Fargate in dev, 5 minutes each, and records latency, errors, default decisions and how many tasks autoscaling started.

The files are in `infra/load/`:

| File | What it is |
| :--- | :--- |
| `locustfile.py` | [Locust](https://locust.io/): each simulated core sends one transaction per second, so users = tx/s. The shape holds each step of `LOAD_STEPS` for `LOAD_STEP_SECONDS` and stops. At the end it prints how the engine answered (`APPROVE`, `HOLD`, `REJECT`, `default`) |
| `transactions.py` | The requests: P2P 60 %, QR 25 %, RECARGA 10 %, RETIRO 5 %, between the seed's active accounts, each in the payer's currency, with a new id each |
| `accounts.json` | The seed's 9,820 active accounts with their currency (one per line), and its 20 active merchants. AWS dev is seeded with the same volume (`SEED_MODE=dev`, `SEED_USERS=10000` in `envs/dev`), so these ids exist there. To write it again, seed locally with `SEED_USERS=10000` and run `python -m infra.load.accounts` |

`services/decision_engine/tests/test_load_transactions.py` checks that every generated transaction is a request the engine accepts.

## Where to read the result

Run from your computer, Locust reaches the load balancer over the internet, so its times include the trip from Colombia to `us-east-2` (about 80 to 120 ms). Run from the EC2 machine inside the VPC ([below](#from-inside-the-vpc-ec2)), they include only a few milliseconds of network. **The 200 ms limit is judged inside AWS:**

- the load balancer's `TargetResponseTime` p99, which is the time the engine took, on the dashboard `securepay-dev` and in alarm 1;
- the engine's decision log, which lists every decision slower than 150 ms (query `securepay-dev/slow-decisions`);
- for each default decision by timeout, one `late_decision` line on the same log with where its time went: `queue_ms` (waiting for a worker), `lookup_ms` (the accounts' round trip to Valkey), `history_ms` (the history's round trip), `rules_ms` and `total_ms`. A stage it never reached is missing. It also carries how many connections to the cache the task has opened (`cache_connections`) and how many times it reloaded the cluster's map (`cache_refreshes`) since it started: if they jump between two lines of the same task (`@logStream`) in the seconds of a stall, the client reconnected. In Logs Insights, on the engine's log group:

```
fields @timestamp, @logStream, queue_ms, lookup_ms, history_ms, rules_ms, total_ms, cache_connections, cache_refreshes
| filter event = "late_decision"
| sort @timestamp asc
```

Locust's numbers say what a client sees, and they are the ones to look at for errors.

## Run it

1. Dev must be up with the engine on Fargate, the database seeded and the cache loaded: [Deploy to AWS](./deploy-aws-terraform.mdx), steps 4 to 7. In particular, run `-list-loader` once. Otherwise every decision is a default decision and the test measures the wrong thing. Confirm the `ops-alarms` subscription to see which alarms fire.

   Dev runs 2 to 4 engine tasks by default (`engine_min_tasks`, `engine_max_tasks`). The test sizes the service as the design does, 4 to 24, so set it in `terraform.tfvars` and apply before the test:

   ```hcl
   engine_min_tasks = 4
   engine_max_tasks = 24
   ```

   Remove the two lines afterwards, or destroy dev: 4 tasks idle cost twice what 2 do.

2. Install Locust (it is in the `load` dependency group, outside the default ones):

   ```powershell
   uv sync --group load
   ```

3. Check one request (from the root of `SecurePay`; `$ALB` as in step 6 of the deploy page):

   ```powershell
   $env:LOAD_STEPS = "5"; $env:LOAD_STEP_SECONDS = "30"
   uv run --group load locust -f infra/load/locustfile.py --headless --host "https://$ALB" --only-summary
   ```

   0 failures and mostly `APPROVE` and `HOLD` in the `decisions` line.

4. The full test (15 minutes). Open the dashboard first, and save Locust's numbers as CSV:

   ```powershell
   Remove-Item Env:LOAD_STEPS, Env:LOAD_STEP_SECONDS
   New-Item -ItemType Directory -Force load-results
   1..3 | ForEach-Object { Start-Process -NoNewWindow uv -ArgumentList "run --group load locust -f infra/load/locustfile.py --worker" }
   uv run --group load locust -f infra/load/locustfile.py --master --expect-workers 3 --headless --host "https://$ALB" --csv load-results/run
   ```

   Three worker processes and one master. One Locust process tops out at a few hundred requests per second, and 300 tx/s needs headroom. Locust's `--processes` option does not work on Windows. Each worker prints its own `decisions` line at the end, so add them up. If Locust warns that the CPU is above 90 %, the client is the bottleneck, not the engine: add workers or run from a faster computer.

5. While it runs, note for each step (50, 150 and 300):

   | Measure | Where |
   | :--- | :--- |
   | p50 and p99 inside AWS | Dashboard: engine latency (`TargetResponseTime`) |
   | p50 and p99 at the client, errors | Locust's summary, `load-results/run_stats.csv` |
   | Default decisions | Locust's `decisions` line; dashboard: decisions |
   | Engine tasks running | **ECS → securepay-dev → Services → engine**: running count; or `aws ecs describe-services --cluster securepay-dev --services engine --query "services[0].runningCount"` |
   | CPU of the tasks | Dashboard, or the service's CPU in ECS |
   | Cache size and use | **CloudWatch → Metrics → ElastiCache**: `BytesUsedForCache` (max) and `ElastiCacheProcessingUnits` (sum) of `securepay-dev-cache`, at the end of the 300 step. It closes the cache size question of [Open questions](../architecture/open-questions.mdx) |
   | Queues and database | Dashboard: queue age, RDS CPU and connections. Each decision also goes to the three queues and becomes database rows |
   | Alarms that fired | **CloudWatch → Alarms**, and the `ops-alarms` inbox |

6. Write the numbers in the table below and in the logbook, then destroy dev (or keep it for the EKS session of [Run the engine on Kubernetes](./kubernetes.mdx), which uses the same test).

### From inside the VPC (EC2)

The recommended way for the measured run. The client is an EC2 machine in an application subnet (`modules/load_runner`, topic 6 of the brief): Amazon Linux 2023, `c7i-flex.large` (2 vCPU, allowed on AWS's free account plan, USD 0.0848 an hour on demand). It has no SSH, no key and no inbound rule: Systems Manager runs the test, and the CSV files go to the artifacts bucket under `load-tests/`. With it, your computer's CPU and the internet no longer count in Locust's numbers.

1. Add `load_runner = true` to `terraform.tfvars` and apply. It must say `7 to add`: the role, its two policies, the instance profile, the security group, its HTTPS rule and the machine. The machine clones `main` (`load_runner_git_ref` changes the branch) and installs Locust by itself in about 3 minutes:

   ```powershell
   terraform apply
   ```

2. Run the full test (15 minutes) and keep the command id. Start the dashboard first:

   ```powershell
   $RUN = Invoke-Expression (terraform output -raw load_test_command)
   $VM = terraform output -raw load_runner_instance_id
   ```

   Ask how it is going; it says `InProgress` until it ends, then `Success` and the summary with the `decisions` line:

   ```powershell
   aws ssm get-command-invocation --command-id $RUN --instance-id $VM --query "[Status, StandardOutputContent]"
   ```

   If it fails at once with `securepay-load: command not found`, the machine was still installing: wait a minute and run step 2 again.

3. Copy the CSV files, `run_stats.csv` among them:

   ```powershell
   $ARTIFACTS = (terraform output -json bucket_names | ConvertFrom-Json).artifacts
   aws s3 cp --recursive "s3://$ARTIFACTS/load-tests/" load-results/
   ```

4. Remove `load_runner = true` and apply again (`7 to destroy`), or leave it for `terraform destroy`.

A shorter run is `securepay-load <seconds per step> <tx/s> ...`. For example, this does 30 seconds at 5 tx/s, like step 3 above:

```powershell
aws ssm send-command --instance-ids $VM --document-name AWS-RunShellScript --parameters "commands=securepay-load 30 5" --query Command.CommandId --output text
```

## Expected and how to read it

- **Autoscaling** starts at 4 tasks and adds tasks at 60 % CPU or at 1,800 requests per task per minute (30 tx/s, `engine_requests_per_task`), whichever asks for more, up to 24. The estimate is about 25 tx/s per task (0.5 vCPU). 50 tx/s should hold on the 4 tasks, and 300 tx/s should reach about 12 tasks. If p99 goes above 180 ms while tasks are still being added, the scaling is too slow for the ramp: lower the CPU target or raise the minimum. Record the time from the start of the 300 step to the last new task.
- **HOLD grows with the load.** 9,820 accounts share the load. At 50 tx/s an account sends about 2 transfers in 10 minutes and velocity (more than 5 in 10 minutes) seldom fires; at 300 tx/s it sends about 11 and velocity holds about half of the traffic (run 5: 0.2 % HOLD at 50 tx/s, 54 % in the last minute at 300). A HOLD is a full decision with every rule run, so it costs about the same as an APPROVE, but it adds a line to the decision log. `REJECT` comes from the accounts whose owner is on the restricted list.
- **Default decisions above 1 %** (alarm 2) mean the rules or the cache did not answer in `DECISION_TIMEOUT_MS`. That is a failure of the test even if the latency looks good.
- After the test, the engine's history in Valkey keeps these accounts' activity for 24 hours (`out:{account}`), and the cases consumer has opened cases for the restricted accounts. Dev is disposable; do not run this against data that matters.

**Cost.** The 15 minutes of load cost about USD 0.10 with 10 tasks; each step is in [Cost of a run](#cost). Dev itself is about USD 0.15 an hour more.

## Result

**Where it stands (November 8, 2026).** RNF-01 and CA-09 ask for a p99 of 200 ms or less at 300 tx/s. With 10 tasks of 0.5 vCPU **it is not met end to end**: at 300 tx/s the load balancer's p99 goes above 200 ms in some minutes of every run (run 5: 229 ms over the step; runs 7 and 8: 205 to 215 ms in some minutes). It is met at 50 and 150 tx/s, at 300 tx/s in most minutes and on Locust's p99 (140 to 180 ms in runs 7 and 8), and with 20 tasks (run 4: 129 ms). The cause is a pause of 100 to 300 ms about once a minute, not the load or the CPU. It is a known issue, open, to be fixed after the delivery: see [Known issue: p99 at 300 tx/s](#known-issue).

Run 5 (November 5, 2026, 21:28 UTC), from the EC2 machine, 10 tasks at 0.5 vCPU that never scaled out, the cache limited to 20,000 ECPU/s:

| Step | Requests | p50 / p95 / p99 in AWS (ms) | Default decisions | 5XX | CPU avg / max |
| :--- | ---: | :--- | ---: | ---: | :--- |
| 50 tx/s | 14,967 | 12 / 18 / 50 | 0.02 % | 1 (load balancer) | 4.5 / 6.6 % |
| 150 tx/s | 44,723 | 22 / 36 / 85 | 0.07 % | 1 | 13.1 / 16.7 % |
| 300 tx/s | 89,796 | 32 / 106 / **229** | 0.40 % | 2 | 26.6 / 40.8 % |

At the client (Locust, every step): p50 29 ms, p99 170 ms, 4 `HTTP 502` in 149,486 requests (the load balancer's 5XX, none from the engine). The cache never throttled (peak 14,430 ECPU/s; read p99 3.6 ms). The limit is met at 50 and 150 tx/s, not at 300 tx/s: the p99 per minute was under 200 ms in 2 of the 5 minutes (184 and 125 ms) and above in 3 (207, 290 and 267 ms). Of the 389 default decisions, 298 fell in the first 5 seconds of a minute: something stalls once a minute, not the load. The `late_decision` line (above) is there to find it in the next run.

Every run of the day, at 300 tx/s:

| Run | Tasks | Change before it | p95 / p99 (ms) | Default decisions |
| :--- | ---: | :--- | :--- | ---: |
| 1 | 4 to 5 | — | — | 100 % |
| 2 | 10 | late decisions waiting for a worker are cancelled (`_decide_in_time`) | p50 1,250 | — |
| 3 | 10 | the cache's limit from 5,000 to 20,000 ECPU/s (`cache_max_ecpu_per_second`) | 164 / 246 | 1.79 % |
| 4 | 20 | — (to check that the limit was per task) | 40 / 129 | 0.40 % |
| 5 | 10 | 4 round trips to Valkey per decision instead of 8.4 | 106 / 229 | 0.40 % |
| 6 | 10 | the `late_decision` line (only measures) | p99 about 150 to 160 per minute, 250 in the minute of the step to 300 | about 0.3 % |
| 7 | 10 | Valkey client timeouts and keepalive (PR #125) | client p99 180; load balancer p99 about 200 to 215 per minute | 0.2 % |
| 8 | 10 | node-based cache, `cache_node_type = "cache.m7g.large"` (PR #128) | client p99 140; load balancer p99 about 150, two minutes at 205 to 215 | 0.1 % |

Run 6 (November 7, 2026, 20:43 UTC) repeated run 5 with the `late_decision` line, to find the once-a-minute stall:

- **At 300 tx/s the limit was met in every minute but one.** The load balancer's p99 per minute stayed at about 150 to 160 ms, except in the minute of the step from 150 to 300 tx/s (about 250 ms at 20:54), so the run still does not meet it end to end. In that minute the cache was scaling itself: its maximum write latency rose to about 50 ms, and for a few seconds the accounts' lookup took 200 to 650 ms. The engine's CPU stayed under 25 %.
- **The stall at second :02 is not the cache and not the client.** Of the 342 default decisions, 260 fell in the first 5 seconds of a minute, most of them at :01 to :03. In those decisions `lookup_ms` and `history_ms` both grow (50 to 180 ms each) while `rules_ms` stays near 0 and `queue_ms` mostly under 50 ms. The cache's own maximum latency per minute (`SuccessfulReadRequestLatency`, `SuccessfulWriteRequestLatency`) stayed at a few milliseconds outside 20:54, and the decisions that reach the engine at :02 are as many as in any other second (171 to 173, the busiest second had 181). The time is lost between the engine and the cache (the network, ElastiCache Serverless's proxy or the client's connections), on 10 to 20 decisions a minute, under 1 %: it does not move the p99.

Run 7 (November 7, 2026, 23:42 UTC) repeated run 6 with explicit socket timeouts and keepalive on the Valkey client (PR #125) and two counters on the `late_decision` line. Locust: 149,340 requests, 2 failures, p50 29 ms, p99 180 ms over every step, 0.2 % default decisions. The load balancer's p99 at 300 tx/s was about 200 to 215 ms per minute. The stall at seconds :01 and :02 stayed, on all 10 tasks in the same second, and no task reconnected or reloaded the cluster's map in it (`cache_refreshes` always 0, `cache_connections` only grew at 23:52, while the cache scaled for 300 tx/s). The time is lost inside ElastiCache Serverless's own layer, which its latency metrics do not count. Run 8 compares it with a node-based cluster: `cache_node_type = "cache.m7g.large"` in `terraform.tfvars` (one shard, a primary and a replica in the other zone); without it the cache stays Serverless.

Run 8 (November 8, 2026, 03:26 UTC) repeated run 7 with a node-based cluster instead of Serverless. Locust: 149,339 requests, 5 failures, p50 25 ms, p99 140 ms, 147 default decisions (307 in run 7). The stall at seconds :01 to :03 stayed, mostly on one task and again without reconnections, so it was not the Serverless layer. **Known issue, open:** something pauses an engine task about once a minute for 100 to 300 ms. The likeliest cause, not proven, is the log output: every HOLD writes a line (about a quarter of the traffic at 300 tx/s), and a slow delivery to CloudWatch makes the process wait. The way to check it is a run with `decision_line()` limited to REJECT and default decisions. The limit is met on the client's p99 and in most minutes at the load balancer, but not in every minute: see [Known issue: p99 at 300 tx/s](#known-issue).

In run 2 the cache throttled about 72,000 commands a minute. In runs 3 to 5 it throttled none, and the CPU stayed under 41 %: what is left is the pause once a minute (runs 6 to 8, [known issue](#known-issue)). The autoscaling did not add tasks in run 5 because 300 tx/s over 10 tasks is exactly its target of 1,800 requests per task per minute.

With the numbers:
- check alarm 1 (p99 > 180 ms) and alarm 7 (fewer than 2 healthy tasks per zone), and adjust `latency_p99_seconds` or `min_healthy_tasks_per_zone` of `modules/monitoring` if they fired with the engine healthy;
- confirm or revise [ADR-07](../architecture/decisions.mdx#adr-07) (the maximum of 24 tasks).

**Tested locally** (November 4, 2026), against one engine process (`uvicorn`, no workers) with local Valkey: 25 tx/s for a minute, 0 failures, p99 150 ms. That only proves the script. It says nothing about Fargate.

**First run in AWS** (November 5, 2026), with 4 to 24 tasks and the 98 accounts of the seed of then: it failed. 50 tx/s held. At 150 tx/s the load balancer's p99 rose to 3 s and then to 6 s, the engine never passed about 80 tx/s, and 73 % of the decisions were default decisions (17,600 of 24,000 per worker; 4 `HTTP 502` in 71,879 requests). The service stayed at 4 tasks: its CPU never passed 38 %, under the 60 % target. The engine's log said why: `elapsed_ms` p50 was exactly 120 ms (`DECISION_TIMEOUT_MS`), so most rules ran out of time.

The cause was the test, and a weakness it uncovered. 98 accounts took about 700 transactions each in 15 minutes, `out:{account}` keeps 24 hours, and every decision read and parsed the account's whole day from Valkey. Reproduced locally (one core, 150 tx/s, about 600 movements per account): p50 121 ms and 27 % default decisions; about 70 % of the time went to reading Valkey's reply in Python. The changes:

| Change | Where | Local result (same case) |
| :--- | :--- | :--- |
| Valkey's C reply parser | `valkey[libvalkey]` in `pyproject.toml` | p50 65 ms, 6 % default decisions |
| The rules read at most the newest 100 outgoing movements (team decision, November 5, 2026) | `HISTORY_OUT_LIMIT` in `history.py`; the catalog caps velocity's `limit` at 99 and splitting's `min_transactions` at 100 | p50 11 ms, 0 % default decisions |
| 9,820 accounts instead of 98 | `SEED_USERS=10000` in `envs/dev`, `accounts.json` | 15 ms with 9,820 accounts |
| Scaling on requests per task, not only CPU | `aws_appautoscaling_policy.engine_requests` | Checked in AWS in the next run |

The table above is filled in with the next run.

## Known issue: p99 at 300 tx/s {/* #known-issue */}

**Status: open.** The team decided on November 8, 2026 not to optimize the engine further before the delivery ([Team decisions](../architecture/team-decisions.mdx#no-more-engine-optimization)). It has to be fixed afterwards.

| Item | Detail |
| :--- | :--- |
| Requirement | RNF-01 / CA-09: decision p99 ≤ 200 ms at 300 tx/s in the load test |
| Met | At 50 and 150 tx/s (run 5: p99 50 and 85 ms). At 300 tx/s: in most minutes at the load balancer, on Locust's p99 (140 to 180 ms in runs 7 and 8) and with 20 tasks (run 4, 129 ms) |
| Not met | At 300 tx/s with 10 tasks, end to end at the load balancer: run 5, 229 ms over the step; run 6, about 250 ms in one minute; run 7, about 200 to 215 ms per minute; run 8, 205 to 215 ms in two minutes |
| Not the cause | The CPU (under 41 %), the cache's capacity (no throttled commands), ElastiCache Serverless (run 8 with nodes kept the pause), the client's connections to the cache (no reconnections, run 7) |
| Symptom | An engine task pauses 100 to 300 ms at seconds :01 to :03 of each minute, sometimes one task, sometimes all of them. The default decisions gather there |
| Hypotheses, not proven | 1. The log output: every HOLD writes a line, and a slow delivery to CloudWatch blocks the process. 2. Python's garbage collector pausing the process |
| Next check | One run with the `awslogs` driver in non-blocking mode (`mode = non-blocking` and a `max-buffer-size`) and `uvicorn --no-access-log`; in the same run, measure the GC pauses (`gc.callbacks`, logged once a minute). If the pause goes away with the first, the fix is the log; if not, the second says whether it is GC |
| Workaround today | 20 tasks meet the limit, but the team does not accept 20 fixed tasks for a pause the CPU does not explain |

E-15 asks for the cost of each step. These are the resources the load adds, for run 5 (the reference: 10 tasks the whole time, ElastiCache Serverless, the requests of its table above). Rates for `us-east-2`, on demand:

| ElastiCache Serverless (Valkey) | $0.0023 per million ECPUs; $0.084 per GB-hour, at least 100 MB billed | Same page; the [ElastiCache pricing page](https://aws.amazon.com/elasticache/pricing/) gives the same rates (its example is N. Virginia) |

Assumptions:
- 10 tasks for the whole 15 minutes (autoscaling did not add any in run 5).
- About 33 ECPUs per decision ([Terraform](../architecture/terraform.mdx)), so about 9,900 ECPU/s at 300 tx/s. The measured peaks were higher (12,200 to 14,430 ECPU/s, up to about 48 per decision); with 48 the cache column grows by about 40 %, half a cent for the run.
- Cache storage billed at the 100 MB minimum. It was not measured: the idempotency keys of 150,000 decisions may take it to a few hundred MB, which adds under half a cent for the run.
- Load balancer: Locust keeps its connections open, so the capacity units come from processed bytes, about 2 KB per request and answer: about 0.35 LCU at 50 tx/s, 1 at 150 and 2 at 300.
- The EC2 machine runs the whole test.
