# Testing

Each repository runs its own tests with `uv run pytest` from its root:

| Repository | Tests | Where | Needs |
| :--- | ---: | :--- | :--- |
| `SecurePay` | 256 (engine, rules API, consumers, shared) | `services/*/tests/`, `shared/tests/` | PostgreSQL with the seed, Valkey, LocalStack |
| `securepay-seed` | 29 | `tests/seed/`, `tests/kaggle_etl/` | Nothing |
| `securepay-generator` | 32 | `tests/` | Nothing |
| `securepay-csv` | 46 | `tests/kaggle_datasets/`, `tests/partner_statements/` | Nothing (one test uses LocalStack and is skipped without it) |
| `securepay-apis` | 38 | `tests/restricted_list/`, `tests/exchange_rates/` | Nothing (two tests use LocalStack and are skipped without it) |

While the backup folders `db/`, `generators/` and `sources/` stay in `SecurePay`, its `uv run pytest` also runs their old copies of the source tests.

## How to run the tests

**1. Start the local services**, so that no test is skipped (see [Local setup](./local-setup.mdx)):

```bash
docker compose up -d
```

**2. Load the seed** from the `securepay-seed` repository. The engine API tests need the users, accounts and restricted list in PostgreSQL:

```bash
cd ../securepay-seed
uv run python -m securepay_seed.seed
```

**3. Run the tests from the root of each repository:**

```bash
uv run pytest
```

**Run only part of the suite:**

```bash
uv run pytest services/decision_engine   # SecurePay: only the engine
uv run pytest services/consumers         # SecurePay: only the consumers and messaging
uv run pytest shared                     # SecurePay: only the shared database connection
uv run pytest tests/partner_statements   # securepay-csv: only the partner statements
uv run pytest -k velocity                # tests whose name contains "velocity"
uv run pytest -rs                        # also show why each test was skipped
uv run pytest -x                         # stop at the first failure
```

## How to read the results

pytest prints one character per test while it runs and a summary line at the end:

| Mark | Meaning | What to do |
| :--- | :--- | :--- |
| `.` | Passed | Nothing. |
| `s` | Skipped: a service it needs (Valkey or LocalStack) is off | Start it with `docker compose up -d` and run again. `-rs` says which service. |
| `F` | Failed: the code did not do what the test expects | Read the assertion under `FAILURES`; it shows the expected and the actual value. |
| `E` | Error while preparing the test (a fixture failed) | Usually configuration: a wrong `.env` value or a missing seed. |

**A healthy run** with every service up and the seed loaded ends with all tests passed:

```text
181 passed
```

**The same run with nothing started** (no Docker) looks like this. It is expected, not a bug:

```text
14 failed, 148 passed, 19 skipped in 16.17s
```

- The **19 skipped** are the Valkey and LocalStack tests: they detect the service is off and skip themselves.
- The **14 failed** are the engine API tests. They do not skip: the engine answers `503` when Valkey is down, so they fail on purpose to make the missing dependency visible.

**Common causes of a failure:**

| Symptom | Likely cause |
| :--- | :--- |
| API tests fail with `503` | Valkey is not running. |
| API tests fail with `422` (account not found) | The seed is not loaded, or it was loaded with another seed value. Reload it with `SEED_RESET=true`. |
| Velocity or idempotency results look shifted | Keys left over from a previous run. Clean Valkey (see [Simulate the full flow](./simulate-full-flow.mdx#1-clean-valkey)). |
| A generator test with exact counts fails | Something changed the generator's randomness; with seed 42 it must always produce 1,035 events. |

## Conventions

- Each rule's fraud pattern has a **control case** that sits just on the side that must *not* trigger the rule. If the engine flags a control case, the engine is wrong.
- The generator is deterministic: with seed 42 it always produces 1,035 events, the same on Windows and Linux. Tests can rely on exact counts.
- Test names describe the behavior they check (`test_sixth_transfer_in_ten_minutes_is_held`), so a failure line already says what broke.
